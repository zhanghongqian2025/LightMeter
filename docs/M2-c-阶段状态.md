## 1. 位置级排除：序号模型与三步顺序

### 1.1 两级粒度

| `occurrence` | 语义 | 来自 |
|---|---|---|
| `ANY = -1` | 这个值**所有**出现处都别脱 | M2-b 能力，缺省值 |
| `>= 0` | 只别脱**第 occurrence 次**（0 基） | M2-c 新增 |

缺省（JSON 里没有这个字段）= ANY，与 M2-b 语义一致，**不破坏已有客户端**。

### 1.2 序号口径：按「界面上看得见的那一批」编号

序号在 `resolveOverlaps` **之后**、`applyExclusions` **之前**算，口径是
「不排除时会出现在清单里的那些命中」。于是被身份证规则挡掉的手机号片段**不占序号**——
用户看不到它，界面也不该让它占一个号。

### 1.3 三步顺序不可换

```
1. collected = collectMatches(text, rules)
2. ordinals  = assignOccurrences(resolveOverlaps(collected), numbering)
3. collected = attachOccurrences(collected, ordinals)   ← 必须在过滤之前
4. kept      = applyExclusions(collected, excl)
5. kept      = resolveOverlaps(kept)
6. apply(text, kept, allocator)
```

**第 3 步的位置是这一块最贵的坑**：我第一版把序号回填在 `applyExclusions` 之后，
于是喂给 `applyExclusions` 的 `Match.occurrence` 仍然是 `-1`，
位置级排除**一条都匹配不上**。

症状极具欺骗性：`occ=0` 的输出与「完全不排除」**一模一样**，接口返 200、
报告数字正常、值级排除照常工作。探针 `Probe2` 打出来是这样：

```
occ=-1 -> [甲 13800138000 乙 <手机号1>]
occ=0  -> [甲 <手机号1> 乙 <手机号2>]   ← 错误，等于没排除
occ=0  -> [甲 13800138000 乙 <手机号1>] ← 修好后
```

对照实验 **⒕** 就是把这一步挪回错误位置，钉死它。

### 1.4 引擎层回归：我自己破坏了自己写的不变式

第一次把编号插在 `resolveOverlaps` **之后**、`applyExclusions` 之前——
这样「被挡掉的输家」也能拿到序号，看起来更周全，结果 `ExclusionTest.排除输家时赢家也要让开` 红了：

```
expected: 证件 11010519491231002 结束
actual:   证件 <丁1>231002 结束
```

因为输家一被排除，赢家就失去了「该不该接管这一段」的依据。
改成「先按 NONE 口径统一算序号 → 排除 → 再 resolve」才对。

> 这条值得记一笔：**我给引擎加的「更完整」的口径，破坏了引擎原本就有的不变式。**
> 测试当场抓住了它——这正是为什么每加一层语义就要配套加测试。

### 1.5 「替换倒着做，记录正着发」

`apply()` 里替换**必须从文末向前**做（否则前面的偏移会把后面的位置推走），
但 `changes` 记录**必须按访问顺序（start 升序）发出**——因为界面上的序号
是按清单顺序数的。两个方向不一致的话，界面上的「第 2 处」会落到文件的第 1 处。

代码注释里明确写了「访问顺序 ≠ Word 翻页顺序（docx 按 zip 条目顺序走）」，
没有夸大成「文档顺序」。

### 1.6 紧凑构造器里的 null 回落

`HitRef.occurrence` 用 `Integer` 而不是 `int`，原因是实测发现
**Jackson 给缺失的 int 字段填 `0` 而不是 `-1`**。
用 `int` 会把「这个值整条别脱」悄悄变成「只放过第 0 次出现」——
用户以为整条排除了，实际后面几次照样被脱，而界面上看不出任何异常。

报文里**显式写 `occurrence: 0` 仍然表示「第 0 次」**，两者语义不同，
这个区分由 `Integer` 的 null 回落保住。

## 2. 隐形路径审计：5 处「改了内容但命中不进清单」

M2-b 之后我审计了全部 11 个 `session.redact` 调用点，找出 5 处**隐形路径**：

| 位置 | 改的是什么 | 为什么隐形 |
|---|---|---|
| `PdfRedactor.java:130` | PDF 文档元数据 | 不在文本层，命中不进清单 |
| `XlsxRedactor.java:218` | 工作表名 | 表名在 zip 里排在单元格之前 |
| `XlsxRedactor.java:232` | 定义名称 | 同上 |
| `XlsxRedactor.java:246` | 批注 `<t>` | 批注文本不在单元格 |
| `OfdRedactor.java:437` | 附件条目名 | 条目名不是 TextObject |

全部改为 `session.redactHidden(...)`：**照常脱敏、照常进映射、照常服从值级排除，
但不消耗出现序号**。

### 2.1 为什么它们不能占序号

序号口径是「界面上看得见的那一批」。如果隐形路径占序号：

- 用户在界面上数到第 2 处，实际文件里那 1 处是**别的东西**；
- 用户勾「第 3 次别脱」，作用到了一个他从来没在界面上看到过的位置；
- **全程零报错**——文件正常生成、报告数字漂亮、令牌也对。

让它们不占序号，代价是「同一值在正文出现 3 次、在元数据出现 1 次，
界面上说出现 3 次」——但那是**少报**，方向上多脱，安全；
而错位是**作用在错误的位置上**，方向不可控。

### 2.2 ⒖ 的第一次 GREEN：又是测试不敏感

变异把 3 处 `redactHidden` 改回 `redact`，测试**跑出来是绿的**。
查下去是**测试不敏感**，不是变异无效：xlsx 夹具的工作表名原本排在单元格**之后**，
所以改变它不影响序号归属。

修法：给 `XlsxFixture` 加 `sheetName(String)`，并让测试把表名写在 `sheetData` **之前**
（zip 条目顺序），这样「表名不占序号」才真的可观测。

> 第二次撞上同一类问题：**破坏跑出 GREEN 时，先分清是「变异无效」还是「测试不敏感」，
> 不要直接改期望值。**

## 3. 任务 LRU 回收

### 3.1 满 64 时淘汰最久未访问者，而不是报错

原来是 `throw new TooManyJobsException()`。改成 access-order `LinkedHashMap`
（**不是插入序**——插入序会踢掉用户正在挑排除项的那一份，
因为用户上传完往往先挑几个 job 对比，最后才回到第一个）。

`TooManyJobsException` **整个删掉了**：它已永不抛出，
而它的文案「关掉服务再试」是**假的**（用户没法关一个本地服务的 UI）。
永不抛出的异常 + 说谎的文案 = 该删。连带删掉 `ApiHandlers.java` 两处 catch。

### 3.2 淘汰必须连磁盘一起清

`evictOldest()` 里除了丢内存条目，还调 `workspace.delete(sourceName / previewName / outputName)`。
不删的话，用户以为处理完就没了，**原始文档其实一直躺在临时目录里**——
对一个脱敏工具来说这是隐私问题，不是磁盘问题。

`/api/health` 如实报出 `activeJobs` / `maxJobs` / `evictedJobs`。

对照实验 **⒗**（淘汰时不删磁盘文件）、**⒘**（改成插入序）守住这两条。

### 3.3 ⒘ 第一次 INVALID：判据选了会抛异常的

⒘ 最初用 `assertThrows` 判断淘汰行为，变异体导致 `IOException`，
**红灯原因是异常不是断言失败**，脚本按纪律判 INVALID。

改成「磁盘文件是否存在」后既咬住了又不抛异常。
> 对照实验的判据要优先选**不会抛异常的事实**。

### 3.4 `JobStore.scan` 拆出无 HTTP 版本

`scan(String clientName, byte[] body)` 与 HTTP 版本分离。
连传 65 份文件时每份起一个 socket，测试慢了十倍——而淘汰逻辑与 HTTP 无关。

## 4. 排除项对不上时，接口返 400 而不是出件

`JobStore.verifyExclusionsMatch`：排除项对不上扫描结果（值没命中，或序号越界）
→ `BadRequestException` 400，**被拒的 jobId 也取不到任何产物**。

这里**有意与 M2-b 的口径不同**：

| 层 | 行为 | 为什么 |
|---|---|---|
| 引擎层 | 对不上就**照常脱敏** | fail-closed 到「多脱」这一侧，M2-b ⒑ 钉死 |
| 接口层 | **整个请求 400，不出件** | 不该交回一份没按要求处理的文档 |

原 `RedactionApiTest.无效排除项不误伤` 那条断言 200，与新守卫冲突。
选择改守卫（更严：不出件），同时保留引擎层 fail-open-to-redact 的性质
（`ExclusionTest` 那条仍绿）——**两个层次各守各的不变式，不互相迁就**。

## 5. Web 界面

`src/main/resources/web/{index.html, app.js, app.css}` 全部重写。
三步流程条 + 三个面板 + 命中清单表格（列：保留 / 原值 / 规则 / 出现处 / 文档中写入）。

### 5.1 下载走 `fetch` + Blob，不是 `<a download>`

`/api/download` 需要 `X-Litemask-Token` **自定义头**，
而导航请求带不上自定义头。所以：fetch → `URL.createObjectURL` → 临时 `<a download>` → 立刻 `revokeObjectURL`。

### 5.2 前端一律 `textContent`，用户数据走 `dataset`

绝不 `innerHTML`。理由不是洁癖：**这个页面恰好是唯一能看到敏感原值的地方**，
是 XSS 最值钱的落点。

### 5.3 静态接线对账（`WebUiTest` 15 条）

脚本里 `$("id")` 引用的每个 id 页面里都必须存在；三个步骤、三个面板、接口路径对得上；
下载必须走 fetch；全程不碰 `innerHTML`/`outerHTML`/`document.write`。

> **这些静态检查必须先去注释再查**：文件头的纪律注释里就写着「绝不拼进 innerHTML」，
> 不剥注释的话断言永远红，而且红得毫无意义。

### 5.4 清单的一行现在可能代表**多个值**（2026-10-19 补）

原先一行 = 一个 `(规则键, 原值)`，前端把 `ruleKey` / `original` 放在 `dataset` 上、
勾选时直接发这两个值。这条形状在「一个标识符被不同规则切开」时不再成立：
同一个地址会被切成三段、显示成三行。

现在：

| 项 | 改前 | 改后 |
|---|---|---|
| 一行的含义 | 恒为 1 个值 | **1 个或 N 个值**（N>1 时是「归组行」） |
| 排除项来源 | `dataset.ruleKey` + `dataset.original` | `dataset.members`（JSON 数组），勾选时**逐个成员**发 N 条 |
| 计数口径 | 行数 | **按值**（`distinctHits` / `excluded` / `redacted`），另给 `summary.rows` 区分行数 |

归组行带 `merged` class 与「原文里紧挨着的 N 处命中」标注。
**映射本身没有合并**——一行归组仍对应 N 条映射、文档里仍是 N 个紧挨着的令牌。
归组条件与「PDF 为什么不归组」见 **M3-3 §1.21**。

服务端为此加了一道 fail-closed 守卫：归组行只排除一部分成员时**整个请求 400**，
不留「保留了一半的标识符」（同 §4 的纪律，触发条件不同）。

> ⚠️ 这条**浏览器那半边没有真人验收**（本项目一直没有浏览器自动化测试）。
> `WebUiTest` 里只有静态断言守着「按成员逐个 `excluded.push`」，
> 真正的安全网是服务端那道 400 守卫。

### 5.5 映射出口与还原：界面上现在真的可逆（2026-10-19 补）

**缺口是怎么发现的**：`Workspace` 的类注释写着「预览件、成品件、**映射件**都走这里」，
但 `newDiskName` 全项目只有两处调用点——**映射件这条路从来没被走过**。
而映射本身只活在 `job.applied.mapping()` 那块内存里：进程一退出，映射就没了。
`POST /api/restore` 则是一个明明白白的 **501 占位**。

也就是说，命令行那条路（`litemask redact` 产映射件 → `litemask restore --map` 还原）
是通的，但**界面这条路上，用户拿不到映射、也就没法还原**。
G1「可逆」对产品主界面不成立——界面上显示「脱敏成功」而实际上不可逆，
这比不做脱敏更糟。

#### 5.5.1 映射件必须落盘

映射落盘在**会话目录**里，和原件、成品件同一套敏感数据纪律：

| 项 | 取值 | 为什么 |
|---|---|---|
| 存放位置 | 会话目录 | 进程退出整棵删；不留「桌面上的映射件」 |
| 文件名 | `<uuid>.json` | 与成品件同格式，不含用户输入 |
| 淘汰 | LRU 淘汰时**连它一起删** | 映射和它对应的原件同生共死 |
| 取用 | **要令牌** | 映射里全是原值，与 `/api/download` 同一条纪律 |
| 上传白名单 | **不进** | `newMappingName()` 与 `newDiskName()` 分开：后者校验的是「用户能传什么」 |

> `newMappingName()` 单独开一个方法，是因为 `newDiskName` 会在上传白名单上做校验——
> 把 `.json` 塞进去等于开了「上传 json 冒充映射件」的口子。
> 单测 `WorkspaceTest.映射件名字与上传白名单` 直接把 `evil.json` 传进去，
> 要求抛 `UnsupportedFileTypeException`。

#### 5.5.2 映射文件长什么样

顶层必须有 `"mapping"`（**令牌 → 原值**），方向与命令行产出的映射文件一致，
所以 **GUI 产出的映射件可以直接喂给 `litemask restore --map`**。

顶层其余字段：

| 字段 | 内容 |
|---|---|
| `mapping` | 令牌 → 原值，**还原只依赖这一段** |
| `format` | 源格式 |
| `source` | 源文件名 |
| `changes` | 按**值**聚合的清单（命令行侧按**处**） |
| `notes` | 写明上面那处结构差异 + 「可以直接用 `litemask restore --map` 还原」 |

> `changes` 的结构与 CLI 不同是**有意的**：界面按值计（见 §5.4），命令行按处计。
> 还原只依赖 `mapping` 段，所以两边互不影响——但这个差异必须写在文件里，
> 否则用户拿 GUI 的映射件去对 CLI 的输出，会以为哪里错了。

映射件用**带缩进**的 JSON（`Json.toPrettyBytes`），
而接口响应仍是紧凑的——映射件是要被人打开看的文件。

#### 5.5.3 `POST /api/restore` 还原的是服务端自己那份成品

**它不接上传体。** 不引 multipart、不做「用户传回一个自己改过的脱敏件」这条路——
那是 CLI `restore --map` 的活，而且那条路已经通了。
服务端只还原**自己生成的那份成品**，攻击面最小。

还原件是中间产物，**读进内存后立刻删掉**（`finally` 里 `workspace.delete(outName)`）：
它含原值，留在会话目录里就是多一份敏感数据。

响应体是**文件**（用户要的就是那份还原出来的文档），处数与提醒放响应头：

| 头 | 含义 |
|---|---|
| `X-Litemask-Restored` | 实际替换了几处 |
| `X-Litemask-Notice` | 百分号编码的提醒（如「还原的是文本内容，不是文件字节」） |

> 「还原了 0 处」这种事实**必须能被调用方读到**，
> 否则它会拿着一份没变的文件以为还原成功。所以哪怕正文已经是文件，
> 头里也必须留一个位置放它。

#### 5.5.4 还原的边界：文本内容，不是文件字节

还原是**有限的**。下面这些动作**不可逆**，原值从未被保存过：

| 不可逆的动作 | 说明 |
|---|---|
| 文档属性清空 | Author / Creator 等，PDF、OFD 都有 |
| 签章移除 | 签章数据不保留 |
| 数值单元格转文本 | 公式与数值格式的还原不保留 |

所以还原件与原件**在文本上一致，但不是同一个文件**。
这条提醒在**接口响应头**和**界面提示**里都写出来了。

OFD 另有一条专属提醒（Author/Creator 直接清空、签章已移除）；
PDF 的 `restore` 自带 warnings，一并透出。

#### 5.5.5 前端接线

下载卡片上多了两个按钮：「下载映射文件」「还原并下载」。

- 三个下载按钮共用一个 `下载(path, 文件名, 按钮id, 错误id)` 辅助函数
  （fetch + Blob + `revokeObjectURL`——下载要带自定义头，导航请求带不上）；
- 还原按钮读 `X-Litemask-Restored`，显示「已还原 N 处」；
- 还原失败走 `restoreError`，不塞进别的错误位；
- 重新走一遍流程时 `againBtn` 会把 `state.mappingName` / `state.restoreName` 复位。

> 界面必须**明说**两件事：映射是还原的唯一凭据；还原的是文本内容不是文件字节。
> 这两句是用户判断「我的原值还在不在」的唯一依据。
>
> ⚠️ 这一块的**浏览器那半边仍然没有真人验收**（同 §9.1）。
> 现有的安全网在服务端：未 apply → 400、无令牌 → 403、未知的任务 → 400。

### 5.7 长任务：进度反馈与取消（2026-10-19 补）

#### 5.7.1 为什么要有：界面在长任务上是「装死」的

此前的脱敏是在**请求线程里同步跑完**的：界面上点「开始扫描」，按钮就一直是禁用的，
文案停在「正在扫描…」，用户既看不到进度，也没法放弃，只能等。

更糟的是本地服务的 HTTP 线程池只有 4 个：几份大文件就能把它占满，
连 `/api/health` 都答不上来——界面连「服务还活着吗」都问不出来。

这一块把「上传」与「脱敏」拆成两段，中间夹一个**可轮询、可取消**的状态：

```
POST /api/task-scan   → 202 {ok, taskId, status:"running"}   ← 立刻返回
GET  /api/task?taskId=→ 200 {status, phase, done, total, message, result?}
POST /api/task-cancel?taskId= → 200 {status:"canceling"}      ← 只是受理
```

界面每 500ms 轮询一次 `GET /api/task`，直到 `status` 变成 `done` / `failed` / `canceled`。

#### 5.7.2 任务表刻意不放在 `JobStore` 里

`JobStore` 的监视器会被正在跑的脱敏占着（落盘、登记这些短操作要在锁里）。
如果任务表也放在那里，**读进度的人会被干活的人堵住**——那正好抵消了这一块的意义。

所以任务表独立成 `server/TaskRunner`：`ConcurrentHashMap` + 固定 2 个工作线程。
轮询完全不碰 `JobStore` 那把锁。

顺带把 `JobStore` 里的**重活移出了监视器**：脱敏、还原、读文件在锁外，
只有淘汰与登记在锁内的短临界区。原先一次 `scan` 会把整个 `JobStore` 锁住整段脱敏时间。

> **顺带修掉一个既有缺陷**：`JobStore.jobs` 是 **access-order** 的 `LinkedHashMap`，
> 而 `require()` 里的 `get()` **会重排链表**，此前却**从未加锁**——
> 4 个 HTTP 线程并发就足以损坏它。本块给 `job` / `require` / `size` 都加上了 `synchronized`。

#### 5.7.3 取消是协作式的，而且**不产出任何文件**

`TaskContext` 在管线里布了检查点：每个文本单元之前、每条规则之前、每个 NER 来源之前。
取消之后跑到下一个检查点就停。

关键在**停下来的那一刻什么都不留下**：

- 扫描被取消 → 已落盘的**原件**与**半成品预览件**都被删掉；
- 应用被取消 → 半成品成品件被删掉，**映射件不写**。

否则用户点了「取消」，界面上文件不见了，磁盘上却躺着一份他以为没上传过的敏感文档。
那是对脱敏工具最不能出现的那类落差。

取消**不把线程从中间拽走**——那会留下半写坏的文档。检查点落在「正在处理一个单元」
和「正在跑一条规则」上，是安全的粒度。

#### 5.7.4 进度不报百分比

各格式的文本单元总数**事先都算不出来**：PDF 按内容流、OOXML 按段落、OFD 按文本对象，
而段落数要等文档解析完才知道。所以 `total` 只能传 `-1`，界面上显示
「已处理 N 个文本单元」，进度条走**不确定态动画**。

> 拿一个估算值糊出「47%」比说「不知道」更糟——用户会以为它可信。
> 这条是**写进代码注释**的取舍，不只是文档里的一句话。

#### 5.7.5 界面走异步，脚本走同步

同步的 `POST /api/scan` 与 `POST /api/apply` **仍然留着**：脚本与命令行式调用
要的是一个「发过去、拿结果」的来回，拆成两段反而更麻烦。
界面改走异步那套。

`WebUiTest.写接口都有入口` 的断言**又一次改了方向**：
现在查的是异步那 4 个路径（`/api/task-scan`、`/api/task-apply`、`/api/task`、`/api/task-cancel`），
并**额外断言界面不再调同步那两个**——界面用同步接口就等于在长任务上装死，
那正是这一块要解决的问题。

任务完成后的 `result` 与同步接口**同形状**，界面拿到直接就能渲染，不必再调一次。

#### 5.7.6 取消在 HTTP 层也要令牌

`GET /api/task` 的结果里是**命中清单**，清单里全是原值——和下载映射件一样，
所以它也是 `write=true`。查进度不是「读」，这一点不能含糊。

#### 5.7.7 界面那半边：静态断言也得会「咬人」

浏览器那半边仍然**没有自动化浏览器**（长期缺口，见 §9），
守着它的只有 `WebUiTest` 的静态断言。这一块把它们加固了三处：

1. **接线断言卡的是「接上了事件」，不是「引用过这个 id」**。
   脚本里还有别处会引用 `cancelBtn`（比如设置它的禁用态），
   只查「出现过 `$("cancelBtn")`」的话，把监听器整段删掉也能过——
   而那正是按钮点了没反应的形状。**这条是被对照实验逼出来的**：
   照原样写时，「删掉取消按钮的监听器」这一条变异**没被咬住**（§5.7.8）。

2. **新增括号配平检查**。静态断言全是字符串匹配，它们看不见
   「这段根本不是合法的 JavaScript」。脚本少写一个右括号，浏览器会把整个文件丢掉，
   界面变成一片空白，而服务端那几十条单测**全绿**——没有任何人会收到信号。
   现在有一个只看括号的检查（**不是 JS 解析器**，更细的语法错误仍然抓不到，
   原因是要真解析就得给核心包加进几十 MB 的 JS 引擎依赖）。

3. **不确定态的类名必须与样式里的选择器对得上**。类名对不上，
   那段动画根本不生效，进度条会是一根不动的死条。

#### 5.7.8 这一块实际跑了什么

单测新增 **37 条**（`TaskCancelTest` 8 + `TaskApiTest` 9 + `WebUiTest` 20），
其中「取消」那几条判据都是**产物层面**的：取消之后
`JobStore` 里没有 job、会话目录里一个文件都不剩——
不是「接口说取消了」。

对照实验新增 **12 条**（ⓧⓨⓩ + ❶-❽ + ❾），逐条对应一个真实失效形状：

| 编号 | 变异 | 咬住它的测试 |
|---|---|---|
| ⓧ | 取消不生效（点了取消，任务照跑到底） | `TaskCancelTest` |
| ⓨ | 取消后不删原件（用户以为没上传过，原文档还躺在磁盘上） | `TaskCancelTest` |
| ⓩ | 进度不递增（界面上的进度永远停在 1） | `TaskCancelTest` |
| ❶ | 总量报一个假数（界面画出 47%，而那个数是编的） | `TaskApiTest` |
| ❷ | 进度回调根本不调（界面永远停在「准备中」） | `TaskCancelTest` |
| ❸ | 已跑完的任务被谎报成已取消 | `TaskCancelTest` |
| ❹ | 任务表满了不拒绝，默默删掉一个正在跑的任务 | `TaskCancelTest` |
| ❺ | 任务跑完不回结果（界面上只剩一个空清单） | `TaskApiTest` |
| ❻ | 界面改回同步接口（长任务上界面又装死了） | `WebUiTest` |
| ❼ | 取消按钮没接上事件（点了毫无反应） | `WebUiTest` |
| ❽ | 不确定态的样式改了名（进度条成了一根死条） | `WebUiTest` |
| ❾ | 脚本少一个右括号（浏览器丢掉整个脚本，界面空白而服务端全绿） | `WebUiTest` |

**❼ 第一次没咬住**，这是本轮最值得记的一条：
照原样写时，静态断言只查「出现过 `$("cancelBtn")`」，
而脚本别处（`showTask` 设置它的禁用态）也引用这个 id——
把监听器整段删掉照样绿。改成查 `$("cancelBtn").addEventListener` 之后才咬住。

> 顺带发现：❼ 的变异体其实把 app.js 改成了**语法错误**，
> 而服务端全绿。所以顺手补了「脚本括号配平」检查（§5.7.7 第 2 点）——
> 那条检查抓的是「整段不是合法 JavaScript」这一类，不是 JS 解析器。

端到端（`tools/e2e-serve.sh` 9g 章节）新增 **24 条**，
其中「真取消」那一条用 12 万行纯普通文字的 txt：
提交 → 立刻取消 → 终态 canceled → **没有 jobId** → 会话目录里**前后文件数不变**。

**这一块还有一个当时没注意到的缺陷**，是被后来的浏览器端到端抓出来的：
扫完之后「生成脱敏文件」按钮一直是禁用的（§5.8.4）。

### 5.8 浏览器那半边：真 Chrome 驱动的端到端（2026-10-19 补）

#### 5.8.1 补的是哪个缺口

「界面那半边没有自动化测试」是本项目的**长期缺口**（§9.1）。
守着它的只有 `WebUiTest` 的静态断言——而静态断言全是字符串匹配，
它们看不见「脚本在浏览器里根本没跑起来」这件事。

最典型的形状：**app.js 少写一个右括号**。浏览器会把整个文件丢掉，
页面变成一片空白，而服务端那几十条单测**全绿**——
没有一个人会收到任何信号。括号配平检查（§5.7.7）能挡住这一类最常见的破坏，
但它只挡「少一个右括号」这一种，其余语法错误照旧漏。

#### 5.8.2 为什么没直接用现成的浏览器自动化工具

原计划是直接用宿主提供的 `capture_browser_scenario`。**实测走不通**：
它要一个 `actions` 数组，而参数绑定层把这个数组**强制转成了对象**
（`{"item": [...]}`），服务端每次都回「actions: must be array」。
三次不同形状的入参都一样。这是**宿主参数绑定的限制**，不是缺 Chrome
（本机 Chrome 155 就在 `/Applications`）。

于是自己写了一个 CDP 驱动（`tools/browser-cdp.js`）：
Node 22 自带全局 `WebSocket`，连 devtools 的 ws、发命令收事件，**零第三方依赖**。
依赖是要进核心包体积预算的，一个测试脚本不值得为它引一棵树。

#### 5.8.3 驱动做了什么

用 `--headless=new` 起一个 Chrome（独立临时 profile，结束即删），
连上 devtools 的 page target，然后：

- `Page.navigate` 打开首页；`Runtime.enable` + `Log.enable` 收**未捕获异常**与 console error；
- `DOM.setFileInputFiles` 往文件输入框里塞样本——这一步会触发 change 事件，
  和真人选文件走的是同一条路；
- `Runtime.evaluate` 点按钮、等条件；
- `Page.captureScreenshot` 存证据；
- `Browser.setDownloadBehavior` 让下载**真的落到盘上**，
  这样「下载后的文件名和页面显示的是不是同一个」可以自动判。

**42 条断言**（2026-10-20 补了「不支持的后缀被提交时拒掉」那 5 条），覆盖：
脚本跑起来了没有 → 选文件 → 扫描 → 命中清单 →
进度文案 → 应用 → 下载卡 → 下载文件名 → **真点一次取消** →
窄屏（420px）下没有横向溢出、长文件名没被吞掉。

样本由 `tools/gen_browser_fixture.py` 现造（zipfile + 手写 XML，**不 import 任何项目代码**）：
一份小文档（身份证跨三个 run、手机号、邮箱、页眉、文档属性）、
一份 8000 段的大文档（够慢，取消才点得中；段落型，进度才看得见在爬）、
一份文件名 60 个汉字的文档（测窄屏换行）。

#### 5.8.4 它当场抓到了两个真缺陷

**（一）界面能扫、不能脱——这是本轮我自己引入的回归**

`showTask` 把「生成脱敏文件」按钮禁用了，而 `hideTask` 只在
「应用」那一种任务结束时才放开它——于是**扫完之后那个按钮永远是禁用的**。

点一个禁用的按钮**不会报错、不会发请求、界面上什么现象都没有**：
用户只看到「扫描完了，但生成不了文件」。
那几处代码**单看都合理**，服务端几十条单测全绿也没人发现。
真正抓到它的是浏览器：点「生成脱敏文件」之后下载卡没出现，
而 `/api/download` 返 400。

修法：三个按钮的可用状态**收在一处**（`syncButtons`），
判据只剩一个——「有没有 jobId」。

**这个缺陷顺手补了一条静态代理断言**（`WebUiTest` 20 → 22 条）：
判据是「按钮的可用状态由 jobId 决定」——源码里必须出现
`$("applyBtn").disabled = !state.jobId;`，且 `syncButtons()` 的调用点**不少于 2 处**
（一处定义、一处触发；只有一个定义没人叫，等于没接上）。

但它是**代理，不是本体**：静态断言只能证明「这句话还在源码里」，
证明不了「点了真的有反应」。本体的牙是浏览器端到端。
所以对照实验里给这条缺陷配了变异 **❿**（把判据换成恒禁用），
它必须让单测变红——**静态代理能咬住自己，才敢把它留在回归里**。

> 顺带一条值得记住的：**`element.click()` 对禁用的按钮照样返回成功**，
> 只是不派发事件。任何用「点 DOM 元素」驱动的测试，
> 都必须**另外断言按钮的 `disabled` 状态**，否则会一路绿到底。

**（二）窄屏下整页横向溢出 173px**

`.steps` 是 `display:flex` 却没写 `flex-wrap`，三个步骤被撑成一行（527px）；
再加上 `main` 的 grid 列是 `auto`（基准尺寸 = 各项 min-content 贡献），
而规则表那种宽表格的 min-content 有 500 多像素——
于是 420px 宽的屏上整页被顶宽 173px，**步骤条把别的内容都顶没了**。

修法三处一起，缺一不可：
`grid-template-columns: minmax(0, 1fr)`、`.card { min-width: 0 }`、`.steps { flex-wrap: wrap }`。
后两处缺一个，内容照样顶得开——**这是量出来的，不是看出来的**：
用 `width: min-content` 探针逐个元素量，才知道是「规则卡片的 min-content = 565」在顶。

#### 5.8.5 怎么证明这个测试会咬人：负控制

一个永远绿的浏览器测试比没有测试更坏。所以驱动支持**在传输途中改写 app.js**
（CDP 的 `Fetch` 域，页面拿到的就是被改过的脚本）：

| 负控制 | 改写 | 期望 | 实测 |
|---|---|---|---|
| ① | 删掉取消按钮的监听器 | 必须失败，且失败点落在「取消」那几条 | 失败点正是「点取消后界面进入「正在取消」」「任务终态是「已取消」」 |
| ② | 制造一个语法错误 | 必须失败，且失败点落在「规则表已填充」 | 失败点正是「规则表已填充」，且浏览器报出 1 条未捕获异常 |

断言逻辑与正常跑**完全一致**——驱动不认得自己被变异了，它只认页面上的事实。
所以「变异后必须失败」这件事是**自证的**。

① 正是当初静态断言咬不住的那一条（§5.7.7）：静态断言只看「引用过这个 id」，
而浏览器测的是「点了有没有反应」。

> **一条测试判据自己被「必要的失败」带偏了的例子（2026-10-20 补）**：
> 加上「不支持的后缀」那个场景之后，「控制台无 error」这条断言红了——
> 因为浏览器对任何 4xx 的 fetch 都会在控制台记一条
> `Failed to load resource: ... status of 400`，而那一次 400 **是场景故意造出来的**。
>
> 修法不是把这条断言删掉，也不是把它放得宽一点，而是**按次数 + URL + 措辞**三者
> 同时对上才放行（必须是 `/api/task-scan`、必须提到 400、只能放过预期条数那么多）。
> 只认「400」两个字的话，页面里真正的 400 会被一起放过——
> **判据变弱和判据变严，在输出里长得一模一样。**

#### 5.8.6 这一块还剩什么没验

浏览器自动化验的是**行为**，不是**观感**。以下仍然只能靠人眼：

- 步骤条折行之后断在哪里、挤不挤；
- 长文件名在表格单元格里换行的视觉效果；
- 配色与对比度。

这些已写进 §9.1，并注明「自动部分已覆盖、观感部分未验」。

### 5.9 上传先落盘：排队中的任务不再抱着 256MB 字节（2026-10-20 补）

#### 5.9.1 这块在补什么缺口

§9 第 8 条记的那个缺口：后台任务从「提交」到「被工作线程捡起来」之间，
那份上传内容一直在**堆**里等着（一个 `byte[]`）。
任务表上限 64、单份上传上限 256MB —— 于是「连着提交 64 份大文件」在理论上就能把内存撑爆，
而那只是用户多拖了几个文件而已。

修法是**先落盘再交任务**：等的那份内容从堆变成磁盘空间，内存里只剩一个 64KB 的缓冲。

#### 5.9.2 三段式：暂存 → 认领 / 丢弃

`Workspace` 多了三个动作：

| 动作 | 做什么 | 关键点 |
|---|---|---|
| `stage(in, clientFilename)` | **流式**写到 `sessionDir/upload-<uuid>.tmp` | 先判后缀再写盘；64KB 分块；超限立刻停 |
| `store(staged)` | `Files.move` 认领成正式件 | 改名不是拷贝（大文件下差别是实打实的） |
| `discard(staged)` | 删掉没人认领的暂存件 | 删不掉不算失败（清理是尽力而为） |

**暂存件只有两个去处**：被认领，或者被丢弃。**没有第三条路**——
留在盘上的暂存件就是一份没人知道它是什么的原文档。

三处取舍，写清楚为什么：

1. **后缀先判、盘后写。** 不支持的类型压根不该占磁盘，
   而且拒绝得越早越好——用户不用等任务跑完才发现白传了一份。
2. **半截文件比没有文件更糟。** 它看起来像一份完整的原文档。
   所以写盘失败（超限、流中断）时 `finally` 里立刻删掉它。
3. **清理责任只留一处。** 暂存件的删除只由 `TaskRunner` 负责
   （任务表满时 `discard`、`finally` 兜底）；`ApiHandlers` 里原先那块 finally 清理
   与它重复，**删掉后自测仍全绿 → 说明它不承重**，于是删掉。

#### 5.9.3 上限变成实例参数

`Workspace.open(root, maxUploadBytes)`：生产默认 256MB，测试可以调到 1KB。

**为什么必须能调**：上限判定如果只能靠「真的传 256MB」触发，
这条判定就没法在测试里被直接验——要么测试慢到不可接受，
要么为了迁就测试把上限改小，而改小的上限就不是生产用的那个上限了，等于测了另一个东西。

调小之后，测的是**同一段代码、同一个判定**。

#### 5.9.4 顺带修掉的四个真缺陷

1. **同步 `/api/scan` 的超限从 500 改 400。**
   以前「你发错了」被说成「服务坏了」——用户看到 500 会以为程序崩了。
2. **「不支持的后缀」「上传超限」从「先收下、异步失败」改成提交时同步 400。**
   以前界面会先显示「已受理」，然后任务失败——用户等了一圈才知道白传了。
3. **`ApiHandlers.taskScan` 的 finally 清理块是冗余的**（见 5.9.2 第 3 点）。
4. **超限报错里的上限数字是错的。**
   上限改成实例参数之后，报错文案还在读静态常量 `MAX_UPLOAD_BYTES`——
   上限一旦不是 256MB，它就会告诉用户一个错的数（用户会以为自己还有 256MB 余量，
   于是反复重传同一个文件）。现在异常带着**实际上限**走，文案由 `humanSize` 念出来；
   小体积也不再被说成「本次 0MB」。

#### 5.9.5 上限做成了命令行选项：`serve --max-upload-bytes`

```
LightMeter serve --max-upload-bytes 52428800   # 单份上传上限 50MB（默认 256MB）
```

**为什么要有这个**：上限判定如果只能靠「真的传 256MB」触发，
那它在**真实服务**上就没法被验——端到端要么得造一个几百 MB 的文件，
要么就只能验别的分支。做成一个选项之后，磁盘小的用户能自己收紧，
端到端也能用小上限在真服务上把这条路径走一遍（见 §7 的 e2e 9h-2）。

#### 5.9.6 判据与对照实验

主判据是「**提交那一刻内容已经在磁盘上**」：
用一个**只收不跑**的执行器把「还没被工作线程捡起来」那个窗口撑开，
断言会话目录里恰有 1 个 `upload-*.tmp` 且长度与上传一致。
它对着旧实现（内容只在堆里）会红，所以它承重。

| 编号 | 变异 | 状态 |
|---|---|---|
| ⒍ | 暂存件路径直接用客户端文件名（路径穿越） | PASS（**重锚过**，见下） |
| ➊ | 暂存件落在会话目录之外 | PASS |
| ➋ | 任务表满时不清暂存件 | PASS |
| ➌ | 后缀白名单被放宽 | PASS |
| ➍ | 上传体积不拦 | PASS |
| ➎ | 超限报错说的是 256MB 那个常量 | PASS |

**⒍ 为什么重锚**：「上传先落盘」重构之后，原来那两行
（`String diskName = randomId() + ext;`）搬进了 `store(StagedFile)`，
而那里**连 `clientFilename` 这个变量都不存在**——原来那条变异已经写不出去了。

但「外部字符串参与路径拼接」这个攻击面**没有消失，只是位移到了暂存阶段**：
`stage()` 里暂存件的路径要是改用 `clientFilename`，
一样能把原文档写到工作目录之外（`newOutputStream` 还会把同名文件截断），
后面的「认领」只是把它挪回来——中间那一瞬它已经在外面了。

配套补了一条单测（`WorkspaceTest.暂存件的落盘位置不受客户端文件名影响`）：
盯的是**暂存件**的落盘位置，不是最终位置——
最终位置那条（`路径穿越写不出去`）在这条路径上反而会被「认领」掩盖过去。

#### 5.9.7 这块没验什么

- **「64 份 256MB 同时排队」这个极限场景没有真造数据测**（那要十几 GB 磁盘和很久）。
  测的是**等价判据**：「提交那一刻内容已经在磁盘上」。
- ~~**进程被强杀（SIGKILL / 断电）时，会话目录会留在磁盘上。**~~
  正常退出有 shutdown hook 兜底（`ServeCommand`），SIGKILL 不走 hook。
  默认工作区在系统临时目录下，最终由系统清理，但**不是立刻**。
  → **2026-10-20 已做**（§5.10）：每个会话持一把文件锁，
  下一次启动时**能锁上的就是主人已死的**，把它的会话目录清掉。
  当初担心的「两个实例共用同一根目录会把正在跑的实例删掉」，
  由一把**启动互斥锁**解决（§5.10.4）。
  **仍然存在的**：**断电**（而不是 SIGKILL）这一形态没覆盖——
  掉电时锁文件可能没落盘，于是那个会话不会被认出来（§5.10.6）。
- **暂存件的删除是尽力而为**：文件被别人占着时删不掉（Windows 上常见）。
  这种情况暂存件会留在会话目录里，靠会话目录整棵删除兜底。

### 5.10 崩溃后的残留清理：被强杀的原文档，下一次启动时清掉（2026-10-20 补）

#### 5.10.1 这块在补什么缺口

§9 第 9 条记的那个缺口：进程被强杀（SIGKILL / 断电）时，
`<tmpdir>/litemask-workspace/sessions/<uuid>/` 连同里面的原文档与暂存件留在盘上。
正常退出有 shutdown hook 兜底（`ServeCommand` 会 `workspace.close()` 整棵删），
SIGKILL 不走 hook。

**为什么这个缺口值得单独做**：它的后果不是「文件被人偷看」
（服务只对**持有会话令牌的本机进程**开放，令牌在页面正文里、外部网页读不到），
而是「**用户的原始文件躺在盘上，而界面上早就看不见它了**」。
对一个专门处理敏感文档的工具，这两件事的严重性是一样的——
用户以为「已经处理完了、文件已经不在了」，实际上它就躺在那儿。

#### 5.10.2 怎么判断「上一次还在不在」：文件锁

三种判据，选了一种：

| 判据 | 为什么不用 |
|---|---|
| 看时间戳 | 进程刚崩、文件刚写完时，分不清是「刚崩」还是「还在用」 |
| 猜进程存活 | 跨平台没有可靠答案（Windows 上根本没有 `kill -0` 这种东西） |
| **文件锁** | **锁由内核持有，进程一死内核就放** → 「这把锁我能拿到」就等于「主人已经不在了」 |

于是每个会话持有一把锁 `<root>/locks/<sid>.lock`，`Workspace.close()` 放掉它并删掉锁文件。
下一次启动时扫一遍 `locks/`，**能锁上的那些就是主人已死的**，把它们清掉。

#### 5.10.3 清扫只认「锁文件指向的会话」

用户可能把 `--workspace` 指到一个装着自己资料的目录。
如果去扫 `sessions/` 下的**每一个**目录，就会把用户自己的东西删掉——
**那比留残留严重得多**。所以只认两条同时成立的：

1. 有对应的锁文件；
2. 会话名匹配 `^[0-9a-f]{32}$`（本工具的会话 id 格式）。

**扫不动就当没扫**：宁可留残留，也不要误删。

锁文件放在**会话目录之外**（`<root>/locks/` 而不是 `<root>/sessions/<sid>/`），
有两个好处：会话目录里只剩用户的文档（语义干净），
以及所有「数会话目录文件数」的判据（单测与端到端里有一批）**不受影响**。

#### 5.10.4 启动临界区：清扫和启动之间要有一把互斥锁

这一节记的是**实现过程中发现的一个真竞态**——不是事后补的保险。

清扫的判据是「锁我能拿到 = 主人已死」。而主人自己也是
「**先建锁文件、再锁上**」——在这两步之间，
另一个实例的清扫会看到一把**还没人锁**的锁文件，
于是把「刚启动起来的实例」当成「崩溃留下的」，
把它的会话目录连同里面的用户文档一起删掉。

窗口很窄（微秒级），但后果是**删掉正在被使用的用户文档**，
所以不能靠「窗口窄」来接受它。

修法：把「清扫」和「建自己的锁与目录」放进一个**启动临界区**，
临界区由两把锁保护：

| 层 | 手段 | 为什么 |
|---|---|---|
| 进程内 | `synchronized`（按工作目录根分桶） | 文件锁在**同一 JVM** 里是**抛 `OverlappingFileLockException`** 而不是阻塞，`synchronized` 那层必须兜住它 |
| 跨进程 | 文件锁 `<root>/locks/.root.lock` | 锁由内核持有，主人一死内核就放（同一套判据） |

拿不到启动锁时**等 5 秒**再报错退出（临界区只有毫秒级，5 秒是防挂死的上限，
不是设计出来的等待时间）。

> 另一个实例的会话**不会被**这把锁挡住：它只在**启动那一下**持有，
> 跑起来之后各会话各持各的锁，互不影响。两个实例共用同一个工作目录是允许的。

#### 5.10.5 判据：单测 5 条 + 对照实验 2 项 + 端到端 1 章

单测（`WorkspaceCrashCleanupTest`，新文件，5 条）——判据一律是**盘上少了什么**：

| 用例 | 判什么 |
|---|---|
| `死会话被清掉` | 锁没人持 = 主人已死 → 会话目录、原文档、锁文件**全被清掉** |
| `活会话不被删` | 另一个实例启动时，**不能**删掉在位实例的目录和文档 |
| `非本工具目录不碰` | 用户自己命名的目录、**没有锁文件**的会话目录，都不碰 |
| `正常退出会删锁文件` | 否则下次启动会把它误判成崩溃残留 |
| `根目录其它东西不动` | 工作目录根下的用户文件不被删 |

**「崩溃残留」怎么造**：在盘上摆出「锁文件在、但没人持锁」的样子——
这正是 SIGKILL 之后内核留下的状态（锁由内核持有，进程一死内核就放）。
摆出来的**形状**和真崩溃一致，所以测的是同一段判定。

**「活会话」怎么造**：同一 JVM 里 `tryLock()` 对同一个文件抛
`OverlappingFileLockException`——这与「锁被别的进程占着」等价，
正好代表「另一个还活着的实例」。

对照实验新增 2 项：

| 编号 | 变异 | 状态 |
|---|---|---|
| ➏ | 清扫时不管锁直接删（活着的实例被当成崩溃残留） | PASS |
| ➐ | 清扫什么都不删（崩溃残留原样留在盘上） | PASS |

端到端新增 **9i**（走打包后的 jar，**真起服务、真 `kill -9`**）——
单测摆的是「同一种形状」，端到端这一条才补上「真的被杀过」这一半：

1. 起服务 → 上传一个文件 → 等它落进会话目录（**判据成立的前提**）；
2. `kill -9` → 断言会话目录**还在**、原文档**还在**
   （这一步是**前提**不是结论：没有它，第 3 步可能是空转）；
3. **再起一个实例，用同一个工作目录** → 断言旧会话目录被清掉、
   新会话目录建好、且与旧的不是同一个、旧锁文件也没留下。

#### 5.10.6 这块没验什么

- **Windows 上的文件锁语义没验过**。代码里对「锁文件被别的进程占着、打不开」
  （Windows 上会抛 `IOException` 而不是返回 null）按「主人还活着」处理——
  这是保守的一侧，方向对，但**没在 Windows 上跑过**。
- **跨进程**的清扫没在单测里造出来：单测的「活会话」是同一 JVM 里的两个实例。
  跨进程那一半靠的是端到端 9i（那里是真进程）。
- **断电（不是 SIGKILL）没造**。断电是掉电，文件系统可能有延迟写，
  锁文件本身也可能没落盘——那种情况下**没有锁文件指向那个会话**，
  于是它**不会被清**。这是一个真实存在的残留形态，**本块没有覆盖**。
- **删不掉就留着**：Windows 上文件被别人占着时删不掉，下一轮启动再试。
- 启动互斥锁 5 秒上限：极端情况下第二个实例会**启动失败并明确报错**（不是静默卡住）。

## 6. 聚合键必须带分隔符，以及它怎么咬住的

`DocumentService.aggregate` 的聚合键是 `ruleKey + "\u0000" + original`。
不加分隔符时 `("phone","138")` 与 `("phone1","38")` 拼出来都是 `"phone138"`，
两类命中的计数、位置清单、令牌混成一坨。

> 顺带修了一个真实问题：原来源码里写的是**字面 NUL 字符 0x00**，
> 导致 `file` 把 Java 源码识别成 binary、grep 报 "Binary file matches"。
> 改成 `"\u0000"` 转义写法并加注释说明为什么需要分隔符。

### 6.1 ⒚ 第一次跑出来是 GREEN

18 条内置规则键两两之间**没有前缀包含关系**（`phone` 11 位、`telephone` 带连字符、
`bank_card` 16~19 位），**用内置规则库构造不出串键场景**。
这是探针空转，不是变异无效。

修法：`RuleLoader.load(Path)` 在测试里现造一组规则，
`("a","xy")` 与 `("ax","y")`——拼出来都是 `"axy"`。
规则刻意取得不自然，因为这里要验的是**键函数本身的单射性**，不是模拟一份看起来真实的文档。

### 6.2 然后发现新写的测试自己也空转了

变异跑出 `AggregateKeyTest 2 用例 失败1`。手动复现发现：
「排除只放开其中一条」那条测试**在变异体下依然全绿**。

原因：**被排除的命中根本不进 `changes`**，
于是聚合时只剩另一条，而它的键恰好就是「正确实现下另一条自己的键」——
断言 3、4 照样通过。

修法是加一条**前置断言**：不排除时清单里本来就该有两行。
这条断言看起来像废话，删掉它整条测试就会变回空转——已在代码注释里写明为什么不能删。

> 这是本轮第三次遇到「测试不敏感」，但形态是新的：
> **前一次是断言写得不对，这一次是断言写对了、却被前置状态悄悄架空。**
> 判据是变异后失败数有没有如预期变化，不要只看「有没有红」。

### 8.1 破坏⑩ 的第二次漂移，以及一次事故

⒚ 修好之后，全量跑出的**不是 64/64，而是 63 PASS + 1 INVALID**——失效的还是破坏⑩。
根因与 M2-b 那次同类：M2-c1 给 `RedactionEngine.redact` 加了五参重载
（带 `OccurrenceNumbering`），`RedactionSession.redactInternal` 于是变成
「编号分支 / 隐形分支」两条调用，而脚本里那条变异仍写着 M2-b 时期的单行调用，
`sed`/python 替换零命中 → `MUTATION_TARGET_MISSING` → 判 INVALID。

修的时候踩了一个更贵的坑，值得单独立一条纪律：

1. `_run_case_multi` 的参数是**「文件 原文 替换」三个一组**。
   我给第二个调用点补参数时**漏了文件路径**，于是第二个循环拿「原文」当文件名去 `cp`，
   在 `set -u` 下撞 `unbound variable` 让脚本**直接退出**——
   而第一组**已经变异落盘**，还原代码根本没机会执行。
2. 下一次运行时，备份 `cp` 拿到的**就是那份变异源码**，
   于是锚点「未命中」、基线复核报红，看起来像新代码坏了，实际是上一轮留下的污染。
3. 表现极具欺骗性：所有失败信息都指向「代码有问题」，**没有任何一条指向「工具参数写错了」**。

修完后的三条加固（都已进脚本）：

| 加固 | 挡的是什么 |
|---|---|
| `run_case_multi` 参数格式守卫（总数必须是 3 的倍数，否则**在动文件之前**就退出） | 参数写漏 → 变异落盘无还原 |
| **起飞前基线检查**（每次调用先跑一遍全量测试，不绿就拒绝起飞） | 区分「这轮弄坏的」与「进来时就脏的」 |
| 把 `ONLY` 从跳过条件里去掉 | 子集迭代最容易被打断，恰恰最需要起飞检查 |

其中第二条的代价是每次调用多跑一遍全量测试（约 1 分钟）。
**换来的是「红灯一定是我这一轮造成的」**——这次事故里，正是因为没有它，
我花了好几轮才确认污染不是来自刚写的代码。

> 这条与已有的「对照实验拆到下一轮容易留下脏产物」是同一个教训的两种形态：
> **中断本身就会留下变异源码，而下一次运行不会告诉你这件事。**
> 靠人记得「上次是不是跑完了」是不行的，得让工具自己说出来。

## 9. 已知限制与缺口

1. **浏览器端「行为」部分已于 2026-10-19 用真 Chrome 自动化覆盖；「观感」部分仍未验。**
   上一版这里记的是「本轮所有界面结论都来自静态接线对账 + HTTP 端到端，没有真人打开浏览器点过一遍」。
   2026-10-19 补了 `tools/e2e-browser.sh`（自建 CDP 驱动，零第三方依赖，见 §5.8），
   下面这几项**现在有自动断言撑着**（不是推断，是 Chrome 真跑出来的）：
   - 步骤条在窄屏下**不横向溢出**（视口压到 420 像素，`scrollWidth - clientWidth ≤ 1`，实测溢出 0）；
   - 步骤条**没跑出屏幕**（`stepPick` 右边界 ≤ 421）；
   - 长文件名（60 个汉字）在摘要里**没被吞掉**；
   - 下载后浏览器的文件名与**页面显示一致**，落盘文件非空；
   - 扫完之后「生成脱敏文件」按钮**确实可用**（这一条当场抓到过一个真缺陷，§5.8.4）；
   - **不支持的后缀在提交时就被拒**：界面上明确说了「不支持」，
     任务卡收起来、文件框重新可点、**没有出命中清单**（2026-10-20 补）；
   - 页面**没有未捕获的 JS 异常**、控制台**无 error**（`/favicon.ico` 的 404 按 URL 精确排除）。

   **仍然只能靠人眼**（自动化验的是「对不对」，验不了「好不好看」）：
   - 步骤条折行之后断在哪里、挤不挤；
   - 长文件名在表格单元格里换行的视觉效果；
   - `notes` 在窄屏下左侧警示条是否挤占表格；
   - 配色与对比度。
2. ~~**`/api/restore` 仍是 501。**~~ **本条已于 2026-10-19 做掉**（§5.5）：
   映射件落盘 + `GET /api/mapping` + `POST /api/restore` + 界面上两个按钮。
   但注意 §5.5.4 的边界：**还原的是文本内容，不是文件字节**；
   且**界面那半边的行为已有自动化覆盖**（真 Chrome 端到端），
   **观感仍未验**（同本节第 1 条）。
3. **单任务不可重入。** 同一个 `jobId` 重复 `apply` 直接 400，改排除项要重新上传。

4. **PDF 的命中没有位置信息**，界面无法高亮到具体位置，只能列出值。

5. **位置说明超过 20 条时截断**，界面只展开前 20 次，剩余部分只报计数。

6. **`aggregate` 的位置说明条序 ≠ 文件里的物理位置顺序。**
   docx 按 zip 条目顺序走，与 Word 翻页顺序不一定一致。序号与清单对齐是保证了的，
   但「第 N 处 = 翻到第 N 页」这种直觉对应关系不成立。
7. ~~**长任务没有进度反馈。** `scan` 是同步的，200 页 PDF 会让界面停在「上传中」，
   只能等。没有超时、没有取消。~~
   → **2026-10-19 已做**（§5.7）：脱敏挪到后台任务池，界面轮询 `GET /api/task`

   理论上「连着提交 64 份大文件」能把内存撑爆。~~
   → **2026-10-20 已做**（§5.9）：上传一律**先流式落盘**再交任务，
   任务不再持有上传字节；「不支持的后缀」「上传超限」也从异步失败
   改成了**提交时同步 400**（顺带把同步 `/api/scan` 的超限从 500 改成 400）。
   **新留下的缺口**：进程被强杀时暂存件/原文档会留在磁盘上
   → **2026-10-20 已做**（见本节第 9 条 / §5.10：会话持文件锁，下一次启动时清扫）。
9. ~~**进程被强杀（SIGKILL / 断电）时，会话目录留在磁盘上。**
   正常退出有 shutdown hook 兜底（`ServeCommand` 会 `workspace.close()` 整棵删），
   SIGKILL 不走 hook，于是 `<tmpdir>/litemask-workspace/sessions/<uuid>/`
   连同里面的原文档与暂存件留在盘上。~~
   → **2026-10-20 已做**（§5.10）：每个会话持一把**文件锁**
   （`<root>/locks/<sid>.lock`），锁由内核持有、主人一死内核就放；
   下一次启动时**能锁上的就是主人已死的**，把它的会话目录和锁文件一起清掉。
   清扫只认「**有锁文件、且会话名是本工具 id 格式**」的会话——
   用户可能把 `--workspace` 指到装着自己资料的目录，误删用户数据比留残留严重得多。
   当初担心的「两个实例共用同一根目录会把正在跑的实例删掉」，
   由一把**启动互斥锁**解决（§5.10.4）。
   **仍然存在的**：**断电**（而不是 SIGKILL）没覆盖——掉电时锁文件可能没落盘，
   那个会话就认不出来（§5.10.6）；Windows 上的文件锁语义也没在 Windows 上验过。
