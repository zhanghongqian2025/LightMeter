# 轻量单机脱敏工具 · 开发目标与路线图

> 代号 `desens-desktop`　目标平台：macOS（arm64/x64）+ Windows（x64）
> 技术路线：**方案 B（核心包 + AI 模型包分离）**
> 立项日期：2026-10-14

---

## 一、产品目标

做一个**单机版文档脱敏工具**：把 Word/Excel/PPT/PDF/OFD/纯文本里的敏感信息找出来，替换成占位符，并支持**可逆还原**。全部计算在本机完成，文档内容不出网。

### 必须做到（Non-negotiable）

| # | 目标 | 验收标准 |
|---|---|---|
| G1 | **可逆**：脱敏后能用映射完整还原原文 | `restore(redact(t)) == t`，字节级相等，含换行与空白 |
| G2 | **不漏**：格式类强校验信息必须命中 | 每条规则 ≥10 条正向样本、≥10 条负向样本，测试全绿 |
| G3 | **不误伤**：不该脱的不能脱 | 负向样本零误报；测试须用对照实验证明「撤掉实现就红」 |
| G4 | **不出网**：文档内容零外发 | 封网沙箱下六种格式脱敏 + 还原往返全绿（系统调用层封网），静态标尺扫常量池得出出网白名单，两组负控制证明这条检查会咬（M4 §三十） |
| G5 | **可交付**：双平台安装包 | macOS `.dmg` + Windows 安装包，CI 可复现产出 |
| G6 | **体积硬指标**：核心包 ≤ 90MB | 构建脚本自动校验，超标即失败 |

### 明确不做（Non-goals）

- **不做 SaaS**：不建账号中心、不做多租户、不做云端模型
- **不做老格式**：`.doc` / `.wps` / `.rar` / `.pst` 一律不支持，提示另存为（老格式唯一解是 LibreOffice，300MB+，性价比为负）
- **不做 OCR**：识别扫描件交给外部服务，不进核心包
- **不做云端强制作业升级**：不实现 `forceUpdate` 这种服务端强制能力

## 二、架构决策（先定死，避免返工）

| 决策 | 选择 | 理由 |
|---|---|---|
| 运行时 | **Java 21 + jlink 定制运行时** | 需要本地 HTTP 服务（Word/WPS 加载项只能调 http(s)），JVM 常驻最省事；jlink 把 151MB 压到 ~45MB |
| Web 框架 | **不用 Spring Boot**，用 `com.sun.net.httpserver` | 单机几十个接口，Spring 全家桶 355MB 依赖没有必要；省下的体积比省下的开发时间值钱 |
| 数据库 | **不用数据库**（`JobStore` 内存 + 会话目录文件） | 原定 SQLite（`sqlite-jdbc`，单平台 native ~3MB），**最终没上**：任务本来就是会话态的（进程退出整棵删、满 64 按 LRU 淘汰并清盘），落盘只为了省 3MB 与一份 native 依赖，而持久化反而要求处理「残留的会话目录里留着原值」这个**更敏感**的问题 |
| 文档解析 | **四种 zip 文档（docx/xlsx/pptx/ofd）全部用 JDK 自带的 zip + DOM，零文档库；只有 PDF 引 PDFBox** | 放弃 Aspose（78MB + 商业授权风险）。**放弃 POI**：实测 `poi-ooxml` 整栈 18.4MB，且它把文本框里的段落建模成另一种类型，得同时维护两套遍历；漏一层的后果是「文件正常、报告成功、原文还在」。**放弃 ofdrw 做生产依赖**：OFD 的文本位置是可穷举的（TextCode 元素内容 + @Text + DocInfo + 附件名），把清单列出来本身就是覆盖率证明；而 PDF 不同，字符编码在内容流算子里、字体子集内嵌，没有零依赖解法。⚠️ 但 **ofdrw 仍作为「独立裁判」留在 test scope**：它负责回答「我们改完的文件别人还读不读得动」——测试标尺不能是被测实现自己写的 |
| AI 推理 | ONNX Runtime（**只保留单平台 native**）+ DJL tokenizers | 88.7MB 的 jar 里塞了全平台 native，拆出来单平台 ~12-18MB |
| 模型交付 | **独立 AI 包，首次启用时下载或离线导入** | 模型是平台无关的，没必要两个平台各塞一份；升级模型不用重发整包 |
| 模型精度 | **INT8 动态量化 + 层数蒸馏（12→4~6）** | 只要 7 个标签 3 类实体，12 层严重过配；INT8 除以 4，NER 精度损失可忽略 |
| 加密 | 元数据/模型可加密，但**密钥必须走系统钥匙串**，不硬编码 | 参考品把密钥 XOR 后硬编码在常量池，等于没加密 |
| 分层 | **L0 引擎 / L1 文档栈 / L2 AI 包** 三层，各自可选 | 首版可只发 L0；离线客户单独导入 L1/L2 |

### 分层与体积预算

| 层 | 内容 | 预算 |
|---|---|---|
| **L0 引擎** | jlink 运行时 45MB + 应用与核心依赖 6MB + 前端 4MB | **≤ 55MB** |
| **L1 文档栈** | PDFBox 3.5MB + SQLite + Jackson（OOXML 三件套与 OFD 实测各仅 +20~30KB） | **+15MB** |
| **L2 AI 包** | int8 模型 + ORT native + tokenizers（**跨平台共用一份**） | **+30~35MB** |
| 全量安装 | L0+L1+L2 | **≤ 100MB**（对照原版 820MB / 959MB） |

> L1 原预算 +22MB 是按 POI-lite 估的；实测**没有 POI**，OOXML 三件套合计只增加约 20KB，
> 因此整层下调到 +15MB。**不要把省下来的额度挪去塞别的东西**——
> 这条预算的意义就是逼着每一层都做减法。

> 构建脚本内置体积闸门：任一层超标直接构建失败，不靠人自觉。

- [x] **上传先落盘**（2026-10-20 补，见 `docs/M2-c-阶段状态.md` §5.9）：
      上传内容一律**先流式落盘**再交任务，排队中的任务不再抱着 256MB 的字节
      （任务表 64、单份上限 256MB 的组合原来理论上能把内存撑爆）；
      暂存件只有「被认领」与「被丢弃」两个去处，没有第三条路；
      「不支持的后缀」「上传超限」从异步失败改成**提交时同步 400**，
      顺带修掉两个真缺陷——同步 `/api/scan` 的超限以前返 **500**
      （把「你发错了」说成「服务坏了」）；超限报错里的上限数字读的是
      256MB 那个静态常量，上限一改它就在骗用户。
      上限做成了命令行选项 `serve --max-upload-bytes`（默认 256MB），
      磁盘小的用户能自己收紧
- [x] **崩溃后的残留清理**（2026-10-20 补，见 `docs/M2-c-阶段状态.md` §5.10）：
      进程被强杀（SIGKILL）时 `close()` 不执行，原文档会留在盘上；
      现在**每个会话持一把文件锁**（`<root>/locks/<sid>.lock`），
      锁由内核持有、主人一死内核就放，于是**下一次启动时「能锁上的就是主人已死的」**，
      把它的会话目录和锁文件一起清掉。
      清扫只认「**有锁文件、且会话名是本工具 id 格式**」的会话——
      用户可能把 `--workspace` 指到装着自己资料的目录，**误删用户数据比留残留严重得多**；
      清扫与启动之间另有一把**启动互斥锁**，
      否则「刚启动起来的实例」会被另一个实例误判成崩溃残留、连用户文档一起删掉

      **没有任何一条检查会因为「有人往脱敏路径里加了一次 HTTP 请求」而变红**。
      → 交付**两层**证明（互补，缺一不可）：
        ① 动态：封网沙箱（macOS `sandbox-exec`，**系统调用层**封网，
           Java 与 ONNX Runtime 都绕不过）里跑完整脱敏 + 还原往返
           （docx / xlsx / pptx / pdf / ofd / txt 六种格式）；
        ② 静态：扫 jar 内全部 class 的常量池，看**谁会真的发起出站网络 I/O**
           （判据是「**调了哪个方法**」，不是「引用了哪个类型」——
             按类型判会误报一大片，白名单会退化成「现状清单」，
             新增联网的类只要也引用了 `URL` 就照样混在里面）。
      两组负控制证明这条检查**确实会咬**：A（差分式 wrapper 注入，
      两次跑**只差「封网」这一个变量**）与 B（往**产品自己的代码**里
      真的注入一次出站连接 → 封网后必须红且理由是 `Operation not permitted`，
      还原后必须绿）。
      沙箱本身也先自证三条（外连通 / 内 **EPERM** / 内文件可读写）——
      「连不上」**不等于**「被封」（`ECONNREFUSED` 与 `ETIMEDOUT` 都不是证据）。
      本轮修掉**三个真缺陷**：① 端到端校验器要求映射里有**完整原值**，
      与 §1.19.8「重叠时维持拆分」的定论矛盾（失败理由「还原会失败」
      又与拆分后逐字成功相矛盾）→ 改成「能不能被映射里记着的东西**拼回来**」；
      ② **形态的前提**被当成了通则（无模型形态下人名本来就不脱敏，
      断言却要求它消失 → 恒红）；③ 负控制的**对照组**自己不合格
      （监听口 accept 完就 close → 客户端读到 EOF → 红的是对照组，不是被测对象）。
      本块**没有改动 `src/**`** → 单测数不变。
      **仍然缺的**：**`sandbox-exec` 是 macOS 专有**（别的平台上这条证明**未执行**，
      链里以退出码 77 记「跳过」，不是通过）；`serve` 模式不在封网范围内；
      静态标尺只认**直接调用** JDK 网络 API（反射 / 动态代理 / 第三方库内部不覆盖）；
      **入站**（本地监听）不在标尺范围；夹具与校验器不在沙箱内；
      `model download` 按设计要联网（那一段的边界是验签 + 信任锚，不是零外发）。
- [ ] 真机验收（另一台没装过 JDK 的 Mac 的首次打开 + Gatekeeper）—— **未做**，本机不是干净机器

## 四、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 文档解析库解析不可信输入的 CVE | 高 | 只用新版本；引入 fuzz 测试；解析失败必须 fail-closed 而不是静默跳过 |
| 蒸馏后 NER 精度下降 | 中 | 保留「纯正则模式」作为降级路径；F1 不达标就不切蒸馏版 |
| docx 回写破坏格式 | 中 | 用 XWPF 逐 run 替换，不整段重写；保留原始样式与批注 |
| 体积反弹 | 中 | CI 体积闸门，超标即失败 |
| Word/WPS 加载项需求变更 | 低 | 加载项协议层独立，核心引擎不感知 |
