## 三、架构：为什么是这个形状

### 3.1 `EntitySource` 放在 core，而不是让 core 依赖 ner

依赖方向必须从外向内。`core` 是脱敏引擎，不该知道「onnxruntime」「字符表」这些推理侧的东西。
一旦 core 引用了 ner，就再也做不了不加载模型的纯正则脱敏。

`EntitySource` 的返回值就是 `Match`——**NER 命中与正则命中在这里汇合成同一种东西**，
于是「算序号 → 按排除过滤 → 解析重叠 → 替换」这四步只有一份实现。

> **不给 AI 命中开第二条替换路径。** 两条路径各自算偏移，
> 现场是正文里少字或多字，而报告一切正常。

### 3.2 优先级：NER = 900（常量，不可配）

现有正则规则实测范围 **76..120**。让 NER 压过它们的理由：

- 典型重叠是「北京某某科技有限公司」——若某条正则只命中里面的「北京」，
  按正则优先就会把机构名切成两截，正文变成 `<机构名1>某某科技有限<地名1>公司`。
- 反过来，NER 误报吞掉一个身份证号的概率极低（身份证几乎全是数字），
  而这个工具的既定取舍是**宁可多脱**。

**做成常量而不是配置项**：一旦能配，某个部署就会配出一份「正则压过 NER」的规则集，
而那种配置下的错误现场是机构名被切碎、报告正常。

同时**不是特权**：`sortOrder` 高于 900 的正则仍然胜出，有测试守着（`更高优先级的正则仍然胜出`）。

### 3.3 三种失败的处理方式不一样

| 情况 | 处理 | 理由 |
|---|---|---|
| 识别器**抛异常** | 向上传播，整篇失败 | 模型没加载 / native 缺了，界面一片正常而文档少脱了人名 |
| 识别器**返回 null** | 当作没有命中 | 接口文档要求返回空列表；一个坏来源不该毁掉整篇 |
| 区间**越界** | 拒绝整条 | 越界说明坐标换算坏了；截断等于少脱，丢弃也等于少脱 |

这三档各有一条对照实验（⒱ / ⒲ / ⒰）。它们看起来像同一件事的三个分支，
但判据不同、后果不同，所以分开测。

## 四、这一轮挖出来的真实缺陷

### 4.1 CRF 广播方向写反（最严重，训练彻底跑不出结果）

**现场**：loss 从 1073 掉到 −691660，再变成 NaN，训练照跑完 12 轮，
末尾还打印「最终 F1 0.0000」。一次发散被包装成了一次正常实验。

**根因**：

```python
alpha.unsqueeze(1) + trans        # 错：alpha 被按 to 索引
alpha.unsqueeze(2) + trans        # 对：alpha 落在 [B, C_from, 1]
```

两者生成的张量**形状完全一样**（都是 `[B,C,C]`），任何形状断言都拦不住。
后果不是形状不对，而是**算出来的 logZ 根本不是配分函数**——
alpha 的贡献在同一列里对所有 from 取同一个值。

**判据**：`logZ ≥ 金标路径分` 是数学不变量，NLL 必须 ≥ 0。
第一版没有这道断言，直到把屏蔽值从 `-1e4` 改成 `-inf` 之后才暴露出来
（`-1e4` 会让非法路径在 logZ 里被系统性低估，`logZ` 掉到金标之下）。

**标尺**：`tools/verify_crf.py` 用**暴力枚举全部合法标签路径**做独立对账。
「再写一遍 DP」不成立——同样的错误会写两遍。

**标尺的盲区（实测出来的，不是猜的）**：注入这个错误后，
T=1,3,5,7,9 五组里抓到 4 组，**T=1 漏过**——
单点序列没有转移，广播方向错了也看不出来。真正把关的只有 T≥3 的几组。

### 4.2 屏蔽值用有限数会让 NLL 变负

CRF 的 logZ 是「所有路径」的 log-sum-exp，非法路径也参与求和。
用 `-1e4` 时，屏蔽量与 emission 的实际量级可比，非法路径被**系统性低估**，
一旦模型把 emission 压到同一量级，`logZ < 金标`，NLL 出现负数，再往后双双溢出成 inf。

**必须用 `-inf`**，让非法路径的概率恰好为 0。导出到 ONNX 时再换回有限的 `-1e4`：
Java 的 `SequenceDecoder` 本来就用 `TagScheme` 把非法转移整个跳过，根本读不到那些位置，
有限值只是为了不让 ONNX 文件里出现非有限字面量。

### 4.3 ONNX 导出多出一个输出

第一版 `forward` 返回 `(emission, transitions + em.sum() * 0.0)`，
结果导出后图里出现**三个**输出：`emission`、一个被自动命名成 `"26"` 的中间结果、
以及后来手工追加的 `transition`。前两个是同一个张量。

`sess.run(None, ...)` 收到三个返回值——按名取还能凑合，按位置解包的调用方直接炸。
顺带一提，`* 0.0` 那个挂法在 logit 出现 inf 时会产出 nan。

**改成**：`forward` 只返回 `emission`，转移矩阵用「追加 `Identity(constant)`」挂到图上。

### 4.4 `padding_idx=0` 让 UNK 永远学不到

id 0 是 UNK，不是 padding。设了 `padding_idx=0` 之后 UNK 那一行永远拿不到梯度，
于是「表外字符」在模型眼里始终是随机初始化的向量——而 UNK 恰恰是所有表外字符的入口。
补齐位本来就不进损失（`crf_log_partition` 与 `gold_path_score` 都按 mask 累加），
不需要靠 `padding_idx` 屏蔽梯度。

### 4.5 导出时模型还在 MPS 上

`torch.onnx.export` 的 dummy 输入是 CPU 张量，模型留在 MPS 上就会报
`Passed CPU tensor to MPS op`。现场是**训练全部跑完、指标都打出来了，最后一步炸掉**。

### 4.6 引擎早退时忽略了非正则来源（引擎侧）

`if (text == null || text.isEmpty() || rules.isEmpty()) return 原样;`

这条早退在加 `EntitySource` 之前是对的。加了之后，「只启用 NER、不启用任何正则」
这条配置会直接返回原文——**一个字都不脱**，界面上还显示「0 处命中」，没有任何报错指向它。

改成 `(noRules && srcs.isEmpty())`。对照实验 ⒬ / ⒭ 守住。

## 五、测试设计的几条取舍

### 5.1 翻译逻辑不加载 ONNX

`NerEntitySource` 依赖的是函数式接口 `TextRecognizer` 而不是具体的 `NerRecognizer`。
理由：本类干的活只是「翻译」，为测它去加载 ONNX 不但慢，
还让「翻译写错了」和「模型跑不动了」两类故障在测试里混成一个红——而两者的修法完全不同。

端到端另用真实夹具跑一次（`端到端` / `端到端无实体`），证明链路真的通。

### 5.2 引擎侧用手写假来源

`EngineEntitySourceTest` 全部用假来源，区间是手写的，期望结果可以逐字写出来。
理由同上：这里要验的是引擎的行为，「模型认不认得出人名」不在射程内。

### 5.3 一条测试因为前提不成立而「因为错误的原因通过」

`排除挡跨度` 第一版写的是人名 `[2,5)` + 手机号 `[5,16)`——那是**不相交的相邻两段**，
挡不住是当然的。测试照样绿，但它其实什么都没验。
已改成「人名一路吞到句末」的重叠场景，并在测试里显式断言两个起点，
让前提不成立时立刻红。

**教训**：写完一条「挡跨度」类的测试，要先问「被挡的那条真的落在被排除的区间里吗」。

### 5.4 一条测试的期望值本身是错的

`套娃防护` 第一版断言新令牌是 `<机构名1>`。而输出里已经有一个 `<机构名1>` 了——
那会造出**两个一模一样的令牌**，还原时都指向同一个值。
引擎的行为（发 `<机构名2>`）才是对的。测试写错了，实现没错。

## 六、模型精度（这一块的诚实数字）

### 6.1 数据集实测

| 数据集 | 句子 | 字符 | 实体 |
|---|---|---|---|
| MSRA train | 45,000 | 2,171,573 | PER 17,615 / ORG 20,584 |
| MSRA test（留出） | 3,442 | 172,601 | PER 1,973 / ORG 1,331 |
| cluener2020 | 10,748 | 401,764 | PER 3,755 / ORG 8,025 |

标签映射：`PER ← name`；`ORG ← company + organization + government`。
MSRA 的 `LOC` 与 cluener 的 `address/scene/…` 一律映射成 `O`——**地名走正则规则，不进模型标签集**。

### 6.2 训练结果

| 轮次 | 参数量 | MSRA test 实体级 F1 |
|---|---|---|
| v1（无 dropout，192 维，20 轮） | 1,203,294 / 4.59 MiB | 0.8039（ep10 见顶 0.8079 后回落） |
| v2（dropout 0.3，256 维，30 轮） | 1,751,838 / 6.68 MiB | 见下 |

v1 的曲线是典型过拟合：训练 loss 一路降到 0.023，留出集 F1 却在 ep10 见顶后回落。
加上 dropout 与加宽之后仍在爬升。

**验收线是 F1 ≥ 0.9。** 达不到就加宽加深，不放宽验收线——见 §七。

## 七、未达标的项（不藏）

- **MSRA 留出集实体级 F1 尚未达到 0.9 的验收线。** 训练与导出链路已经打通、
  指标真实可复现，但精度还差。已在文档、TodoWrite 与汇报里如实标注为未达标。
- **`maxEntityChars = 35`**（训练语料里的最长实体）。这条数字直接决定
  Java 侧滑动窗口必须 `overlap ≥ 35` 且窗口宽度 > 35——
  也就是说**每个窗口至少 36 个字，75% 的内容是重叠的**，推理成本是「朴素单窗」的好几倍。
  这个契约在 M3-1c 推导过，但 35 这个实际值比当初假设的大一个量级，需要专门评估。
- **Windows 侧全空白**：win-x64 native 进了 jar，但能不能加载、jlink 多大、
  安装包多大，都没测。现有全部数字是 macOS arm64。
- **五条格式管线还没接 NER**：本轮证明了适配层能进引擎，但
  docx/xlsx/pptx/pdf/ofd 的 redactor 还没有把 `NerEntitySource` 传下去。
- **200 条自标样本的验收还没做**：现有 F1 是在 MSRA / cluener 上测的，
  不是法律文书域。
