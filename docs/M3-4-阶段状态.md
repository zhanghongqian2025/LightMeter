# M3-4 阶段状态：体积收口

## 〇、开头结论（含一条被推翻的旧结论）

- 最终模块集：`java.base, java.xml, jdk.httpserver, java.logging, java.desktop`
  （`--list-modules` 实测还会带上传递依赖 `java.datatransfer`、`java.prefs`）。
- 三层合计 **75.60 MiB ≈ 79.28 MB**，预算 90 MB，余量 **14.40 MiB**（2026-10-22 实测；
  M3-4 当轮量到的是 75.41 MiB / 余量 14.59 MiB，之后 M2-c 补块加了服务端代码与前端资源，
  复测 +17,226 B，**零新增第三方依赖**）。
- **M3-1d「`java.desktop` 可以砍」是错的，本轮推翻。** 当初的实测只跑了四条路径
  （模型包加载 / 脱敏 / 映射序列化 / `rules`），**没有一条走 PDF**。
  PDF 管线一跑就炸：`NoClassDefFoundError: javax/imageio/IIOException`。
- 顺带补上了一个当初连想都没想到的必需模块：`java.logging`
  （ONNX Runtime 的 `OrtEnvironment` 静态初始化要 `java.util.logging.Logger`）。

这两条是本阶段真正的产出。体积数字只是副产品。

## 一、这一块要回答的问题

用户定的硬指标是「核心包 ≤90MB」。这是个**没法靠推理得到答案**的数字——
每加一个依赖、每换一个序列化库、每改一次 jlink 的模块集，它都会变。
所以本阶段的交付物不是一份「当前 61MB」的报告，而是**两个每次都能重跑的闸门**：

- `tools/measure-size.sh`：三层实测 + 90MB 判定；
- 五套端到端在**精简运行时**上实跑（见 §三），这是模块集的真正闸门。

理由：体积是唯一一个「涨了不会有人发现」的东西。功能坏了会红、测试会挂、
用户会报错；体积涨了 3MB 时一切都正常，只是文档不再说得对。

> **2026-10-18：这个闸门被发现从未真正工作过。**
> `measure-size.sh` 的默认路径写的是 `target/runtime`，而 `package-macos.sh`
> 产出的是 `target/runtime-image`——它每次都 `MISSING`、`exit 1`，
> 失败得足够显眼，于是一直被当成「环境没准备好」而没人查。
> 也就是说，**为「唯一会悄悄涨的东西」建的闸门，从写下来那天起就没量到过东西**。
>
> 已修三处（详见 `M3-3-阶段状态.md` §1.15）：
> 1. L0 默认路径改为与 `package-macos.sh` 同名的 `target/runtime-image`；
> 2. L2 默认回退到「app 内 models/ner」与「用户实际投放的 `~/.litemask/models/ner`」——
>    原来指向的 `target/models/ner` 不是任何真实产物的位置；
> 3. 预算行把 `90 × 1048576` 的**字节数**打成了 MiB（`94371840.00 MiB`），
>    而这一行恰恰是唯一声明预算口径的地方。
>
> 修后做了三向验证：超预算 `rc=1` / 组件缺失 `rc=1` 且提示覆盖方式 / 正常 `rc=0`。
> **只看闸门正常时说什么不算验证过**——`rc=0` 也可能是因为压根没找到文件。

## 二、三层口径与实测值

对应 `docs/开发目标与路线图.md`。L0 用本轮 jlink 产物实测，不再引用 M3-1d 的旧数字。
**下表 L2 已更新到 v7 模型**（原表为 v4）：

| 层 | 内容 | 本次实测 |
|---|---|---|
| L0 | jlink 定制运行时（5 模块 + 2 传递） | 51,559,749 B = **49.17 MiB** |
| L1 | 应用 + 核心依赖（fat jar，**已剔除 win-x64 原生库**） | 13,555,997 B = **12.93 MiB**（M3-4 当轮 13,349,139 B = 12.73 MiB） |
| L2 | NER 模型包（**v9**，宽度 384） | 14,160,149 B = **13.50 MiB** |

合计 **79,275,895 B = 75.60 MiB ≈ 79.28 MB**，预算 90 MB，**余量 14.40 MiB**
（L1 为 2026-10-19 重测：映射出口 + 还原那一块加了代码，**零新增第三方依赖**）。

### L1 瘦身：剔掉另一个平台的 ONNX Runtime 原生库（省 4.26 MiB）

`com.microsoft.onnxruntime` 的 Maven 包**同时带 win-x64 与 osx-aarch64 两套**
（实测：win-x64 11.65 MB、osx-aarch64 25.56 MB 未压缩）。
发布到 macOS 就不该带 Windows 那套。实测两种剪法：

| 剪法 | jar 体积 | 收益 | 适用 |
|---|---|---|---|
| 排除 `win-x64` | 16.97 → **12.71 MiB** | **−4.26 MiB** | macOS 包（**已实测**；2026-10-19 重测后剪完是 **12.73 MiB**，剪除收益仍是 4.26 MiB） |
| 排除 `osx-aarch64` | 16.97 → 10.39 MiB | −6.57 MiB | Windows 包（**未实测**，见下） |

已验证：剔除 win-x64 后 ONNX 加载与推理结果**逐字不变**（主集 F1 0.8479），
且 7/8 步「装了模型」形态的实跑验证照常通过。
**余量因此从 10.36 MiB 涨到 14.62 MiB**（2026-10-19 重测后为 **14.59 MiB**）。

⚠️ `package-windows.ps1` 里的对称改动**从未被执行过**（本机无 Windows），
且它比 macOS 版多一处风险：Windows 上没有 `zip` 命令，
改用 `[System.IO.Compression.ZipFile]::Open($jar,'Update')`，
并显式 `Add-Type -AssemblyName System.IO.Compression.FileSystem`
（PowerShell 5.1 不自动加载，不加会在第 1 步就抛类型找不到）。

> **预算重估**：余量 14.59 MiB，按 §1.11 的算术，宽度 512 约需 +13.4 MiB——
> **技术上装得下，但只剩约 1.2 MiB 缓冲**。若要继续加容量，
> 建议先做一次取舍（砍 `java.desktop` 或量化）再动宽度。

复现：`./tools/measure-size.sh`（默认路径已与打包脚本对齐，无需手动传参；
需要量别的产物时用 `RUNTIME=<dir> MODEL=<dir>` 覆盖）。

> 「MB」在 Windows 资源管理器上是 1000²、在 macOS 的 `ls -lh` 与 jlink 里是 1024²。
> 闸门统一用 MiB 比较（数字更小、更保守），但两套都打印出来，
> 免得「文档写 75.60MiB、用户看到 79.28MB」被当成造假。

## 三、模块集怎么定：两次都定错了，第三次才靠实跑定下来

这一节是本阶段最值得留下来的部分。

### 3.1 第一次错：`jdeps` 报告被当成了结论

对 fat jar 按包逐个跑 `jdeps --print-module-deps`：

| 包 | 模块依赖 |
|---|---|
| `com/litemask`（本项目代码） | `java.base, java.xml, jdk.httpserver` |
| `com/fasterxml`（Jackson） | `java.base, java.desktop, java.sql` |

于是第一版模块集定为三个模块。**这是错的**：`jdeps` 只看**编译期可见的引用**，
而运行时真正决定成败的是**静态初始化块和注册表式调用**——
它们在字节码里就是一条 `invokestatic`，`jdeps` 认不出它会摸到哪个类。

### 3.2 第二次错：验证路径选得不够，于是「实测通过」等于没测

用 `java.base, java.xml, jdk.httpserver` 三个模块构建运行时，实跑四条路径：

| 路径 | 结果 |
|---|---|
| `rules` 子命令（Jackson 反序列化 `core-rules.json`） | 通过 |
| 脱敏（不挂 NER） | 通过 |
| 写出映射文件（Jackson **序列化** + pretty print） | 通过 |
| `--ner-model` 加载模型包 | **失败**：`NoClassDefFoundError: java/util/logging/Logger` |

栈是决定性的：

```
java.lang.NoClassDefFoundError: java/util/logging/Logger
  at ai.onnxruntime.OrtEnvironment.<clinit>(OrtEnvironment.java:27)
  at com.litemask.ner.OnnxRunner.open(OnnxRunner.java:67)
```

`java.util.logging` 在 `java.logging` 模块里。补上之后，**又撞上第二个**：

```
java.lang.NoClassDefFoundError: javax/imageio/IIOException
  at org.apache.pdfbox.filter.FilterFactory.<init>(FilterFactory.java:42)
  at org.apache.pdfbox.filter.FilterFactory.<clinit>(FilterFactory.java:35)
  at org.apache.pdfbox.cos.COSStream.getFilterList(COSStream.java:302)
  at org.apache.pdfbox.pdfparser.COSParser.parseXref(COSParser.java:420)
  at org.apache.pdfbox.Loader.loadPDF(Loader.java:246)
  at com.litemask.pdf.PdfRedactor.open(PdfRedactor.java:181)
```

PDFBox 的 `FilterFactory` 静态注册过滤器时无条件构造 `DCTFilter`，
而 `DCTFilter` 引用 `javax.imageio.IIOException`（`java.desktop`）。
而 `COSStream.getFilterList()` 是**解析任何带交叉引用流的 PDF**（即 PDF 1.5+，
也就是绝大多数真实文档）必经的一步。**没有绕开的办法**，除非换掉 PDFBox。

**为什么第一次的「四条路径全通过」没抓到它**：那四条里没有一条是 PDF。
M3-1d 的结论「`java.desktop` 可砍」在它自己的验证范围内是成立的 ——
问题是这个范围小于产品的实际范围，而报告把它写成了全局结论。

### 3.3 第三次：把「精简运行时实跑」变成常设闸门，而不是一次性探针

修法不是「再探一次」，而是把验证方式本身改掉：

1. `tools/e2e-*.sh` 全部支持 `LITEMASK_RUN_JAVA` —— 打包仍用完整 JDK，
   **跑产品那一步换成 jlink 产物**。夹具与校验器留在完整 JDK
   （让夹具跟着裁模块，会把「夹具缺模块」误判成「产品缺模块」）。
2. **补上 `tools/e2e-ooxml.sh`** —— 原来 docx / xlsx / pptx 只在单测里跑过，
   而单测跑在完整 JDK 上。**没有任何一条检查会在裁过的运行时上跑 OOXML**，
   这就是 §3.2 那个错误能活下来的原因。

五个 e2e 在交付运行时上的实测结果（同一份 jar，同一个 jlink 产物）：

| 套件 | 结果 | 覆盖 |
|---|---|---|
| `e2e-serve.sh` | **107/107 PASS** | 真起 HTTP 服务、curl 从外部打、安全姿态、退出清理（2026-10-20 重测；M3-4 当轮是 46/46，其后 M2-c 补块加到 58，长任务章节 9g 到 83，上传先落盘章节 9h/9h-2 到 96，崩溃残留章节 9i 到 107） |
| `e2e-ooxml.sh` | **15/15 PASS** | docx/xlsx/pptx 全包扫描 + 令牌写入 + 还原往返 |
| `e2e-pdf.sh` | 通过 | PDFBox 独立校验文本层/表单/元数据 |
| `e2e-ofd.sh` | 通过 | Python 独立解析器校验 OFD |
| `e2e-untrusted.sh` | **6/6 PASS** | zip 炸弹、路径穿越、XXE |
| 手工探针 | 通过 | `--ner-model` 加载 v3 模型包 → 脱敏 → 映射 |

其中 `--ner-model` 跑通了 `张三丰`→`<人名1>`、`朝阳区人民法院`→`<机构名1>`，
映射文件 JSON 完整——这就是 `java.logging` 存在的理由。

### 3.4 定下来的规矩

**M0 之后每新增一条走第三方库的路径，都要在精简运行时上跑一次对应端到端；
新增一条管线就必须同时新增一个端到端脚本**（单测不能替代——它跑在完整 JDK 上）。

「精简运行时上跑一遍」也必须**逐条管线**跑，不能抽样跑：
本轮 PDF 炸了而 OOXML 没炸，恰恰是因为当时两者都不在采样里。

## 四、闸门怎么算的：`du -sk` 是错的

目录大小按**真实文件字节**累加（`find -type f -exec stat`），不用 `du`：

- `du` 报的是**磁盘占用**，每个文件至少占一个块（macOS APFS 常见 4KB），
  结果依赖块大小——换台机器、换个文件系统量出不同数字，报告没法复现；
- 本机实测（88,068,060 B 的 jlink 产物）：`du -sk` 虚高 311,332 B（0.30 MiB）。
  这个差值本身不大，但**它随文件数与块大小变化、不可预测**，
  而预算判定要的是可复现的数字。jlink 运行时里几千个小文件时差距会明显放大。

`stat` 的参数跨平台不同（macOS `-f%z`、Linux `-c%s`），脚本先探测一次。

## 五、`e2e-ooxml` 顺手暴露的一个真实行为

新写的样本把身份证**故意拆到两个段落**（`身份证`+`110105`+`号` / `续`+`19491231002X`+`尾`），
结果映射里出现：

```
phone  '19491231002'
```

`phone` 规则是 `(?<![0-9])1[3-9]\d{9}(?![0-9])`。第二段的前一个字是汉字「续」，
后一个字是 `X`，两侧都不是数字，于是中间 11 位 `19491231002` **完全符合手机号形状**，
被当成手机号脱敏了。

- **不是泄漏**：18 位原值一个字符都没留在包里（全包扫描通过），还原后逐字一致。
- **但标签是错的**：用户看到的是 `<手机号1>`，而原文是身份证。
- 根因是「不跨段落合并」这个既定决策（见 §六）。跨 run 合并是有的（破坏⑥ 守着它），
  跨段落合并没有——而真实文档里身份证被段落切断是常事。

处理方式：**记进已知限制，不改实现**。要修就得跨段落合并，
那会把两栏版式拼成不存在的字符串（OFD 已经因为同一个理由踩过）。
这条属于「取舍」，不属于「缺陷」。

> **⚠️ 更正（2026-10-20，块 13）**：上面那句「**不是泄漏**」**是错的**，
> 而且错在**推理**上，不只是结论。
>
> 错在哪：它拿「全包扫描没查到 18 位原值」当证据。
> 可那 18 位**从来就没有连续出现过**——被段落切开之后，包里只有两段碎片，
> 拼起来才是那个值。**「查不到完整值」与「没有泄漏」不是一回事。**
>
> 实测（`work/probe-cross-para.py`，手写 XML，不 import 被测代码）：
> 6 + 12 切法下只命中 1 处、且那 1 处是**手机号**（第二段里的 11 位 `19491231002`
> 被错标成 `<手机号1>`），区划码 `110105` 与校验位 `X` **原样留着**；
> **14 + 3 切法下 0 处命中，整张身份证原样留在文档里**。
>
> 顺带暴露了 e2e 标尺的盲区：本文 §五 说的那个跨段样本
> `tools/gen_ooxml_sample.py` **本来就造了**，而
> `tools/verify_ooxml.py` 的全包扫描只查**完整值**——
> 碎片残留**查不出来**，于是 e2e 一直是绿的，而碎片一直在交付物里。
>
> 已修：见 `docs/M4-阶段状态.md` §十五（跨单元续接，只归类不合并），
> 端到端的碎片级扫描与它的变异自证也在那一节。
> **本节原文保留不改**——错的是当时的判断，而当时的判断也是当时那轮的真实结论；
> 留着并标注更正，比悄悄改掉更有用。

## 六、已知缺口（不要当成已经量过）

- **Windows 侧 jlink 产物完全没量过**。jlink **不能在 macOS 上交叉构建 Windows 运行时**
  ——它需要目标平台的 `jmods`，而 macOS 的 JDK 不带 Windows 的。
  必须在 Windows 机器上构建，所以 M4 的 Windows 产物**本机做不出来**。
  win-x64 的模块集大概率与 macOS 相同（`java.logging` / `java.desktop` 都在），
  但 `.dll` 体积、ONNX Runtime 的原生库是否随包带 Windows 版本，都**未实测**。
- **安装器自身体积**（`.pkg` / `.msi` 框架与压缩后体积）未计入闸门。
- fat jar 未做 `--compress`（zip 压缩）处理，压缩后通常还能再降几 MB；
  打包时是否值得，取决于安装器是否已经压缩过一次。
- **跨段落被切断的标识符会被按段内形状重新归类**（见 §五），标签可能与原类型不符。
- **模型包签名校验未做**：SHA-256 是训练时算的，攻击者可以同时替换
  模型 / 词表 / 摘要三者。七道闸门拦的是「文件损坏与路径穿越」，不是「恶意替换」。
