# M2-b 阶段状态 · 脱敏 API 与「排除误报」能力

> 结论先行：M2 的第二块交付完成。`scan → 排除 → apply → download` 四个接口打通，
> 排除能力从 HTTP 层一直贯通到五种格式的**输出文件内容**。690 单测全绿、
> 对照实验 57 项全覆盖、端到端 22/22。
>
> **这一块真正的产出不是那四个接口，而是「排除」这个功能本身**——
> 它意味着正则误报不再需要用户去改规则文件重来一遍。

---

## 1. 为什么「排除」必须先沉到引擎

界面上点一下「这条是误报，别脱」，这件事要成立，得同时满足三件事：

1. 引擎认得「这条要跳过」；
2. 跳过之后**别的规则也不许接管那一段**；
3. 这个「跳过」能一路传到最终写出的文档里。

第 3 条最容易被忽略，因为它**不报错**：加一个重载参数忘了传，编译通过、输出文件照常生成、
报告数字照常漂亮，只是「用户点了别脱」这一项不起作用。所以这块的测试分两层：

| 层 | 测什么 | 谁 |
|---|---|---|
| `ExclusionTest`（13） | 引擎的**顺序语义**对不对 | `core` |
| `RedactorExclusionTest`（7） | 排除项**有没有真的落到输出文件里** | `core`，五种格式各一条 |

第二层是 M2-b 才有意义的一层。

---

## 2. 三条顺序语义，逐条钉死

它们的共同点是**错了不报错**，用户只会觉得「这工具不听话」，然后不再信任它的提示。

### 2.1 排除必须按「值」，不是按「位置」

排除键是 `(规则键, 原值)`，不是令牌、不是行号：

- **令牌**是分配出来的。一旦「排除了几条」，后面的编号就会变，
  界面发回来的排除项在第二次扫描时对不上号。
- **行号**在 PDF 里根本不存在——同一页的文本流位置会随重排变化。
- `(规则键, 原值)` 在「同一份文件 + 同一套规则」下稳定。测试 `排除键跨扫描稳定`
  把「扫两遍键集合相同」这件事钉死了。

顺带一个产品判断：用户看到的是「这条是误报」，他要表达的是**这个值别动**，
不是「第 3 次出现的那次别动」。同值同符本来就是本工具的核心不变式，按值排除与之一致。

### 2.2 排除先于重叠消解，且保护整个跨度

这条是最反直觉的。两条独立的规则：

- 用户排除身份证 `11010519491231002X`，
- 手机号规则仍可能从里面抠出 `19491231002` 脱掉——
  **用户排除了整段，文档里却还剩半段**。

所以引擎先把「被排除的命中所在的跨度」收成保护区，再让保护区挡住**所有**重叠命中，
最后才做常规的优先级消解。

### 2.3 顺序的证明必须来自「排除输家」

我第一版写错了：排除的是重叠里的**赢家**。那种情况下「排除放在消解前」与「放在消解后」
结果完全相同（赢家被拿掉后没人接手），**测不出顺序**。

真正能区分的是排除**输家**：正确实现按跨度保护，输家一被排除赢家就失去依据；
错误实现（先消解后排除）里输家早被丢掉了，那次排除是空操作，赢家照旧留下。

> `排除输家时赢家也要让开` 这条是补上来的。补之前那条测试是「绿的，但什么也证明不了」——
> 这正是本项目反复遇到的一类问题：**空转的断言比没有断言更危险，因为它看起来在守着什么。**

## 3. 排除项对不上任何命中时，必须照常脱敏

| 实现 | 结果 |
|---|---|
| 当成「用户没排除任何东西」→ 正常脱敏 | ✅ 密不透风 |
| 当成「意图不明，保守起见」→ 整篇不脱 | ❌ **fail-open** |

第二种会在这里发生：界面上规则键发错了、服务端规则改名了，
于是一份**完全没脱敏**的文档被用户当成脱敏结果下载走。

对照实验 ⒑ 专门守这一条。附带一条：`对不上的排除项不误伤` 这个名字也说明了这不是「宽容」，
是**方向不能反**——脱敏工具里，多脱是安全，少脱是事故。

---

## 4. 残缺的排除项：让请求失败，而不是悄悄丢掉

我原本在 `Exclusions.ofList` 的注释里写「丢弃完全空的项，避免一次空数组把整次请求判废」，
然后测试立刻打脸——`HitRef` 的紧凑构造器**先抛异常**，那条路径根本走不到。
等于宣称了一个做不到的宽容。

改成如实的行为：

- 数组里的 `null` 元素 → 丢弃（没有语义）
- 规则键或原值为空 → **整个请求 400**

为什么不静默丢弃一条排除项：丢掉的方向是「多脱」，密不透风，但用户会以为
「我保留的那个号码留下了」而它其实没留下，于是不再信任界面上每一条提示。
两种错法都不可接受时，选**能让问题当场暴露**的那个。

## 5. 接口

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/scan` | POST | 请求体就是文件本身（`application/octet-stream`），文件名在 `X-Filename` 头；返回命中清单 |
| `/api/apply` | POST | `application/json`：`{jobId, excluded:[{ruleKey, original}]}` |
| `/api/download` | GET | `?jobId=…`，按 jobId 取，**不接受调用方给的文件名** |
| `/api/restore` | POST | 仍为 501 占位（M2-b 后续增量） |

### 5.1 不引 multipart

上传体是 `application/octet-stream` + 一个 `X-Filename` 头。浏览器直接
`fetch(url, {method:'POST', body: file, headers})` 就够，引一个 multipart 解析器
是白付一份攻击面。

### 5.2 `scan` 会真的生成预览件，不是干跑

用户若一条都不排除，`apply` 直接把预览件转正——不重跑。对一份 200 页的 PDF 来说
重跑是白等几秒，而且两次运行之间文件没变，结果理应一致；与其赌这条不变式，不如直接复用。
`零排除` 那条测试同时验了「转正」与「重跑」两条路径给出同样的结果。

### 5.3 命中明细归一化，但**位置信息有多少说多少**

五个 redactor 的 `Report` 各不相同。归一化后每条命中带
`(ruleKey, original, token, occurrences, locators, hasLocators)`。

- docx 带「第 N 段」，xlsx 带单元格 locator，ofd 带载体名；
- **PDF 没有位置概念**，所以 `hasLocators: false`、locators 为空——
  界面上必须显示「无位置信息」，而不是画一个空的位置列。

排除不依赖 locator（键是值），所以「没有位置」不妨碍功能，只影响用户核对时能看到多少上下文。

### 5.4 报告里必须区分「0 命中」与「没得脱」

PDF 没有文本层时，`notes` 里会明确写出来：

> 这份 PDF 没有文本层（多半是扫描件）……0 处不是「文档干净」，是「没有可读的文本」。

端到端测试 `pdf无文本层必须报出来` 用一个空页面把这条钉住了。
把扫描件当脱敏过的文件传出去，是这个产品最不能犯的错。

OFD 的签章移除、附件改名、属性清空，xlsx 的数值转文本，pptx 的图表数值缓存——
全部按各自格式的措辞进 `notes`，并在 `stats` 里带上各格式自己的计数。

## 6. 本轮修掉的 4 个真实缺陷

### 6.1 `X-Filename` 头传中文会变成问号

**HTTP 头是 ISO-8859-1 的。** 测试里 `合同.docx` 回来变成了 `??.docx`——
一个把用户文件显示成问号的界面，会让人以为是文件坏了而不是工具坏了。

修法：客户端 `encodeURIComponent` 发，服务端 `URLDecoder.decode` 解，解不动按原样用。
连同 M2-a 的 `Content-Disposition` 下载名，两端都用 RFC 5987 的百分号编码。

### 6.2 `Content-Type` 校验漏在 try 之外 → 400 变成 500

`apply` 里 `requireContentType` 写在 try 外面，异常被 `dispatch` 的兜底 catch 接成 500。
**把「你发错了」说成「服务坏了」**，用户会去重启程序而不是改请求。已移进 try。

### 6.3 `Stats.of(String...)` 把「键值成对」留给运行时检查

少写一个值就把整条请求打成 500，而这是编译期就该知道的事。改成链式 `put`，类型安全。

### 6.4 我自己写的一条测试差点报假警

`新接口同样要令牌` 最初失败、无令牌却返回 200——看着像「令牌校验对新接口失效」的真漏洞。
追下去发现是**测试 helper 把令牌一并塞进了「无令牌」的请求里**。

已改成：**上传头默认不含令牌，需要令牌时由调用方显式加**，
并在测试里加了一条前提断言「这条请求确实没带令牌头」。
把「无令牌」写成构造上就做不到，胜过写完再检查一遍。

## 7. 验证结果（本轮实跑）

### 单测 690 全绿

新增：`ExclusionTest` 13 · `RedactorExclusionTest` 7 · `RedactionApiTest` 13。
657 → 690，**新增 33，零回归**。

`RedactionApiTest` 的判据一律看**下载回来的那个文件的内容**，不看接口自己报的命中数——
「接口说脱了 2 处」和「文件里真的没有原值」是两件事。

### 对照实验 57 项全覆盖，基线 GREEN

本轮新增 4 项：

| 编号 | 变异 | 打中的断言 |
|---|---|---|
| ⒏ | 排除只按值删命中，不保护整个跨度 | 三条顺序语义一起红 |
| ⒑ | 排除项对不上时整篇放弃脱敏（fail-open） | `对不上的排除项不误伤` |
| ⒒ | 五个 redactor 都不传排除项给会话 | `RedactorExclusionTest` 五条 |
| ⒓ | 写接口不校验 Content-Type | `contentType必须校验` |

**首轮全量跑出的不是 57/57，而是 56 PASS + 1 项 INVALID**，失效的是破坏⑩
（每段新建分配器）。脚本没有放它过关，打印了 `MUTATION_TARGET_MISSING` 并判无效——
这个守卫正是为这种情况存在的。根因是 M2-b 把 `RedactionEngine.redact` 换成了
`redact(text, rules, allocator, exclusions)` 四参重载，而脚本里那一条变异仍然写着三参的旧签名，
`sed` 替换零命中、源码原封不动跑了一遍全绿的测试。**没命中 ≠ 没风险，只等于这一项没测。**

修正变异目标后单项重跑：PASS，四个测试类同时转红
（`DocxRedactorTest` 失败 2、`RedactionRoundTripTest` / `XlsxRedactorTest` / `PptxRedactorTest` 各 1），
基线复核 GREEN，残留 `.bak` 为 0。

顺带一条纪律写进了脚本注释：**改任何被变异源码的方法签名，都要顺手核一遍
`control-experiment.sh` 里以该行文本为锚点的变异**。这类漂移不报错、不变红，
只会让某一项覆盖悄悄消失。

### 端到端 22/22 PASS（`tools/e2e-serve.sh`，走打包后的 jar）

新增一条：**表单类型被拒**（不能只靠令牌一道防线）。

### 打包体积

`target/desens-core.jar` = **6,291,318 B（6.00 MiB）**，比 M2-a 的 6,261,614 B 增加 29,704 B。
新增的只有 Jackson（`Json.java` 共用 `ObjectMapper`）与 HTTP 层代码，**零新增第三方依赖**。
距离核心包 90 MB 硬指标还剩约 84 MB。

## 8. 已知限制与缺口

1. **`/api/restore` 仍是 501。** 还原走的是映射文件那条线，本块没做。
2. **单任务不可重入。** 同一个 `jobId` 重复 `apply` 直接 400「已经应用过」，
   改排除项要重新上传。界面上做成「改完重新走一遍」即可，但这是个 UX 妥协，记下来。
3. **任务数上限 64**，超了拒绝新的。目前没有任何回收机制——只有进程退出才清空。
   长时间开着的服务需要加 LRU，M2-c 前得补。
4. **`scan` 会把预览件真的写到磁盘。** 上传即脱敏，不存在「只扫描不落盘」的路径。
   对本机工具来说这是对的（用户就是要这个文件），但接口设计上没有 dry-run。
5. **排除只到「值」这一级**，不支持「第 N 次出现单独保留」。
   同一份文档里同一个手机号出现 5 次、只有第 2 次是误报时做不到——
   这属于 M2-c 的「手动区域调整」，需要位置级排除。
6. **PDF 的命中没有位置信息**，界面无法高亮到具体位置，只能列出值。
7. **M2-a 的浏览器端那一半仍未验证**（同源策略是浏览器行为），M2-c 验收项。
