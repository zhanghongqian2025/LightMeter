# M1-d 阶段状态：PDF 管线（2026-10-15）

## 结论

PDF 管线完成。**474 测试全绿，对照实验 26/26**，fat jar **5.91MB**
（M1-c 为 2.38MB，整条 PDF 能力增加约 3.5MB）。至此四种格式全部打通。

四种格式里只有 PDF 引入了第三方库（PDFBox 3.0.3 + fontbox + pdfbox-io）。

## 为什么 PDF 必须引库，而 OOXML 三件套不用

M1-a 选型时的判据是「**这个库覆盖不到的位置有哪些，漏了会不会静默失败**」，
结论是 OOXML 全部用 JDK 自带的 zip + DOM，一个字库都不引。到了 PDF，这个判据给出了相反的答案：

- OOXML 的文本藏在**少数几种固定节点**里（`<w:t>` / `<si>` / `<a:t>`）。把清单列出来
  逐个处理，「列出清单」本身就是覆盖率证明。
- PDF **根本没有「文本节点」这个概念**。字符被编码进内容流的算子操作数里，字形编码由
  字体子集决定（Identity-H / 各类 CMap），字体还可能缺 ToUnicode。
  自己实现等于重新实现一个 PDF 解析器，而漏掉的分支会「文件正常生成、工具正常报告成功、
  原文还在」。

所以 **PDF 引入 PDFBox，但仍然不重新编码整条内容流**：
用 PDFBox 拿结构（页、资源字典、字体、元数据），
再用自己的词法扫描器拿**精确字节区间**，定点替换。未改动的 token 逐字节原样复制。

## 覆盖范围

| 位置 | 说明 |
|---|---|
| 页面内容流 | 拼接匹配，允许一个敏感信息跨多个 Tj/TJ |
| **表单 XObject** | 页面上的模板块，递归深度上限 8 |
| **不可见文本（Tr=3）** | 扫描件上盖的 OCR 层：屏幕上看不见，复制/检索/抽取都拿得到 |
| 元数据 | `/Info`、`/Metadata`(XMP)、`/PieceInfo`、自定义键位 |
| 批注 | `/Contents` 过脱敏引擎，作者 `/T` 清空 |
| 书签 | 标题脱敏 |
| **内嵌附件** | `/Names/EmbeddedFiles` |
| **JavaScript** | `/Names/JavaScript`、`/OpenAction`、`/AA` |
| 表单 | `/AcroForm` |
| 增量保存 | 输出**整体重写**，旧版本原样留在文件里的情况不会发生 |

## PDF 的要害：删字符会挪动版面

OOXML 里替换一段文字，版面纹丝不动。PDF 里不行——显示算子的位移是**累积**的，
删掉 N 个字符，后面的文字就整体前移 N 个字的宽度。

所以回写必须**补位移补偿**，用的是 `TJ` 数组里的调整数（规范 9.4.4：数值 n 让位置左移
`n/1000 × Tfs × Th`）。补与删合并在同一个 `TJ` 里，不需要跟踪文本矩阵。

三条纪律：

1. **整算子处理**：一个显示算子要么整段原样复制（字节不动），要么整段重写。
2. **绝不发 `Tm/Td/T*`**：只改文本不改坐标。
3. **删掉的每一段都要补位移**，一段都不能少（下面第三个缺陷就是漏了这一条）。

## 本阶段修掉的缺陷

### 1. 跨算子续段删了字符却不补位移（**会泄露原文**）

一个手机号被排版切成 `(1380)` + `[(013) -120 (8000)]` 两段。令牌只写进第一个算子，
后面那段只删字符——但删字符不会自己把笔挪回去。

结果不只是版面歪：`8000` 落在 x=98.13，正好压在令牌（x=70~140）上，
抽取出来是 `Tel <PHO8N00E0_d1o>ne` 这种交错乱码，而**那四个数字原封不动留在文件里**。

原来的断言只查「完整的手机号还在不在」，手机号被切成三段全删光之前，
漏掉任何一段都不会让断言变红。改成了逐字比对整段抽取文本：

```java
assertEquals("Tel <PHONE_1> done", squeeze(PdfFixtures.extractText(out)));
```

> 这类缺陷的形态值得记住：**测试是绿的，内容却在泄露**。
> 凡是「查原文还在不在」的断言，都要先问一句：如果原文被切成几段、只漏掉一段呢？

### 2. 跨元素的命中只对第一个字符串元素生效

元素循环末尾的 `editIdx = q` 把一条跨元素的命中提前标记成「已消费」，
于是同一个 `TJ` 里的第二个字符串（`8000`）根本没看到这条编辑，字符原样保留。
和缺陷 1 是两个独立的漏，测试补强后分别被对照实验 ⑳ 咬住。

### 3. Type0 字体解码死循环 → 任何中文 PDF 都会 OOM（**最严重**）

```java
while ((code = font.readCode(in)) >= 0) { ... }   // 错
```

PDFBox 3.x 的 `PDType0Font.readCode(InputStream)` 在**输入耗尽时返回 0 而不是 -1**。
于是这个条件在耗尽后仍然成立，又没有新字符可解码，`StringBuilder` 一直涨到 OOM。
实测 3GB 堆照样撑爆。

`Type0/CID 字体是中文字体的唯一形态`——也就是说**任何真实的中文 PDF 都会在这里把进程撑爆**，
而所有用标准 14 字体的拉丁夹具永远走不到这条路径。这是一个**只在真实文件上才会现形的雷**，
而且此前 448 条测试全绿。

修法：终止条件挂在「输入还剩几个字节」上，并加一层「本次读取一个字节都没消费就停」的兜底
（字体不认这段编码时不至于空转）。抽成 `PdfCodes.forEachCode` 供四处共用。

配套加了**看门狗测试**：在守护线程里跑中文脱敏，60 秒不结束就明确失败。
不加看门狗的话，这类回归只能等 OOM 才暴露，既慢又拿不到「哪条断言不成立」的证据。

### 4. 还原时只换编码不换 Tf（中文整段乱码）

令牌是用标准 14 字体画的，所以脱敏件里**令牌算子生效的字体是令牌字体**。
还原时要用原字体编码原文——但只换编码不换 `Tf` 的话，
字节是原字体的码位、解释它们的却是 Helvetica，中文整段变乱码，
而工具照样报告「已还原」。

修法：从令牌算子后面那个 `Tf`（脱敏时 `emitToken` 写回去的）取出原字体，
还原时先把 `Tf` 切回去再写文字。

### 5. 位移补偿按单个字符串元素算，而不是按整个命中区间算

命中横跨同一个 `TJ` 里的多个字符串时，`removedWidth` 只量了第一个元素，
补偿不足，后续文字偏移。对照实验 ㉒。

### 6. 同一个 TJ 里的多个字符串各写一次令牌（**页面画出两个令牌**）

这是上面第 1 条的「同 op 版」。回写器里的判断是 `if (ed.replacement() != null)`，
而一条命中横跨同一个 `TJ` 里的两个字符串时，这个条件对**每个**元素都成立，
于是令牌被写了两次。页面上是 `联系电话：<PHONE_1> <PHONE_1>`，
还原时也会被换回两遍，得到 `1380013800013800138000`。

跨算子（缺陷 1）和同算子跨字符串（缺陷 6）是两条不同的路径，
修一处不修另一处，另一处照样漏。补了 `done[]` 标记，替换文本只发一次。

### 7. 还原报告恒为「还原 0 处」

`restore` 里声明了 `List<Change> all` 用来记账，却**从来没往里填过**。
文件里其实已经换回去了，报告却说 0 处。

> 凡是「报告里的数字」，都要有一条测试专门断言它和实际做的事一致。
> 这类 bug 不会让功能出错，只会让用户没法判断该不该信你。

### 一条方法论

缺陷 6 和 7 **都是 474 条单元测试全绿的情况下，被端到端脚本抓出来的**——
单元测试用的夹具没有「一个 TJ 里放两个字符串」这种写法，
而单元测试根本不经过 CLI 那一层（报告是 `Report` 对象，不经过打印路径）。

**端到端验的是另一类东西**：它验的是「用户实际会走的那条路」，
包括夹具不会刻意去造的组合、以及报告与事实是否一致。两者不能互相顶替。

脚本里加了两条约束，都是踩过之后补的：

1. **靠抛异常红的对照实验判为无效。** 早先的 ⑲ 变体是往列表里塞了个 `Integer`，
   `flushTj` 强转 `Double` 时炸掉——那是「崩溃了」，不是「断言发现文档不对」。
   现在要求红灯必须来自**至少一条断言失败**。
2. **CRASH 期望模式。** 死循环/内存爆炸这类变异在物理上不可能产生断言失败，
   进程先被打死。它的证据形态是 surefire 的 fork 崩溃，判它有效，
   但**必须同时确认崩溃真的发生了**，否则一个无关的红灯也能混进来。

## 端到端验证（真实中文 PDF，`tools/e2e-pdf.sh`）

脚本用**命令行**（不是内部 API）跑一份满是坑的样本：中文子集字体、手机号被排版切成
同一个 `TJ` 里的两段、扫描件式的不可见 OCR 层、作者姓名、批注正文里的手机号、
内嵌附件名、JavaScript、书签标题里的手机号。

校验用一份**完全独立的程序**（`tools/E2ePdfSample.java`），
只用 PDFBox 自己的文本引擎加原始字节扫描，不碰被测代码的解码逻辑。

结果：

- 脱敏 **5 处**：跨算子切分的手机号、正文身份证、邮箱、银行卡、**不可见 OCR 层里的身份证**
- 清理 **7 项隐藏信息**：`/Info`、XMP、`/Names/EmbeddedFiles`、`/OpenAction`、书签标题、
  批注正文、批注作者名
- 字节级扫描：6 类原文值在**整个文件**里 0 残留（不只是文本层）
- 往返：还原后抽取文本与原件**逐字一致**，无残留令牌

> 这套端到端在第一次运行时抓出了两个 474 条单元测试全绿也看不见的缺陷（见上文缺陷 6、7）。


## 一个刻意的取舍：令牌恒定 100% 缩放

试过「令牌比原文宽就横向压到与原文等宽」，视觉整齐，代价是**还原彻底对不齐**：
压扁写在 `Tz` 上，而还原时无从知道原文的 `Tz` 该是多少，只能留下一个歪掉的版面。

于是宁可让令牌偶尔比原文宽（实际绝大多数相反：18 位身份证远比 11 个字符的令牌宽），
也要保证脱敏与还原严格互逆。

另配一张 ASCII 短前缀表（`id_card→ID`、`ip_address→IP`、`email→MAIL`），
消掉 `<IP_ADDRESS_1>` 比 `192.168.1.100` 还宽这种最常见的溢出。

## 如实呈现的局限

1. **PDF 令牌是 ASCII，Word/Excel 是中文。** 两边映射文件不通用。
   PDF 的字符串是字体编码，中文令牌要用子集内嵌的原字体画，会缺字形；
   用标准 14 字体则一个中文字形都没有。宁可令牌是英文，也不塞 5~15MB 字体进安装包。
2. **元数据与内嵌附件名的清理不可逆。** 原值从未保存，`restore` 换不回来。
   这是有意为之（存着原值等于没脱敏），但**必须写进用户文档**，不能让人以为还原能全复原。
3. **解不出字符就不脱。** 字体缺 ToUnicode 时直接拒绝并说明原因，
   不做「尽力而为」——继续下去等于「看着处理了、其实没处理」。
4. **需要真口令的 PDF 一律拒绝**；空用户口令的「加密」PDF（DRM 商业文件）能解开就正常处理，
   但输出时去掉加密。
5. **没有文本层（扫描件）会明确报出**，且措辞是「没有可读的文本」而不是「文档干净」。

## 已知边界

- **不做 OCR**：扫描件里的图像文字一个字都不处理
- **不做「涂黑」模式**：目前只能写可还原的令牌。若后续要支持「只留白/涂黑、不可还原」，
  令牌溢出问题会随之消失
- 渲染模式 4（填充+描边）等特殊模式未逐一验证
- 中文字体路径依赖本机存在 CJK 字体（测试会跳过并说明，不假装通过）
