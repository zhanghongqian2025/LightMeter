## 三、这一块为什么这么选

### 3.1 夹具用手写 protobuf，不依赖 onnx 包

`tools/make_ner_fixture.py` 纯标准库拼 protobuf 字节。理由是**标尺独立性**：
夹具生成器如果用 `onnx` 官方 Python 包，那它和被验的 Java 解析路径就共享了「官方 protobuf 编码」这一个假设。
一旦这个假设有偏差（比如某个字段的 wire type 写错），两边会**一起错**，测试照样全绿。
手写字节反而是第三方实现，能交叉验证。

### 3.2 必须 `check_model(full_check=True)` + 真的加载一次

这一条是本轮踩出来的，见 §4.2。

### 3.3 `OnnxRunner.open()` 里先过自包含闸门，没有绕过入口

`OnnxSelfContained.assertSelfContained` 写在 `open()` 内部而不是作为可选的前置检查。
理由：它是 M3-1b 立下的「模型必须自包含」这条规矩的执行点。
做成可选，就等于留了一个「正常路径之外也能加载外部数据模型」的口子——
而那种模型包的后果不是脱敏不准，是**本地文件被读走**。

## 四、这一轮挖出来的真实缺陷

### 4.1 滑动窗口的「左切边丢弃」会把跨窗口实体整个丢掉（最严重）

**现场**：`张三丰北京大学`（7 字），窗口宽 5、重叠 2，窗口是 `[0,5)` 与 `[3,8)`（越界部分按全文末尾处理）。

| 窗口 | 看到的「北京大学」 | 结果 |
|---|---|---|
| `[0,5)` | `[3,5)`，终点贴右切边 | 丢（截断的半截） |
| `[3,8)` | `[3,6)` 起点恰好等于左切边 | 丢（老实现的对称规则） |

两边都不认领，**实体整个消失且零报错**。对脱敏工具来说这就是漏脱。

**根因**：老规则左右对称地丢，理由是「贴切边就可能被截断」。但**左边的理由不成立**——
解码器在 BIO + `allowsStart` 双约束下只会输出以 `B-` 开头的实体，
所以一个起点落在窗口左边界上的实体，**是真的从那里开始的**，不可能是被截断的尾巴。

**修法**：`贴着切边` 只判右边。顺带发现一条可以强制的不变量（见 §4.4）。

**测试**：`SlidingWindowNerTest.左切边上的起点不是截断`。
这条测试的另一个存在理由是：修 bug 之前，所有用到窗口的测试**都特意把实体挪开了左切边**，
等于这条分支从来没被当成期望行为测过——**「另一面没测」就等于没测**。

### 4.2 `Gather(data, indices)` 参数顺序写反，普通 `onnx.checker` 查不出来

`tools/make_ner_fixture.py` 里把 `Gather` 的两个输入写反了。

- `onnx.checker.check_model(m)`（默认）**通过**——它不做类型推导。
- 真正加载时报 `Type 'tensor(float)' of input parameter (table)...`，
  实际含义是「这个参数被当 indices 了，而 indices 必须是整型」。

**教训**：ONNX 夹具的校验必须**同时**满足两条：
①`check_model(full_check=True)`；②用目标运行时（这里是 ORT）**真的加载并跑一次**。
少任何一条都可能放行一个「结构合法但类型错误」的模型。

### 4.3 `tag=None` 走到实体分支，普通字符失去 O 倾向

夹具生成器对普通字符调 `entity_row(None)`，7 通道变体里七行全落 `-5.0`。
argmax 仍然挑通道 0（所以**看通道号是对的**），但分数是 -5——**只有做数值比对才暴露**。

**教训**：「挑中了正确的类别」和「这一类别的分数合理」是两件事。
断言只看 argmax 下标的测试，对这种缺陷完全免疫。

### 4.4 `overlap ≥ maxEntityChars` 是「不丢实体」的充要条件

相邻窗口起点相隔 `step = maxChars - overlap`。长度 L、起点 a 的实体，
能被某个起点 s ≤ a 的窗口完整包含，当且仅当 `maxChars ≥ L + (a - s)`；
最坏情况 `a - s = step - 1`，于是要求 `maxChars ≥ L + step - 1`，即 **`overlap ≥ L`**。

同一条件下，实体也**不可能**恰好结束在某个窗口的右切边上（那需要 `L > overlap`），
所以「贴右切边丢弃」这条规则不会误伤。

违反时的现场是**实体整个消失且不报错**。因此 `NerRecognizer` 构造时直接校验，
不满足即抛 `IllegalArgumentException`——**宁可启动失败，也不静默继续**。
对照实验 `破坏⒪` 守住这条。

## 五、体积：这一轮真正的坑在 PDB 上

### 5.1 `onnxruntime.pdb` 单个 304,648,192 B（290 MB）

加了 ORT 依赖后第一次 `mvn package`：

```
desens-core.jar  76.47 MiB
```

`onnxruntime` 的 jar 里同时打进了 macOS 与 Windows 的**调试符号**。
shade 插件只排除了 `**/*.dSYM/**`（macOS 的形式），没排除 `**/*.pdb`（Windows 的形式）。
补上之后：

| 阶段 | fat jar |
|---|---|
| 排除 dSYM 之后（未排除 pdb） | 76.47 MiB |
| 补上 `**/*.pdb` 之后 | **16.93 MiB（17,757,154 B）** |

**可推广的判据**：调试符号的**文件名后缀按平台规则不同**，
`*.dSYM/` 是 macOS 的目录式调试符号、`*.pdb` 是 Windows 的文件式调试符号。
过滤规则必须**按平台各写一条**，只写一条就等于给另一个平台留了个 290MB 的洞。

### 5.2 当前 jar 里实际装了什么

```
ai/onnxruntime/native/osx-aarch64/libonnxruntime.dylib
ai/onnxruntime/native/osx-aarch64/libonnxruntime4j_jni.dylib
ai/onnxruntime/native/win-x64/onnxruntime.dll
ai/onnxruntime/native/win-x64/onnxruntime4j_jni.dll
```

`*.pdb` / `dSYM` 条目数 = **0**。
双平台 native 一起打进同一个 jar，运行时由 ORT 按平台挑，不出双 jar。

| 层 | 实测 | 备注 |

## 六、M3-1c 带来的接口约定（M3-2 / M3-3 必须遵守）

### 6.1 ONNX 模型的形状契约

| 项 | 约定 |
|---|---|
| 输入 | `ids`，`int64`，形状 `[batch, time]` |
| 输出 1 | `emission`，`float32`，形状 `[batch, time, C]` |
| 输出 2 | `transition`，`float32`，形状 `[C, C]`，按 `[from, to]` |

**转移矩阵放在 ONNX 里，而不是旁边再放一个文件**。理由是杜绝「换了模型忘了换转移矩阵」——
那种错的现场是全部实体类型判错，而报告一切正常。

### 6.2 通道顺序 = `TagScheme.bio()`

```
0=O   1=B-PER   2=I-PER   3=B-ORG   4=I-ORG
```

`TagScheme` 要求**恰好一个** null 类型，且每种实体类型恰好两个标签（B- 与 I-）。
所以模型标签集与 `EntityType` 是**严格对齐**的，不能多也不能少。

### 6.3 三条硬约束，训练侧必须与推理侧一致

1. **BIO 结构约束**：`TagScheme.allowsByBIO` + `allowsStart`。
   训练脚本 `tools/train_ner.py` 里的 `ALLOWED` / `ALLOW_START` 必须与它逐条对应。
2. **不训练 start/end 转移**。`SequenceDecoder` 不读它们，多训只会让训练口径与推理口径不一致，
   症状是推理 F1 比训练 F1 低一截且查不出原因。
3. **非法转移先屏蔽（-1e4）再学**，使导出的 `transition` 与 `TagScheme` 的硬约束**幂等**：
   Java 再叠一层约束不会改变结果。

### 6.4 词表文件格式

`vocab.txt` 每行一个字符，**第 i 行（0 基）对应 id i+1**，id 0 是 UNK 占位。
这与 `CharVocab.ofListedChars(List<String>)` 对齐。

## 七、这一块没做到什么（不藏）

- **NER 还没有接进脱敏管线**。`NerRecognizer` 能返回 `List<EntitySpan>`，
  但到 `core.Match` 的适配层（ruleKey / tokenPrefix / sortOrder）还没写，
  五种格式的管线也还没接。这是 M3-1c 的后半段，也是下一步。
- **模型精度完全没有测过**。现在只有玩具夹具（`out[t,:] = table[id[t],:]`），
  它验证的是链路通不通，与「认不认得出人名」无关。
- **Windows 侧体积一片空白**。win-x64 native 进了 jar，但在 Windows 上能不能加载、
  jlink 运行时多大、最终安装包多大，都没测。现有全部数字是 macOS arm64。
- **`java.desktop` 还没砍**，`ServeCommand` 仍用 `java.awt.Desktop` 开浏览器。
- 端到端 46/46 覆盖的是 M2 的服务端接口，**没有一条用例真的跑过 NER**——
  因为 `NerRecognizer` 还没进管线。
