## 2. 访问控制：为什么一个「只监听 127.0.0.1」的服务还要这一层

这是本块最需要讲清楚的部分。浏览器里的**任意外部网页**都能向 `http://127.0.0.1:PORT/...` 发请求。
受同源策略限制它<b>读不到响应</b>，但<b>请求本身会真的执行</b>。三条缝：

| 缝 | 不补会怎样 | 本项目的做法 |
|---|---|---|
| 不校验 `Host` | DNS rebinding（让 evil.com 解析到 127.0.0.1）成立，服务等于对外公开 | Host 必须是 `127.0.0.1`/`localhost`/`[::1]` 且端口精确相等 |
| 不校验 `Origin` | 外部网页的跨源写请求畅通，能驱动用户本机处理文件 | Origin 必须与本服务同源；无 Origin 放行（非浏览器客户端） |
| 不校验令牌 | 任何知道端口的进程都能调写接口 | 每次启动随机 48 位十六进制令牌，写操作必须带 |

### 三条相互独立，不是一道

对照实验 ⒉⒊⒋ 逐条拆掉其中一道，每条都让对应的那批断言变红——说明它们不是同一道门的三种写法。
拆掉 Host → `SecurityPolicyTest$Host` 16 条失败；拆掉令牌 → `$Write` 2 条失败；
拆掉 Origin → `$Origin` 14 条失败。

### 刻意不做的事

- **不返回 `Access-Control-Allow-Origin`**。不配 CORS 是这里的安全默认值：
  跨源脚本连响应都读不到，令牌自然也偷不走。Word/WPS 加载项走本机进程调接口，不受 CORS 约束。
- **不答 `OPTIONS` 预检**。答了预检等于告诉浏览器「跨源可以试试」，而这条门恰恰要关着。
  `OPTIONS /api/scan` 返回 405（单测与端到端都验了）。
- **不解析 `multipart/form-data`**。上传体是 `application/octet-stream` + `X-Filename` 头。
  引一个 multipart 解析器就是多一份攻击面，而「拖一个文件进来」并不需要它。

## 3. 两处实现被测试逼着改掉的地方

### 3.1 Host 解析：`parseInt` 会让畸形端口蒙混过关

写测试时我把 `127.0.0.1:08931` 放进了拒绝清单，结果发现**现实现会放行**它——
`Integer.parseInt("08931")` 等于 `8931`。同类问题还有 `127.0.0.1:`（有冒号没端口，
端口段为空时旧代码直接跳过端口校验）。

修法不是把断言改软，是把解析改成**没有意外分支**的形式：

- 端口按**字符串精确比对**，不用 `parseInt`——前导零、空白、非数字一律拒；
- 多个冒号却不带方括号（漏了方括号的 IPv6 字面量）显式拒。旧代码会落进「按最后一个冒号切端口」
  的分支，把 `::1` 切成 `host="::" port="1"`，**本服务端口恰好是 1 时就放行了**。
  那是「意外成立」而不是「设计成立」，两类都该拒绝。

不接受裸 `::1` 也是同一个理由：RFC 7230 要求 IPv6 字面量带方括号，不带就是畸形。

### 3.2 健康检查里的 `bindAddress` 原本是写死的，会在绑定地址被改掉后继续说谎

代码复查时发现的：`posture.put("bindAddress", "127.0.0.1")` 是一个常量字符串。
将来有人把 `BIND_ADDRESS` 改成 `0.0.0.0`，**这个接口仍然会报「绑在 127.0.0.1」**——
而界面正是照着它显示的。报告字段说谎，比没有这个字段更糟。

修法是从 socket 读（`LocalServer.boundAddress()` / `loopbackVerified()`），
没有第二份字符串可以走样。

另外把 `hostHeaderChecked: true` 的**依据**写进代码注释：它不是写死的常量，
而是「请求能走到这个处理器，本身就说明 Host 头已过校验」——`dispatch` 在读请求体之前就判了。

**这条修复没有自己的对照实验，说清楚为什么**：`boundAddress()` 返回 `127.0.0.1`
和硬编码常量返回 `127.0.0.1`，断言两者相等是恒真的，抓不住任何东西。
真正能抓住「绑到了非回环」的只有对照实验 ⒎ 与「局域网连不上」那条断言。
新加的测试 `绑定地址不是写死的` 只能钉住取值格式与来源一致性——**它的牙齿有限，如实说明**。

### 3.3 `displayNameOf` 的占位分支经 `store` 不可达

我原本写了「上传一个叫 `..` 的文件，断言显示名是 `未命名文件`」——**红灯，理由是测试写错了**：
`".."` 没有合法后缀，会在 `extensionOf` 就被拒。

顺着这条失败查下去发现一件更要紧的事：**能被 `store` 收下的文件名必然含白名单内后缀，
剥掉路径后不可能为空**，所以占位分支经 `store` 是不可达的。它真正服务的路径是
「客户端报了个根本没有文件名的怪东西」时的报错文案。测试改成直接打在那条真实路径上，
并把这个不可达性写进注释——否则下一个人会以为这条分支有覆盖。

## 4. 上传路径：外部文件名绝不参与路径拼接

`Workspace` 存在的唯一理由就是这一条。浏览器交上来的文件名是**攻击者完全可控的输入**，
一旦 `workspace.resolve(session).resolve(clientFilename)`，一个 `../../.ssh/authorized_keys` 就能落到工作目录之外。

分工是死的：

- **磁盘名**由服务端生成（UUID + 白名单后缀），不接受任何外部输入；
- **客户端文件名**只做两件事：判定后缀（白名单）、生成一个剥掉路径分隔符与控制字符的**显示名**。
  显示名只出现在界面上，**永远不进文件系统**。

白名单刻意不收 `.html`（存进去再取出来用浏览器打开等于自己发一个 XSS）、
不收 `.jar`/`.sh`/`.exe`（本机工具没有理由接收它们）。

### 测试用真实哨兵目录，而不是断言字符串

穿越用例如果只断言「返回的 Path 字符串看着没穿越」，那是一次纯字符串断言——
实现里某处多做一次 normalize 它照样绿。所以测试在**工作目录旁边**建一个真实的 `canary/` 目录，
传 `../../../canary/pwned.pdf`，然后断言 `canary/` 仍然是空的。

对照实验 ⒍ 的变异点选的是「直接把客户端文件名拼进 `resolve`」，而不是「忘记剥 basename」：
后者其实仍落在会话目录内（剥完只剩 `pwned.pdf`），测它**证明不了穿越这件事**。
真正会出事的是原始字符串直接进 `resolve`。

## 5. 只绑回环：启动自检是启动失败，不是警告

把 `0.0.0.0` 写成 `127.0.0.1` 只需要改一个字符串，而后果是整个局域网可访问。
本机工具犯这种错的概率高于直觉，所以：

- 绑定地址写死成 `127.0.0.1`，不从参数来；
- `LocalServer.create` 在 `start()` **之前**核对 `http.getAddress()` 确实落在回环上，不是就抛异常中止。

### 端到端真的从局域网地址连了一次

单测里有一条 `局域网地址连不上`：拿到本机第一个非回环 IPv4，尝试连上去，**连上就 fail**。
端到端脚本用 `ifconfig` 取到本机 `172.16.94.97`，`curl --max-time 2` 打过去——连不上。
这是「只绑回环」唯一有说服力的证明：不是读配置，是从外面真的敲一遍。

对照实验 ⒎ 把**绑定地址和启动自检一起**拆掉，此时能抓住它的只有这条断言。
为什么必须一起拆：只拆自检，绑定本来就是对的，什么也测不出来；
只拆绑定，自检会拦住它、测试以 **Error** 而非 **Failure** 变红，
而脚本的判据是「断言失败数 > 0」，会误判成 INVALID。两个一起拆才是真实状态。

## 6. 令牌怎么交给浏览器

`serve` 启动时 `newToken()` 生成 48 位十六进制（24 字节 SecureRandom），**不打到 stdout**
（终端回滚缓冲和截图都是泄露面），需要排障时用 `--print-token`。

交给浏览器的唯一途径是**服务端渲染首页时注入**到 `<meta name="litemask-token">`：

- 不放 URL——URL 会进浏览器历史记录，也可能从 Referer 泄给别的站；
- `Referrer-Policy: no-referrer` 再堵一道；
- 令牌是纯十六进制，不含需要 HTML 转义的字符；即便将来换字符集，走的也是**文本替换**而非脚本拼接。

前端拿它放进 `X-Litemask-Token` 自定义头。**自定义头会触发 CORS 预检，而本服务不答预检**——
所以外部网页连构造出这样一个请求都做不到，令牌是在此之上的第二道，不是唯一一道。

## 8. 已知限制与缺口（如实列出）

1. **写接口是 501 占位。** `scan/apply/restore` 目前只做到「鉴权通过后抵达处理器」这一步，
   这是 M2-b 的事。界面上也明确写了「尚未接入」，没有放一个不能点的按钮假装能用。
2. **浏览器端的那一半无法在本仓库验证。** 同源策略让跨源脚本读不到响应，是浏览器的行为，
   服务端只能靠「不返回 CORS 头」来实现。本测试断言的是「响应里没有任何 CORS 头」，
   **浏览器是否照此执行不在测试判定范围内**。要真正确认需要真人开浏览器 +
   一个跨源页面，那是 M2-c 的验收项。
3. **没有 `Content-Type` 校验。** 目前写接口只看令牌，不看请求体是什么类型。
   M2-b 接上传时必须补上，否则一个不带令牌约束的 HTML 表单仍可能打到 `/api/scan`
   （令牌头是自定义头，HTML 表单设不了——但这条防线不能只靠浏览器）。
4. **`LocalServer` 没有认证/限流。** 知道端口 + 有令牌就能一直打。令牌每次启动都变是当前的全部防线，
   对单机工具够用，但不是多用户场景的答案。
5. **无开机自启、无端口占用自动退让。** 端口被占目前是**明确报错并给建议**（端到端第 10 项验了），
   没有自动换端口重试。开机自启在 M4。
6. **IPv6 回环没做双栈。** 只绑 `127.0.0.1`，所以 `localhost` 在解析到 `::1` 的机器上可能连不上。
   打开浏览器的地址固定用 `127.0.0.1`；Host 白名单仍接受 `[::1]` 以备将来双栈。
7. **请求体上限在 HTTP 层是 `readBody` 的参数，M2-b 接上传时才会真正被调用。**
   `Workspace.MAX_UPLOAD_BYTES` 已生效并有测试，但两层上限的数值需要到时候统一。
