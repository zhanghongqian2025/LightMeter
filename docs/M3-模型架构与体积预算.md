# M3 模型架构与体积预算（实测依据）

> 记录时间：M3-1b 收口期间
> 目的：把「模型到底能分到多少 MB」和「为什么不能用现成预训练模型」两件事用**实测数字**钉死，
> 避免后续讨论反复回到「随便找个 BERT 就行」的假设上。
>
> 状态标注约定（沿用质量红线第 7 条）：
> **已验证** = 本轮实际跑过并留下数字；**已实现** = 代码写了但没验；**计划** = 尚未动手。

---

## 1. 结论先说

1. **现成的任何中文 NER 预训练模型都塞不进预算**——不是「不划算」，是**物理上放不下**。
2. 必须**自训一个小的字符级模型**（IDCNN + CRF，约 2–8 MB），
   这是 ≤90MB 硬约束的必然结果，不是偷懒。
3. 顺带发现一个白捡的 14.1 MB：把「打开浏览器」从 `java.awt.Desktop` 换成 `ProcessBuilder`，
   就能把 `java.desktop` 整个踢出 jlink 运行时。

---

## 2. 已验证：固定开销实测

### 2.1 jlink 定制运行时（macOS arm64，JDK 21.0.12.1）

用 `jdeps --multi-release 21 --print-module-deps target/desens-core.jar` 得到真实模块依赖：

```
java.base
java.desktop
java.sql
jdk.httpserver
```

（`javax.xml` 的 DOM 解析来自 `java.xml`，由上述依赖传递引入。）

两种组装方式的实测体积：

| 运行时模块集 | 体积 |
|---|---|
| `java.base, java.desktop, java.sql, jdk.httpserver, java.xml, java.logging` | **49.9 MB**（51,104 KB） |
| 同上去掉 `java.desktop` | **35.8 MB**（36,656 KB） |
| **差异** | **省下 14.1 MB** |

两套都用 `--strip-debug --no-header-files --no-man-pages --compress=2`。

**`java.desktop` 现在只为一个用途存在**：`ServeCommand.java:118` 用
`GraphicsEnvironment.isHeadless()` 判断能否自动开浏览器，`ServeCommand.java:8` 用
`java.awt.Desktop` 打开它。改成 `ProcessBuilder` 调 `open`（macOS）/ `rundll32 url.dll,FileProtocolHandler`（Windows）
即可完全去掉，**这是一个独立的 14.1 MB，与 NER 无关**，优先级可以排在 M3 前面做。

### 2.2 体积总账（M3-1c 打包实测后的修正）

> 下面这组数字**替换**了本文件初稿里「模型只有 32.7MB 上限」那个估算。
> 初稿漏了两件事：没有真正打一次包，以及**只排除了 macOS 的 dSYM、漏了 Windows 的 PDB**。

`mvn package` 的实测结果：

| 项 | 初稿估算 | **实测** |
|---|---|---|
| fat jar（M2，无 ORT） | 6.01 MB | 6.01 MB ✓ |
| fat jar（M3-1c，含 ORT 双平台 native，**未 strip**） | — | **16.93 MiB**（17,757,154 B） |

**打包时踩到的坑（这一条值 290MB）**：

```
ai/onnxruntime/native/win-x64/onnxruntime.pdb        304,648,192 B
```

ORT 的 jar 里带着 **Windows 调试符号，单个 290MB**。M3-0 只处理过 macOS 的
`*.dSYM/**`（当时就记下「dSYM 里的文件名是 libonnxruntime.dylib，按后缀排除会漏」），
**却没有对称地想到 Windows 侧还有 PDB**。结果是 fat jar 第一次打成 **76.47 MiB**，
补上 `<exclude>**/*.pdb</exclude>` 后降到 **16.93 MiB**。

> 推论：**调试符号的排除规则在每个平台上都不同**，
> 必须按平台各写一条，不能因为处理过一个平台就以为处理完了。

最终的体积账：

| 项 | 体积 |
|---|---|
| fat jar（含双平台 native，未 strip） | 16.93 MiB |
| jlink 运行时（无 `java.desktop`） | 35.8 MB |
| 模型（1.9M 参数 fp32，规划值） | ~7.5 MB |
| **合计** | **≈ 60 MB** |

**90 MB 预算下约有 30 MB 余量**，比初稿估计的宽裕得多。
余量的用途已经想好：留给 M3-4 里 strip 后的余量、模型变大、以及安装器本身。
**注意：模型 7.5MB 仍是规划值，不是实测。**

> jar 里的 native 是**未剥离**的（dylib 25.5MB 未 strip / 15.5MB strip，dll 同理）。
> strip 放在 M3-4 的打包脚本里做，**不放进 pom**——`strip` 是平台相关工具，
> Windows 构建机上没有它。
>
> jar 里同时带 osx-aarch64 与 win-x64 两套 native，由 ORT 运行时按平台自己挑，
> 不需要按平台出两个 jar。

## 3. 已验证：现成预训练模型为什么全部出局

HuggingFace 检索（2026-10-16，token-classification + zh，按下载量），
文件体积取各仓库最大的 `.safetensors`/`.bin`/`.onnx`：

| 模型 | 权重体积 | 许可 | 结论 |
|---|---|---|---|
| `segment-any-text/sat-1l-sm` | 399.4 MB | MIT | 超 12 倍，出局 |
| `segment-any-text/sat-3l-sm` | 428.4 MB | MIT | 超 13 倍，出局 |
| `segment-any-text/sat-6l-sm` | 471.8 MB | MIT | 出局 |
| `segment-any-text/sat-12l-sm` | 558.6 MB | MIT | 出局 |
| `hfl/rbt3`（RoBERTa 3 层） | 149.1 MB | Apache-2.0 | 超 4.5 倍，出局 |
| `hfl/rbt6` | 230.3 MB | Apache-2.0 | 出局 |
| `uer/roberta-base-finetuned-cluener2020-chinese` | 388.0 MB | 无许可标签 | 出局 |
| `uer/chinese_roberta_L-2_H-128` | 12.2 MB | 无许可标签 | **塞得下**，但见下 |
| `uer/chinese_roberta_L-4_H-512` | 91.5 MB | 无许可标签 | 出局 |
| `ckiplab/albert-base-chinese-ner` | 38.2 MB | **GPL-3.0** | 超预算 **且** 传染性许可，出局 |
| `ckiplab/albert-tiny-chinese-ner` | 15.3 MB | **GPL-3.0** | 塞得下，**但 GPL-3.0 是硬伤** |

**两个「塞得下」的都不可用**：

- `ckiplab/albert-tiny-chinese-ner`：GPL-3.0 是**传染性**许可证。权重用 GPL 打包进一个
  要分发的桌面工具，会把整个分发物的许可状态染上 GPL。这属于**必须由用户拍板的法务问题**，
  不是我能自行决定的；当前按「不可用」处理。
- `uer/chinese_roberta_L-2_H-128`：它是**通用编码器**，没有 NER 微调，
  要用仍需自己训练（不如直接训小的）；且仓库无许可标签，分发有风险。

> 顺带排除整个 SAT 系列的原因值得记一笔：它的 `model.onnx` 虽然「有 ONNX」，
> 但 400 MB 起，**「已提供 ONNX」不等于「能塞进预算」**。选型时不能只看格式，
> 要看体积档位。

## 4. 架构选型（计划）

在 850 万参数 / 24 MB 的天花板下，候选只有三类：

| 方案 | 参数量 | fp32 体积 | CPU 推理 | 评价 |
|---|---|---|---|---|
| 字符级 IDCNN + CRF（空洞卷积） | ~2M | **~8 MB** | **快**（卷积可并行，比 LSTM 适合 CPU） | **选定** |
| 字符级 BiLSTM-CRF | ~4M | ~16 MB | 慢（循环依赖，难并行） | 备选，体积翻倍换不到更好效果 |
| 微调小型 Transformer（ALBERT-tiny 类） | ~4M | ~15 MB | 中 | 需许可干净的预训练权重，当前无合适来源 |

**IDCNN**（Jiang et al., 2019，*Fast, Accurate, and Simple Models for Chinese NER
using Dilated Convolutions*）是中文 NER 的经典强基线：MSRA 上 F1 约 95，
参数量却只有 BERT 的 1/50。空洞卷积让每层感受野指数增长，弥补了「层数少」的短板。

拟定的规模（**待训练后校正**）：

```
字符表      约 8,000（训练集中出现 ≥5 次的字符，其余归 UNK）
嵌入层      8000 × 100      = 0.80 M
空洞卷积    4 层 × (300×300×3) = 1.08 M
输出层      600 × 7         = 0.004 M
CRF 转移    7 × 7           = 0.00005 M
                              ─────────
                              ≈ 1.9 M 参数 ≈ 7.5 MB fp32
```

**标签集只有 7 个**：`O / B-PER / I-PER / B-ORG / I-ORG / B-LOC / I-LOC`
—— 这正是 M3-1a 的 `TagScheme` 和 Viterbi 解码器要处理的空间，无需改动。

> **一条尚未验证的前提**：上表的 F1 预期引自文献，不是本项目实测。
> M3-3 的验收才是真正的判据。
> ~~**若实测达不到 0.9，先考虑加宽/加深，而不是放宽验收线。**~~
> **2026-10-18 更新**：这条已按实测执行过——加宽**成功**（256→384，附集 +0.0785），
> 加深**失败**（RF 31→63，三外部集同向退化），详见 `M3-3-阶段状态.md` §1.13 与 §1.16。
> 仍不够之后，验收线由需求方下调为**主集 0.84 / 附集 0.70**，
> 见 `docs/精度验收标准.md`。**下调的是数字，不是提示**：
> 「人名会漏、必须人工复核」的产品约束不随验收线一起放宽。

## 5. 为什么训练脚本必须能在别的机器上复现（计划）

本机 Python 环境（**本轮实测**）：

- `python3` = 3.9.6（系统自带），**numpy / torch / transformers / onnx / onnxruntime 全部缺失**
- 另有 `python3.11` (3.11.14)、`python3.12` (3.12.12)、`python3.13` (3.13.12) 可用
- 网络可用（pypi=200，hf=200）
- 磁盘余量 21 GiB

因此：
- 训练环境建在 `../work/venv-train`（python3.12），**不进项目目录、不进版本库**
- 仓库只提交：**训练脚本 + 依赖锁定文件 + 导出脚本 + 推理代码 + 最终权重**
- 换机器时 `pip install -r requirements-lock.txt` 应得到同一套环境
- **权重文件不进 git**（7.5 MB 二进制，且是可再生产物），只提交其 SHA-256

## 6. 已知缺口（本节为「未验证 / 计划」，不得当作已完成）

1. **Windows 侧体积完全未测**。ORT 1.20.0 的 win-x64 native 大小、
   Windows 下的 jlink 运行时体积、最终安装包大小，都必须在 Windows 机器上实测。
   M4 打包前这是**阻塞项**。当前所有数字均为 macOS arm64。
2. **32.7 MB 预算未扣除安装器与杂项**。故实际模型目标定为 ≤24 MB，但余量 8 MB
   本身也只是估算，不是实测。
3. **IDCNN 的 F1 未实测**。§4 表格里的数字来自文献，不是本项目测量结果。
4. **`ckiplab/albert-tiny-chinese-ner` 的许可需要用户确认**。本轮按 GPL-3.0 不可用处理。
   如果用户确认可接受 GPL-3.0，这个 15.3 MB 的现成模型是一个**免训练**的备选路径，
   能把 M3-3 的风险从「训不出 0.9」降到「验证已有模型的精度」。
5. **训练从未跑过**。§4 的规模是按公式估的，实际训练后可能需要调整嵌入维度/卷积宽度。
6. **数据集未下载**。计划用 `RICAR03/cluener2020`（10k 句，标注干净）
   与 `levow/msra_ner`（约 50k 句，标注更接近法律文书），二者在 HF 上均可取。
