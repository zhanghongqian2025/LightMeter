# M3 选型与体积实测

> 结论先行：**ONNX Runtime 要用，但必须钉在 1.20.0 附近的旧版本，并从 jar 里抽出单平台 native 后 strip。**
> 用最新版（1.31.0）会把 macOS arm64 单个平台就推到 **27.9MB**，直接吃掉 L2 全部预算。
>
> 本文件的每个数字都是本机实测，不是查文档抄来的。测量方法写在 §2，**可以复现**。

---

## 1. 为什么先量体积，而不是先选版本

M3 的约束不是「能不能跑起来」，而是「跑起来之后还装得下」。
M2 收口后已知的账：

| 项 | 实测 | 预算 |
|---|---|---|
| fat jar（含 PDFBox + Jackson + 前端资源） | **6,299,475 B（6.01 MiB）** | L0/L1 应用部分 |
| jlink 定制运行时 | 未构建 | 45MB |
| **L0+L1 小计** | | **≈ 51MB** |
| 硬指标 | | 全量 ≤ 90MB |
| **留给 L2 的全部空间** | | **≈ 39MB** |

> 上表是 **M2 收口当时**的账，留作选型时的推理依据。
> 2026-10-22 重测：fat jar **13,555,997 B = 12.93 MiB**，
> L0+L1+L2 = **75.60 MiB / 余量 14.40 MiB**（见 `docs/M3-4-阶段状态.md`）。

39MB 要装下「推理运行时 + 模型 + 分词器」。
所以第一个要回答的问题不是「哪个模型最准」，而是**「运行时本身要吃掉多少」**。

## 2. ONNX Runtime 体积实测

### 2.1 最新版 jar 里装了什么

`com.microsoft.onnxruntime:onnxruntime:1.31.0` = **50,942,147 B**。
解压后按平台统计（未压缩）：

| 平台 | 文件 | 大小 |
|---|---|---|
| osx-aarch64 | `libonnxruntime.dylib` | 44,797,256 B |
| osx-aarch64 | **`libonnxruntime.dylib.dSYM/…/DWARF/libonnxruntime.dylib`** | **55,362,207 B** |
| linux-x64 | `libonnxruntime.so` | 29,345,384 B |
| linux-aarch64 | `libonnxruntime.so` | 25,266,408 B |
| win-x64 | `onnxruntime.dll` | 17,253,176 B |
| 各平台 JNI 桥接库 | — | 约 0.1MB/平台 |

**两个可以直接省掉的东西：**

1. **dSYM 是 52.8 MiB 的 DWARF 调试符号**，打包时必须整条排除。
   注意它的文件名以 `.dylib` 结尾——按后缀排除原生库会漏掉它，
   得按目录名 `*.dSYM/*` 排除。
2. **全平台原生库是重复的**。我们只跑一个平台，其余三个是纯浪费。

### 2.2 strip 前后的差距（macOS arm64，`libonnxruntime.dylib`）

| ORT 版本 | 未 strip | strip 后（`strip -S -x` 再 `strip -x`） |
|---|---|---|
| 1.16.0 | 21,463,704 B | **13,870,840 B（13.2 MB）** |
| 1.17.3 | — | **15,226,952 B（14.5 MB）** |
| 1.18.0 | — | **16,344,504 B（15.5 MB）** |
| 1.19.2 | — | **17,144,440 B（16.3 MB）** |
| **1.20.0** | 25,477,000 B | **16,308,584 B（15.5 MB）** |
| 1.31.0 | 44,797,256 B（42.7 MB） | **29,250,624 B（27.9 MB）** |

**strip 砍掉 30%~35%**，是纯符号表——本机不调试 native，跑的时候用不到。
但即便 strip 过，1.31.0 的 27.9MB 也只剩 **11MB** 给模型，
而一个 INT8 的中文 NER 模型低于 11MB 基本不可能达到 F1 ≥ 0.9。

**注意 1.19.2 → 1.20.0 是**降**的**（16.3MB → 15.5MB）**。
所以在这两个版本之间不存在「保体积就得牺牲新」或反之的取舍**——
1.20.0 同时更新且更小，这一格的取舍是不成立的。

### 2.3 复现方法

```bash
curl -sL -o ort.jar \
  https://repo1.maven.org/maven2/com/microsoft/onnxruntime/onnxruntime/1.20.0/onnxruntime-1.20.0.jar
W=$(mktemp -d); cd "$W"
unzip -q /tmp/ort.jar "ai/onnxruntime/native/osx-aarch64/libonnxruntime.dylib" -x "*dSYM*"
cp ai/onnxruntime/native/osx-aarch64/libonnxruntime.dylib s.dylib
strip -S -x s.dylib; strip -x s.dylib; stat -f%z s.dylib
```

> 记录一下：这个测量第一次跑的时候用了 `rm -rf ortx`，被网关按「危险删除目标」拦了——
> 相对路径 `rm -rf` 一律走 mavis-trash。改用 `mktemp -d` 建工作目录就没这个问题。

## 3. 定版：1.20.0

| 候选 | 结论 |
|---|---|
| 1.31.0（最新） | ❌ 27.9MB 单平台，L2 装不下 |
| 1.16.0 | ⚠️ 体积最优，但最老，且已含已知 CVE（见 §3.1） |
| 1.17.3 / 1.18.0 / 1.19.2 | ⚠️ 14.5~16.3MB，比 1.20.0 更老或更大，没有一格占优 |
| **1.20.0** | ✅ **15.5MB，且比 1.18/1.19 都更小——版本与体积不冲突** |

**给模型留的空间：90 − 51 − 15.5 ≈ 23.5MB。**
按 INT8 算，这是 2300 万参数——足以放一个 4 层、hidden 384 的蒸馏中文编码器，
或者一个 hidden 256 的 BiLSTM-CRF。

### 3.1 已知 CVE 核实（已完成，结论是「不可达 + 一处残留未知」）

**先说工具层面的一个坑**：自动数据源对 onnxruntime **没有逐包记录**。

| 数据源 | 查询 | 结果 |
|---|---|---|
| OSV | Maven / PyPI × 1.16.0 / 1.17.3 / 1.20.0 / 1.22.0 | 全部 0 条 |
| OSV 对照组 | `log4j-core:2.14.1` | **命中 7 条**（证明查询机制没坏） |
| GitHub Advisory | `affects=onnxruntime` | 0 条；且 `ecosystem=Maven` 该端点根本不支持 |

**所以「0 条」只能写成「查不到」，不能写成「没有漏洞」。**
这正是本项目质量红线第 6 条要求区分的那两种状态。

改用检索后，拿到了实际记录。结论分两层：

**第一层：命中的 CVE 绝大多数在 Python 的 `onnx` 包里，对我们不可达。**

| CVE | 问题 | 所在包 | 我们是否受影响 |
|---|---|---|---|
| CVE-2024-5187 | `download_model_with_test_data` tar 路径穿越 | `onnx`（Python） | ❌ 无该函数 |
| CVE-2024-7776 | `download_model` tar 路径穿越 | `onnx`（Python） | ❌ 无该函数 |
| CVE-2025-51480 | `external_data_helper.save_external_data` 任意文件写 | `onnx`（Python） | ❌ 我们不导出模型 |
| CVE-2026-28500 | `onnx.hub.load(silent=True)` 信任校验绕过 | `onnx`（Python） | ❌ 我们不从 hub 拉模型 |
| CVE-2026-34445/34446/34447 | 外部数据的 symlink / hardlink 遍历 | `onnx`（Python `external_data_helper`） | ❌ 同上 |

这些都是 Python 侧的下载与导出辅助函数。Java 应用**不包含也不调用**它们。

**第二层：一处残留未知，必须在实现里正面挡掉。**

上述 CVE-2026-34447 等一组指向**外部数据文件**（模型把权重存在 .onnx 之外时才会用到）。
我们无法从检索结果确认 C++ 运行时自身的模型加载器在 1.20.0 上是否也有同类问题。

**处理办法不是等厂商发版，而是从设计上让它无从发生：**

1. 模型一律是**自包含单文件 .onnx**，不使用 external data；
2. 加载前**主动检查模型是否引用外部数据文件**，引用了就拒绝加载并报错——
   理由与「不跨 TextObject 合并 OFD 文本」同源：一个我们用不到的机制，
   不给它存在的余地；
3. 模型包解压沿用 M1-f 已有的 zip 加固（路径穿越、条目数上限、炸弹预算）。

**版本下限因此定在 ≥ 1.17.0**（`onnx` 的 tar 路径穿越修复版本），
1.20.0 满足。**未动 `pom.xml`**，等 M3-1 实现与测试同时落地。

## 4. 另一个被排除的选项：不用 ORT，纯 Java 推理

认真评估过，因为它的体积优势极大（省掉整个 15.5MB）。

| 维度 | ORT 1.20.0 | 纯 Java 手写推理 |
|---|---|---|
| 体积 | 15.5MB | ~0 |
| 需要支持的算子 | 全部由 ORT 提供 | 自己实现 matmul/conv/LSTM/Viterbi |
| 训练侧 | 必须有 Python + torch 环境 | 同样需要 |
| **测试标尺独立性** | 天然独立（另一个实现） | **需要另想办法** |

**没选纯 Java 的原因不是体积，是测试标尺。**
质量红线第 4 条要求「测试标尺必须独立于被测实现」。
自己写的推理代码如果用自己写的算子做标尺，
「模型推理结果对不对」这件事就只能靠人眼看，
而人眼看不出 0.001 和 0.003 的差别。

用 ORT 反而自然满足这一条：**Java 侧只负责切窗、分词、解码，
逐点 logit 由 ORT 给出**，标尺是 PyTorch 导出的固定数值，两边独立。

而且省下的 15.5MB 换不来更多能力——模型再大也到不了 0.9 以上，
而 ORT 带来的标尺独立性是**买不到**的。

## 5. 训练与数据侧的现实约束

### 5.1 本机没有任何 ML 工具链

```
python3 -V            → Python 3.9.6（系统自带）
numpy                 → 缺
torch                 → 缺
transformers / onnx   → 缺
onnxruntime           → 缺
```

系统 Python 不能直接装包（会破坏 OS 自带工具链）。
**必须建独立 venv**，且 torch 对 Python 3.9 的支持在新版本里已停止，
需要锁定一个较老的 torch 版本。

> 这一条直接影响排期：训练与蒸馏脚本要能在**另一台机器**上复现，
> 所以必须写清依赖锁定文件，而不是「我本地跑通了」。

### 5.2 数据集可用

| 数据集 | HuggingFace ID | 规模 | 实体 |
|---|---|---|---|
| MSRA-NER | `levow/msra_ner` | 约 25k 句 | 人名 / 机构名 / 地名 |
| CLUENER2020 | `RICAR03/cluener2020` | 约 10k 句 | 人名 / 机构名 / 地名 / 职业 |

**只要人名与机构名**，LOC 可以直接丢掉（正则已经在处理地名类标识符，
而且误报代价比漏报还高）。两个数据集标注规范不同，**不能直接拼接**——
必须先统一到一套 BIO 规范再做混合训练，否则标注冲突会把 F1 拉低几个点。

### 5.3 验收样本必须自己标

路线图要求「200 条人工标注样本 F1 ≥ 0.9」。
这 200 条必须**从公开数据集之外另取**，理由是：
用数据集自带的划分做验收，等于拿训练材料考自己。

## 7. M3 已知风险

1. **没有 GPU，也没有训练环境**。蒸馏与量化脚本要在别的机器上跑，
   本仓库只提交**权重 + 推理代码 + 可复现的训练脚本**，不提交训练产物中间态。
2. **F1 ≥ 0.9 对「人名」可达、对「机构名」偏乐观**。
   机构名边界模糊（「北京市朝阳区人民法院」算不算机构名、含不含地域），
   标注规范不统一时同一段文本能算出两个答案。
   **M3-3 若达不到，如实报达不到的数字并说明原因，不放宽验收标准。**
3. **分词方式**：中文没有空格，字符级切分最稳且与模型无关。
   但字符级模型遇到未登录生僻字只能退化成 UNK，机构名里恰恰爱出现生僻字。
4. **长文本切窗的边界实体**：跨窗口的机构名会被切断。
   解法是重叠窗口 + 边界投票，**必须单独测**，否则表现为「偶尔少识别一个」。

**已完成（实测）**

- ORT 各版本在 macOS arm64 的真实体积（1.16 / 1.17.3 / 1.20 / 1.31）；
- 1.31.0 jar 的平台构成与 dSYM 占比；

- 本机 Python 环境与可用数据集；

- §3.1 的 CVE 核实（自动数据源无记录 → 改检索 → 分类可达性 → 定版本下限 1.17.0）。

**未完成**

- 模型结构与参数量定档；
- M3-1 的推理层实现。

**未写入依赖**：本轮没有动 `pom.xml`。
