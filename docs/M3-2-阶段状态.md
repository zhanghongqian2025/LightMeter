# M3-2 阶段状态：模型包加载器 + 接线（方案 B 的分发侧）

## 一、结论

方案 B 要求「核心包 + AI 模型包分离」。核心包不含模型（模型 7MB、还要随版本更新），
模型包是独立分发/导入的产物——**于是模型包就是一个不受信任的输入**，
和「用户拖进来的那个 docx」同一级别。

本阶段分两段做完：

- **M3-2a 加载侧**：`NerModelPackage` 把一个目录变成可用的 `NerRecognizer`，
  中间**七道闸**，任何一道不过就拒绝加载，绝不「尽量兼容地放行」。
- **M3-2b 接线侧**：`NerModelRegistry` 负责「找到模型包 / 找没找到 / 找到了但坏了」，
  `DocumentService` / `JobStore` / `ApiHandlers` / `Main` / `ServeCommand` 全链路透传，
  **NER 在 CLI 与服务端两条路径上都真的生效**。

## 二、七道闸

| 闸 | 挡什么 | 不挡会怎样 |
|---|---|---|
| 1 格式版本 | `formatVersion != 2` | 跨版本字段语义可能变，「尽力解析」出来的结果是静默错脱 |
| 2 路径必须是包内普通文件名 | 绝对路径、`..`、分隔符、NUL、符号链接 | zip-slip 同类入口：清单让工具去读包外的文件 |
| 3 SHA-256 | 下载到一半 / 包被替换 | 三件事在现象上都是「加载成功但结果离谱」 |
| 4 词表严格解析 | 空行、重复字符 | 见下面第五节，本项目真实踩过 |
| 5 模型自包含 | `external_data` / `data_location=EXTERNAL` | ORT 会照着路径去打开本机文件 |
| 6 **嵌入行数对账** | `ONNX 嵌入行数 ≠ 词表字数 + 1` | 每个字符的 id 整体错位一格，**零报错** |
| 7 窗口契约 | `overlap < maxEntityChars` | 跨窗口的实体「完整包含」与「不贴切边」同时不成立，整个消失且不报错 |

第 6 道是本阶段的核心。它需要读 ONNX 图里初始化张量的形状，
为此新增了 `OnnxTensorShapes`——按 protobuf 线格式走
`ModelProto.graph(7) → GraphProto.initializer(5) → TensorProto.dims(1)`，
**packed 与非 packed 两种编码都支持**（protobuf 对 repeated 标量两种都合法，
只认一种的话换个导出器就会读到空维度，而空维度在下游表现为「行数对不上」，
错误信息会指向完全错误的地方）。

## 三、清单格式从 v1 升到 v2

v1 只有训练元信息，**Java 侧无法安全加载**：张量名不能猜（不同导出器给的名字不一样），
摘要不能省（省了就分不清「下载坏了」与「模型本来就长这样」）。

新增字段：

```json
{
  "formatVersion": 2,
  "tags": ["O", "B-PER", "I-PER", "B-ORG", "I-ORG"],
  "tagTypes": { "PER": "person", "ORG": "organization" },
  "window": { "chars": 256, "overlap": 64 },
  "io": { "input": "ids", "emission": "emission", "transition": "transition" },
  "embeddingTensor": "emb.weight",
  "files": {
    "model": { "path": "ner.onnx", "sha256": "…" },
    "vocab": { "path": "vocab.txt", "sha256": "…" }
  }
}
```

`tools/manifest_upgrade.py` 可以把已训好的包原地升级，**不必重训 40 分钟**。

### 3.1 `tagTypes` 为什么必须在清单里

模型用的是数据集惯例（`B-PER` / `B-ORG`），而写进还原映射与排除键的是稳定码
（`person` / `organization`）。两者不是同一套命名，必须显式映射。

早先加载器直接拿标签后缀去查 `EntityType`，对着真实模型包报「不认识 PER」——
那说明模型包与代码各说各话，**不能靠猜后缀来和稀泥**。

映射放在清单里、而白名单留在代码里（`EntityType.byCode`），
于是「一个来路不明的模型包能变成哪条脱敏规则」必须过白名单：
清单可以声明 `PER → person`，但不能声明 `PER → bankcard`。

### 3.2 `-1e4` 必须还原成「不可能」

训练侧的 CRF 屏蔽值是 `-inf`，导出成 ONNX 时换成 `-1e4`（`-inf` 会被某些后端算成 NaN）。
加载侧**必须还原**，否则 `SequenceDecoder` 那条
「全路径 `-Infinity` 就报错」的安全网会被绕过——全是有限的 `-1e4`，`isInfinite` 不触发，
于是模型包配错时不报错，而是编出一条结构非法的路径。那就是**静默错脱**。

还原做两道，都必要：结构上非法的直接置 `IMPOSSIBLE`（精确，不依赖阈值）；
分数 ≤ `-1e4` 的也置 `IMPOSSIBLE`（把训练侧的 `-inf` 语义还原回来）。

## 四、为什么用 `FAIL_ON_UNKNOWN_PROPERTIES`

清单里出现本版本不认识的字段 = 多半是拼错了字段名。实测第一次跑就撞上了：
清单里的 `arch` 没在 record 里声明，直接报错并点名。

放宽成忽略未知字段的话，`"maxEntityChar"` 这种少个 s 的拼写会被静默接受，
然后以一条完全对不上原因的消息炸掉——**错误信息会指向错误的地方**。

同理 `arch` / `entityTypes` / `provenance` 这些「本类不据此改变行为」的字段也要求存在。

## 五、第 4 道闸的来历：一次真实的静默故障

名单式语料合成把换行符带进字符表 → `vocab.txt` 写出一个空行 → 加载端**跳过**空行
→ 4586 个字只加载回 4585 个 → **每个字符的 id 从那行起整体错位一格**。

现场：

- 训练日志打印 F1 **0.8397**（用的是内存里那份正确的词表）；
- 拿导出的 `.onnx` + `vocab.txt` 重新打分只有 **0.1209**；
- 没有异常、没有报错、形状检查全过——**两个文件各自都合法，合起来才不合法**。

三条修法，本阶段全部落到加载侧：

1. 词表**空行直接拒绝**，不跳过。跳过这个动作本身就是在把错误藏起来。
2. `rowsOf` 找不到张量时返回 `-1` 而不是 `0`——「没有这个张量」与「这个张量是 0 行」是两件事。
3. 第 6 道闸把两个文件**合起来**对账。

**训练侧的数字不能代表产物**，只有一条「只读产物」的独立路径能发现这类错位。
现在这条路径有两个：Python 侧导出时的 `_assert_export_consistent`，
以及 Java 侧加载时的行数对账——后者才是真正消费产物的那一端。

## 六、六条新变异

| 编号 | 变异 | 撤掉后的症状 |
|---|---|---|
| Ⓔ | 撤掉模型与词表的行数对账 | 词表与模型不配套的包被正常加载，id 错位一格 |
| Ⓕ | 撤掉**整簇**路径安全检查 | 清单指向 `../ner.onnx` 时被放行 |
| Ⓖ | 词表空行改成跳过而不是拒绝 | 复现 v3 的 id 错位 |
| Ⓗ | 摘要校验改成永远通过 | 传输损坏 / 包被替换检测不出来 |
| Ⓘ | `-1e4` 不还原成「不可能」 | `SequenceDecoder` 的全路径 -inf 安全网被绕过 |
| Ⓙ | `tagTypes` 不查 `EntityType` 白名单 | 模型包可自造脱敏规则 |

### 6.1 Ⓕ 第一版拿到 GREEN，成因是纵深防御而非测试不敏感

第一版只撤了「含路径分隔符就拒」那一条，结果 **GREEN**。

判别之后确认**不是空操作变异**：`resolveInside` 里还有两道重叠检查——
`"." / ".."` 直接拒，以及 `resolve` 之后拿 `normalize().getParent()` 与包目录比对。
后一道把前一道之外的所有穿越形态都挡住了，所以撤掉单条仍然红不了。

**单点变异在这里证明不了任何东西**，改成复合变异：三道一起撤。
复合变异的附带好处是三道都写进了脚本，将来删掉任何一道都看得见。

顺带补上了测试的覆盖缺口——两个只有被撤掉那道才能挡住的输入：

- 含 NUL 的文件名：`Path.resolve` 会抛 `InvalidPathException`，
  那是个与「模型包不合法」完全无关的异常类型，调用方分不出来；
- `"..\\ner.onnx"`：在 Unix 上反斜杠是**合法文件名字符**，不构成穿越，
  但在 Windows 上就是上级目录。两个平台行为不同，必须在换平台之前就钉住。

## 八、M3-2b：接线（NER 已真实生效）

### 8.1 三种「找不到模型」必须分开

`NerModelRegistry` 的查找顺序：`--ner-model` > 环境变量 `LITEMASK_NER_MODEL` >
`<程序目录>/models/ner` > `~/.litemask/models/ner`。

关键在于**两种「没有」不是一回事**：

| 情况 | 行为 | 为什么 |
|---|---|---|
| 根本没装模型包 | 安静降级，`describe()` 如实报「未安装」 | 没装是正常状态，不该报错，更不该拖慢启动 |
| 指到了一个目录但加载失败 | **抛错**，不降级 | 「我指名要这个包，它坏了」必须说；悄悄用正则跑一遍等于交付一份没脱干净的文档 |

`describe()` 的输出直接打到服务端启动日志上，所以「这份输出到底脱没脱人名」
在启动那一刻就能看见，而不是等用户传完文件才发现。

### 8.2 「0 处命中」在数字上与「文档干净」一样

这是本阶段最要紧的一条。NER 没启用时，`DocumentService` 的 notes 里会**明写**
「中文人名与机构名没有被脱敏」——因为 `张三` 原样留在文件里时，
扫描结果与「这个文档确实没有人名」是完全一样的两个结果。

不为这件事单设一句话，用户就只能靠「文件里还有没有张三」来判断有没有脱干净，
而这恰恰是他最不该依赖的信号（一个真叫张三的人名也可能漏检）。

### 8.3 决定性验证（真实 jar + 真实 v3 模型）

样本：`原告张三与被告北京星辰贸易有限公司签订合同，联系电话13800138000。`

| | 无模型 | 带 `--ner-model work/ner-model-v3` |
|---|---|---|
| 输出正文 | `张三` / `北京星辰贸易有限公司` 原样保留 | `<人名1>` / `<机构名1>` / `<人名2>` / `<手机号1>` |
| 终端提示 | 明说「中文人名与机构名没有被脱敏」 | 不再出现该提示 |
| 映射文件 | 仅 `<手机号1>` | 四个令牌齐备 |
| 用映射还原后 | — | **与原文逐字节一致** |

最后一行是这一段真正的验收点：令牌分对了但还原不回去，
比脱错了更难被发现——因为用户看到的是一份「看起来脱敏过」的文件。

### 8.4 JobStore 的 sources 由构造方注入

`JobStore` 的 `sources` 在**构造时**定好并 `List.copyOf`，不在 `scan()` 里读全局单例。
理由有两个：其一，「这次用了哪个模型」必须能从参数看出来，
否则同一份代码既可能接上又可能没接上；其二，测试没法固定一个全局单例，
`JobStoreNerWiringTest` 里那条假 `EntitySource` 就没法注入。

`ServeCommand` 同理：**启动时确定一次模型并保持**，不每请求重新发现——
既慢（每次都要查目录、读清单、算 SHA-256），也让同一个会话里前后两次请求的
脱敏结果可能不一致，而用户没有任何办法察觉。

### 8.5 服务端路径的测试为什么放在 `com.litemask.server` 包下

`JobStore.Job.scan` 是包内可见字段，而断言「服务端路径上人名确实被脱了」
又必须直接读它。绕道 HTTP 层去测会把两件事混成一个：
「JobStore 没接上 sources」与「路由没把 sources 转发过去」。

因此 `JobStoreNerWiringTest` 直接构造 `Workspace` + `JobStore` 调 `scan`，
并且**读回预览件的实际字节**断言「张三 已不在、`<人名1>` 在」——
映射表里有令牌不排除文件里还留着原文，那是两种不同的故障。

它用的 `EntitySource` 是一个**恒真的假实现**（在「张三」位置硬造一个命中），
与模型版本完全解耦：模型换版本时它不会红，
而「JobStore 把 sources 吃掉了」它一定会红。

## 九、本轮修掉的真实缺陷

1. **`OnnxRunner.readConstantOutput` 名字不存在时抛 NPE**。
   原写法直接 `.get(name)` 之后读 `m.length`，现场读起来像「模型包内部坏了」，
   而实际只是清单里写了一个模型没有的输出名。已改成抛 `OrtException` 并列出模型实际有的输出名。

2. **`FileRef` 之外又定义了 `Files` record**，与 `java.nio.file.Files` 撞名。
   于是同一个类里 `Files f = …` 与 `Files.readAllBytes(…)` 并存，
   编译期要靠 import 顺序决定谁是谁——改一个 import 就换一个含义。已改名 `FileSet`。

3. **`JobStoreNerWiringTest` 把 clientId 当文件名传**（本轮）。
   `scan(String clientName, byte[] body)` 的第一个参数是**客户端报来的文件名**，
   测试传了 `"test-client"`（无后缀）→ `BadRequest: 无法识别文件类型`。
   顺带把 helper 从「返回 Path」改成「返回字节」：
   返回 `Path` 时它能被顺手传进 `scan()`，而后缀判定照样能过（`plain.txt` 有后缀），
   于是参数位置的错误被掩盖——只是把无后缀换成有后缀而已。

4. **对照实验脚本的收尾只判 `fail`、不判 `invalid`**（本轮）。
   「4 条里 2 过 2 作废」与「4 条里 2 过 2 真挂」在 `pass`/`fail` 两个数字上完全一样，
   而结论正相反：前者说明变异体编译不过、测试压根没跑，那两条实验**没提供任何信息**。
   原来会判整场绿。现在 `invalid` 与 `fail` 同样致命。

5. **锚点未命中只记 `fail` 不记 `invalid`**（本轮）。
   脚本在 MISSING 时打印的是「实验无效」，计数却只加 `fail`——
   于是全量跑出来是 `fail=5 invalid=0`，读起来像「有 5 条测试咬不住」，
   实际是「有 5 条实验压根没跑」。**规则写在注释里，代码里没落实**——
   这是本轮最值得记的一条：把规则写进文档不等于把规则实现进代码。

6. **5 条锚点漂移**（本轮）：⑩ ⒒ ⒙ ⒠ ⒡。成因分三类：

   | 重构动作 | 症状 | 修法 |
   |---|---|---|
   | 给被变异函数**加参数**（3 参 → 4 参，`sources` 接进 `RedactionSession` 与五个 redactor） | 整行锚点不再存在 | 换锚点；⑩ 的 `run_case_multi` 要退回 `run_case` |
   | `if (a && b) {` 被**折成两行**（行宽限制） | 一行锚点命中不了 | 锚点写成两行字面量（⒠） |
   | **抽公共类**（protobuf 游标搬到 `ProtoWire`） | 逻辑不在原文件了 | 加 `PROTOWIRE` 变量，锚点指向新文件（⒡） |

   修锚点时踩到第二个坑：⒒ 的替换值先写成 `java.util.List.of()`，
   而第三参类型是 `Exclusions`（record）——**变异体编译失败**，被判 INVALID。
   换成 `Exclusions.NONE` 才对。这正是区分 INVALID 的机制救了一次场：
   不区分的话这次会被当成「测试咬住了」，等于自证。

   另外 `mutate()` 现在在未命中时打印**文件里最相近的一行**（按锚点首行与各行的
   字符重合度粗排）。三类漂移里「加了参数」和「折了行」光看 `MUTATION_TARGET_MISSING`
   根本猜不出该改哪里，而每条都要翻两三个文件才定位得到。

7. **「对照实验总数」这个数字从 M3-2a 起一直是错的**（本轮）。
   文档里写「99 条」，命令是 `grep -cE '^run_case'`——
   而那个正则把 `run_case() {` 与 `run_case_multi() {` 两个**函数定义行**也数了进去。
   真实条数是 **97**（92 个 `run_case` + 5 个 `run_case_multi`）。
   更糟的是它每次都被照抄到下一份文档里，没人核过。

   现在脚本收尾自己算 `declared`，并断言 `pass + fail + invalid == declared`——
   少判说明有条实验被静默跳过（`ONLY` 过滤写错、调用名打错），
   那时的 `pass=N` 是个不完整的分子。**数字应当由工具算出来，而不是抄上一轮的。**

   历史文档（M3-1f / M3-1d）里的「93 条」是当时的快照，保留不改——
   它们连同命令一起记着，改数字等于篡改记录。错的来龙去脉记在这里就够了。

## 十、已知限制 / 未验证

- **签名校验未做**。目前只有 SHA-256，它能发现「传输损坏」，
  发现不了「有人换了一份自洽的包」。清单里的摘要是**训练时算的**，
  攻击者能同时换掉模型、词表与摘要。
- **模型包来源只做了「本地目录」**。首次启用下载、离线导入、解压加固都没做——
  那需要签名与证书链，属于 M3-2c。
- **`ServeCommand` 的模型只在启动时确定**：用户在会话中途换模型目录不会生效，
  必须重启服务。这是取舍（换取同一会话内结果稳定），但界面上**没有提示这一点**。
- **接线侧没有变异**。`NerWiringTest` / `JobStoreNerWiringTest` 全是正向断言；
  「谁把 sources 吃掉了」这种回归靠正向断言抓得到（结果里就没有 `<人名1>`），
