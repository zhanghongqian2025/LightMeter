# 精度验收标准（2026-10-18 修订）

> **这是本项目唯一的精度验收权威来源。**
> 其它文档（`开发目标与路线图.md`、`M3-3-阶段状态.md`、`M3-选型与体积实测.md` 等）
> 里出现的「F1 ≥ 0.9」均为**已作废的旧标准**，以本文件为准。

## 一、决定

**把 NER 验收线从 F1 ≥ 0.9 下调为：**

| 评测集 | 旧标准 | **新标准** | 当前实测（v9，2026-10-18） | 余量 |
|---|---|---|---|---|
| 法律文书主集（0 未登录字） | 0.90 | **0.84** | **0.8479** | +0.008 |
| 法律文书附集（19 未登录字） | 0.90 | **0.70** | **0.7419** | +0.042 |

定线低于实测，是有意的：两个评测集都是模板合成的，同一模板下模型表现偏乐观；
而**单次训练没有方差估计**（只跑了一个种子），余量用来吸收这部分未知波动。

**这条决定由需求方在 2026-10-18 拍板**，不是技术推导出来的。
下面的内容是为了让这个数字可被检验，而不是为了论证它合理。

## 二、这不是「证明 0.9 做不到」

必须写清，避免日后被当成技术结论引用：

- **0.9 在当前约束下没做到，不等于做不到。**
- 已经试过并**实测排除**的手段（详见 `M3-3-阶段状态.md` §1.10 全轴表）：

| 轴 | 手段 | 结果 |
|---|---|---|
| 数据：句式骨架 | v5 新增 3 个模板 | **负**（主集 −0.03） |
| 数据：词表覆盖 | v6 扩词表 | **负**（主集 −0.048） |
| 数据：体量 | v7-a 法律语料 3 倍 | **主动停掉**（实验混淆，不可解释） |
| 架构：感受野 | 15 → 31（v7） | **正** +0.0141 |
| 架构：感受野 | 31 → 63（v8） | **负**（三外部集全跌） |
| 架构：宽度 | 256 → 384（v9） | **正**（附集 +0.0785） |

- **体积是当前的硬约束**：核心包 75.60 MiB / 预算 90 MiB，余量 14.40 MiB
  （2026-10-19 实测；剔掉 win-x64 原生库后从 10.36 MiB 涨上来的，见 M3-4）。
  按算术，宽度再上到 512 需要 +13.4 MiB——**装得下，但只剩约 1.2 MiB 缓冲**，
  缓冲太薄，不值得拿它去换一次未实测的容量收益。
- **尚未尝试、且不做就下结论是不诚实的方向**：
  1. **词表 / UNK 策略**——附集人名召回仅 0.667，19 个真实姓氏（眭、仉、訾、郗、阚…）只能落 UNK。
     这是当前最大短板，**没有任何修法被测过**。
  2. 更长训练（30 → 60 epoch）。
  3. 真实标注的法律文书（最大不确定性来源，现在两个集都是合成的）。

## 三、适用范围与不适用范围

### 适用

- **字全部落在训练词表内**的中文法律文书（常见姓氏 + 常见机构后缀）。
- 作为**批量初筛**，配合**人工复核**后使用：
  > 本工具的定位是「把 90% 的机械工作做完，把 10% 需要判断的挑出来给人看」，
  > **不是**「不需要人看就能对外发送」。
- 身份证号、手机号、银行账号、VIN 等**规则型标识符**——这部分不依赖 NER，
  走的是校验位与格式规则，可靠性显著高于人名/机构名。

### 不适用

- **对外发送前不复核。** 人名召回主集 0.800 / 附集 0.667，
  即**每 5 个人名漏 1 个，含未登录字时每 3 个漏 1 个**。
- **含大量未登录字**的文书：生僻姓氏、方言地名、机构简称、内部代号。
  这些字只能落 UNK，召回塌到 0.667。
- **自由文本 / 非法律文书**：本模型的全部法律域收益都来自法律文体，
  在其它文体上没有证据。
- **要求 100% 召回的场景**：漏检是设计内的已知行为，不是可配置项。

### 2026-10-18 实测补充：短文本 + 标识符密集的混合内容，NER 会误伤标识符

这一条不是评测集推出来的，是拿真实输入跑出来的。
对一段 3 行的混合文本（`甲方联系人 张三 电话 13800138000` / … / `身份证 …`）
跑带模型形态，命中清单实际长这样：

| 模型给出的「实体」 | 结果 |
|---|---|
| `人`、`电话`、`1`、`8000`、`乙方` | 全被判成人名 / 机构名 |
| `380013` | 手机号（前半截） |
| `13900139000` | **整串手机号被判成机构名**，手机号规则那条完全落败 |

**后果**：`13800138000` 在清单里变成 `1` + `380013` + `8000` **三条命中**，
用户看到的是「手机号被标成人名」；「排除第一个手机号」这类操作在界面上
也没有整体可排了（能排的只有那三段之一）。

**性质要说清**：
- **没有泄漏** —— 三段全都被脱敏了，往返逐字一致（实测）。
- 但**界面呈现是错的**，而且这个错会让人怀疑工具本身坏了。
- 根因是**上下文太少**：模型在 3 行短文本上几乎没有可依据的上下文。
  同一批文本拉长到法律文书体量时，F1 是 0.85（主集）——**两件事不矛盾**，
  一个是长文里的召回，一个是短文里的误伤。

**所以「不适用」里再加一条**：

- **短文本、标识符密集的混合内容**（如名单页、联系页、表格里的一行行
  「姓名 + 电话 + 证件号」）。这类内容请**关掉 NER、只用规则脱敏**，
  或者把相邻文本并进来一起处理。

## 四、强制约束（不因下调验收线而放松）

1. **README 与产品界面必须保留「人名会漏，请务必人工复核」的醒目提示。**
   下调的是数字，不是提示。
2. **映射文件必须可还原**（已实测往返逐字节无损），
   否则人工复核发现漏检后无法补救。
3. **未启用 NER 时必须明说「人名与机构名没有被脱敏」**——
   打包脚本第 4 步会强制验这一条。
4. **评测集只可因「更真实 / 更难」而修改**，且新旧数字必须并列报告。
   为让指标变绿而改评测集，属于作弊。

## 五、怎么复核这个决定还成立

| 触发条件 | 必须做的事 |
|---|---|
| 换了模型 / 改了架构 / 改了训练数据 | 重跑主集与附集，两套数字都报 |
| 拿到了真实标注法律文书 | 用真实集重测；**真实集的结果优先于本文件的任何数字** |
| 词表或 UNK 策略有改动 | 附集必须重测（它就是为量这件事造的） |
| 体积预算放宽到 100 MiB 以上 | 重新评估宽度 512（v10） |

复核命令：

```bash
JAR=target/desens-core.jar
javac -encoding UTF-8 -cp "$JAR" -d target/probe-classes tools/LegalEvalProbe.java
java -cp "target/probe-classes:$JAR" LegalEvalProbe <模型包目录> <评测集>
```

评测器走**产品路径**（磁盘模型包 → 七道闸 → ONNX Runtime → 解码 → 实体源），
标尺（BIO→span、P/R/F1）独立实现，不复用被测实现——
理由与证据见 `M3-3-阶段状态.md` §四。

### 2026-10-18 定论：一个标识符被切成多段时，**映射里没有完整原值是设计内行为**

上面那条短文本误伤的**下游后果**：一个 `a.b@x.cn` 会被拆成四段命中
（实测映射 `{"<人名1>":"邮箱","<人名3>":"a.b","<邮箱1>":"@x.","<人名4>":"cn"}`），
于是**映射里找不到完整原值**。

**这是有意的，不是缺陷。** 合并需要一个「完整原值」，而它是把不同规则各自认领的
片段拼出来的——**源文件里从未作为整体出现过**。把它写进映射，用户拿它核对源文件时
找不到这个字符串；真当审计证据用，更是拿工具编出来的原值去证明源文件里有这个值。
**代价可见（界面难看、映射没有整体）好过代价不可见（映射里有一条编造的记录）。**

配套事实：**往返仍然逐字一致**，脱敏没有泄漏任何原文片段。所以这一条属于
「呈现层缺陷」，不属于「安全性缺陷」，不进安全相关的验收线。

修法方向是**呈现**（界面上把相邻的同源命中归成一组展示），不是**映射内容**。
证据与取舍过程见 `M3-3-阶段状态.md` §1.19.8。
