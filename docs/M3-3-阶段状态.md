### 1.1 v5 是一个诚实的负结果，代码里保留了它

按中国法院文书的标准体例（送达回证、委托代理人身份信息段、立案受理段落）
又补了 3 个模板，结果**整体更差**：

- ORG 从 0.8660 涨到 0.9072（+0.041，符合预期）
- PER 从 0.8363 掉到 0.7797（−0.057）
- 主集 F1 净跌 0.030，附集从 0.6279 掉到 0.5902

原因：那三个模板句式高度固定（逗号分隔的字段行），模型学成了
「逗号分隔字段里少报人名」，连带把清单式句子里的人名召回也拉低了。

**「加法律模板」不是单调变好的。** 三个模板没有删除，移到了
`ner_legal_aug.OPTIONAL_TEMPLATES`，默认不启用，理由写在了模块注释里——
删掉它们等于把这次负结果也删掉，下一个人会重踩一遍。

### 1.2 为什么不照着评测集的错误样例去调训练集

v5 的模板是按**中国法院文书的公开体例**设计的（送达回证的身份信息行、
委托代理人段、立案受理段），不是从评测集的错误样例里抄句子。

理由是评测集一旦被用来指导训练，它就不再是留出集了：跑一轮、
看错误、加模板、再跑一轮，这个数字每涨一分都有一部分来自泄漏。

同样的纪律适用于 v6：v6 **只在既有 9 个模板内部扩充词表**
（人名角色词 29→52、机构角色词 21→40、行业后缀 20→33、填充片段 26→56，
另加 4 处模板内连接词/序列扩充），新增的每一条都要求「我能说出它出现在
哪一类真实文书里」，只因为「评测集里正好缺它」而补的**一个都没有**。
（规模是逐条数出来的。代码注释第一版写的是 31/22/21/29 四个估值，
与文件里的条目数对不上，已按实际改——报出的数字必须是数出来的。）

注意这条纪律与 §1.8 的做法并不冲突：v6 的诊断用的是**聚合计数**
（漏检分桶、长度分层、离切线距离），不是表面串。

### 1.9 v6 是第二个诚实的负结果：扩词表反而稀释了训练信号

| 评测集 | v4 | **v6（扩词表）** | 变化 |
|---|---|---|---|
| 法律主集 | **0.8271** | 0.7787 | **−0.0484** |
| 法律附集 | **0.6606** | 0.6217 | **−0.0389** |
| MSRA test（公开基准） | 0.8310 | **0.8359** | +0.0049 |
| cluener | 0.9362 | **0.9370** | +0.0008 |

**新闻域微微涨、法律域明显跌。** 这不是整体退化，而是打在了特定切片上：

| 金标长度 | v4 召回 | v6 召回 |
|---|---|---|
| 2 字 | 181/235 = 0.7702 | 181/235 = **0.7702**（逐个相同） |
| 3 字 | 547/709 = 0.7715 | 465/709 = **0.6559**（塌了 82 个） |

v4 的 302 个漏检里只有 84 个变成了 v6 多出来的漏检，而 3 字这一档就占 82 个。

**机制**：句子总数不变而上下文变多，等于每个上下文的样例数下降。
§1.6 已经证明模型靠背上下文工作（同一生成器留出 0.9982 vs 独立评测 0.827），
所以把上下文摊薄必然伤到它。

**候选成因（推断，非定论）**：v6 里把合议庭职务序列从固定 6 人轮转改成
`rng.sample(..., 2..4)`，**减少了人名密度**，而合议庭是人名最密的上下文。
要证它得把那一处单独改回去、只训一次——v6 同时改了 5 件事，这一处无法单独归因。

扩大的词表条目**保留在 `ner_legal_aug.OPTIONAL_*_EXTRA` 里、默认不启用**，
与 v5 的 `OPTIONAL_TEMPLATES` 同一个理由。

### 1.6 训练曲线的真相：不是欠拟合，是背模板

| epoch | 平均 loss | MSRA test F1 | 法律留出 F1 |
|---|---|---|---|
| 5 | 1.3512 | 0.7861 | 0.9873 |
| 11 | 0.7353 | 0.8141 | 0.9938 |
| 16 | 0.5020 | 0.8298 | 0.9969 |
| 21 | 0.3542 | 0.8272 | 0.9982 |

loss 一路在降，但 **MSRA test 从 ep16 起卡在 0.83 不动**，而「法律留出」
（同一生成器出的 200 句）已经 0.998。

**0.998 量的是背模板，不是泛化。** 独立评测 0.827，差的 0.17 就是模型依赖
「我见过这句话」而不是「我认识这个结构」的证据。这也解释了为什么
**加模板（v5）与加词表（v6）是两回事**：前者增加的是新的可背句式。

补充一条容易搞反的：法律合成只占训练语料 **6.4%**，
所以**不是合成数据压倒真实数据**。真实语料上的 MSRA test 本身就是 0.83——
**这不是「模型不懂法律」，是「模型整体就在 0.83」**，法律域与新闻域分数几乎相同。

### 1.7 评测集生成器现在带一条防复发的断言（且已验证会抛）

`_assert_length_coverage` 在「不同长度种类太少」或「短形态一个都没有」时
直接 `SystemExit`。**它已被实测验证会抛**——把旧 `main200_bio.txt` 的分布
喂进去，两个类别都如期报错：

```
X PER 实体只有 1 种长度 [3]，至少要 3 种——实体池的构词形状太单一……
X ORG 实体缺长度 [4, 5, 6]（现有 [7, 9, 10, 11, 13]）——短形态一个都没有……
```

「写完就算数的守卫等于没有守卫」，所以这一步是验证过的，不是假设的。

### 1.8 这套诊断自己也踩了三次坑（都记在这，因为它们会复发）

1. **只对总和的对账抓不出分错桶。** 分类别那张表第一版把 PER 的 253 个漏检里
   262 个记进「切边界」，但三项加起来仍是 253，对账通过、数字全错。
   现在改成**逐桶互校**（每类每一桶都必须等于总表同桶）。
2. **重叠判据写重了半边。** `p.start() < g.end() && p.start() < g.end()`
   少了 `g.start() < p.end()`，于是「起点在金标末尾之前的同类预测」就算重叠——
   金标**前面**那些毫不相干的人名也被算进来。
3. **两套口径各自都「平」。** 上述 1 和 2 合在一起时，总表说「完全没认 168」、
   分类别说 40，两边各自的断言都通过。**一个总数自洽的分解，恰恰是最难自查的一类**。

共同教训：**「加起来对得上」是比「看起来合理」弱得多的证据。**
分解出来的表必须让**两套独立实现互相对账**，否则错法一致时无人发现。

**这一节现在配一张全轴状态表**，因为本项目已经吃过一次「把一条轴的结论当成全部」的亏：
连续两次数据侧干预失败后写下「这条路到顶」，而架构侧根本没测过——
它恰好是唯一有效的杠杆（§1.12，+0.0141）。

| 轴 | 测过？ | 证据 |
|---|---|---|
| 数据：句式骨架 | ✓ | v5 **负结果**（§1.1） |
| 数据：词表覆盖（训练侧） | ✓ | v6 **负结果**（§1.9） |
| 数据：体量 | ✓ | v7-a **主动停掉**（实验混淆） |
| 架构：**感受野 15 → 31** | ✓ | v7 **正结果** +0.0141（§1.12） |
| 架构：感受野 31 → 63 | ✓ | v8 **负结果**（§1.13） |
| 架构：**宽度 256 → 384** | ✓ | **v9 正结果**（§1.16）：附集 +0.0785、cluener +0.0471 |
| 架构：宽度 384 → 512 | ✗ | 未测；按 §1.11 算术约 +13.4 MiB，余量 14.62 MiB **勉强装得下** |
| 架构：更深但保持 RF（如 `1,1,1,1`） | ✗ | 未测；与 v8 不同向，可能是另一条路 |
| 优化：学习率调度 | ✓ | 已有 `OneCycleLR(pct_start=0.1, linear)` |
| 优化：epoch 数 | ✗ | 未测（30 epoch，v9 验证集末段已平台） |
| 词表：字符级 UNK 策略 | ✗ | 未测（附集人名召回 0.667，是当前最大短板） |

**写「到顶」之前必须先把轴列全并逐条标注测没测过**——
顺序上应该先扫轴，再在每条轴内做干预实验。
人最容易先做费时的那类（改数据要重新生成语料、跑几小时训练），
而**最便宜的那条轴被跳过了**：宽度那条 `--embed-dim` 参数从项目第一天就存在
（默认 256），v4/v7/v8 一直沿用默认值，一次都没动过，读一眼代码就能知道。

**两次「到顶」的错误都出在同一处**：
第一次（数据侧连续两次负结果后）架构轴根本没测过，而它恰好是唯一有效的杠杆；
第二次如果现在就写「架构轴也到顶了」，会漏掉 v9——
因为 v8（加深）失败之后，**最自然的结论是「加深加宽都不行」**，
而实测是加深不行、**加宽大行**。**同一条轴上两个方向可以一正一负。**

下面这段是**当时**的结论，保留是因为它记录了一次真实的归因错误：

三次尝试，两次负结果，一次基础设施排除：

| 版本 | 改了什么 | 法律主集 | 结论 |
|---|---|---|---|
| v4 | 9 个法律模板 | 0.8271 | 当时的交付 |
| v5 | **新增** 3 个句式骨架 | 0.8147（旧集 0.8443→0.8147） | 负结果，见 §1.1 |
| v6 | **不新增骨架**，只扩词表 | 0.7787 | 负结果，见 §1.9 |
| v7-a | 法律语料 3 倍 | **未完成** | 启动后发现实验混淆，主动停掉——见下 |

**v7-a 为什么被停掉**：它同时带了 v6 的模板内改动，而我当时只回退了词表常量。
在这样的结果上无法区分「3 倍数据有用」与「模板内改动有害」。
既然 v6 已经证明模板内改动有害，就该先把它还原再测数据量——但那要多等 2.5 小时，
而结论的不确定性比这个成本更重要。**主动停掉一个会给出不可解释数字的实验，
比跑完它再解释要诚实。**

> 命名说明：`v7-a` 是这个被停掉的数据量实验。
> 后来的 **v7 是感受野实验**（§1.12），**v8 是 RF 63**（§1.13）——
> 编号被复用过，读文档时以「改了什么」为准，不要只看版本号。

（`ner_legal_aug` 现已把 v6 的四处模板内改动全部还原，
默认状态与 v4 的训练配方**逐字一致**，v4 的每个数字都可复现。）

**为什么说「合成数据这条路」到了顶**，三条证据互相独立：
（注意：这个结论只覆盖**数据**这一个轴。架构那个轴当时还没测——
§1.12 证明感受野就是一块没看过的短板，所以下面第 3 条要打折读。）

1. **机制**：训练曲线显示模型在**背上下文**（同一生成器的法律留出 0.9982，
   独立评测 0.827）。背模板的天花板由模板数量决定，而模板是有限的。
2. **方向**：两条增加模板信息量的路都失败了——
   v5 证明「加新骨架」会被学成「逗号分隔字段里少报人名」；
   v6 证明「同一批骨架加词」会稀释每个上下文的样例数。
   一正一反都指向同一个上限。
3. **基线**：真实语料上的 MSRA test 就是 0.8310。
   法律域与新闻域分数几乎相同，所以再优化法律模板也撬不动这条基线。
   ——**这一条当时被我当成了「什么办法都没用」，实际上它只说明
   「模板这条路没用」**：模型的感受野只有 15 字这种结构性问题，
   与数据量无关，而我没有在写这段的时候去算它。§1.12 是它的证伪。

**已排除的其它嫌疑**（都不是原因，列出是为了不重复查）：

| 嫌疑 | 排除依据 ||---|---|
| 学习率没调好 | `train_ner.py` 用 `OneCycleLR(pct_start=0.1, linear)`，ep30 loss 仍在降是 OneCycle 的正常形态 |
| 滑窗切掉了实体 | 离切线远近各档召回齐平，无梯度（§1.5） |
| 跨窗口去重不干净 | 重复上报只有 5 个（§1.5） |
| 类型判错 | 「认错类别」桶只有 5 个（§1.5） |
| 合成数据压倒真实数据 | 法律合成只占训练语料 6.4% |

**所以 0.9 这条线要往前走，需要的是这三条里的一条，都不是本机能自己解决的：**

1. **真实标注的法律文书**（哪怕 200~500 条）。合成模板再多也补不上
   「真实文书的句式多样性」这个缺口——这正是 `gen_legal_eval.py` 模块注释
   早就写下的限制，本轮把它从「理论上的保留」变成了**实测确认**。
2. **换更强的中文 NER 底座**（如开源的 BERT/RoBERTa 微调版）。
   代价是体积：本项目核心包预算 90MB，现已用 72.90 MiB，
   放不下 BERT-base（~400MB fp32）。要放就得量化裁剪或换档位，
   那是选型决策，不是调参。
3. **下调验收线并写清适用范围**。0.83 左右的水平在
   「卷宗里人名机构名高度密集且格式规整」的真实文书上可能够用，
   在自由文本上不够用——但这个判断需要真实脱敏样本才能下，
   本项目拿不到用户侧数据。

**在此之前交付模型维持 v4**，并在 `README.md` 里写明「人名识别约 0.83，
自由文本下可能漏」。

### 1.12 v7 是第一个正结果：感受野 15 → 31 字

**唯一一个改结构就见效的实验。** 前面三次（v5 加模板、v6 扩词表、v7-a 数据量混淆）
全在**数据**上调，两次负结果、一次主动停掉。

然后回头看架构，发现一件**可以算出来、却一直没算**的事：

```
感受野 = 1 + 2 × Σdilation
      = 1 + 2 × (1 + 2 + 4) = 15 字      ← 只有左 7 右 7
```

15 字意味着「委托诉讼代理人」这类 7 字角色词刚好塞得下、再多一个字就看不全。
而 §1.4 已经把靶子定死在**人名「完全没认出来」**——这类错误要靠上下文判断，
而不是靠字形（机构名的字形特征就在附近，所以机构名几乎全是边界问题）。

于是只加一层 `dilation=8` → 感受野 **31 字**，其余参数与 v4 逐字相同
（同种子 20261016、同数据、同 epoch 数）：

| 指标 | v4 | **v7** | 变化 |
|---|---|---|---|
| **法律主集 F1** | 0.8271 | **0.8412** | **+0.0141** |
| 法律主集 P / R | 0.8846 / 0.7766 | 0.8875 / 0.7996 | +0.0029 / +0.0230 |
| 法律附集 F1 | 0.6606 | 0.6634 | +0.0028 |
| PER F1（主集） | 0.8145 | **0.8283** | +0.0138 |
| ORG F1（主集） | 0.8623 | **0.8782** | +0.0159 |
| **PER「完全没认」** | 154 | **122** | **−32** |
| PER「切边界」 | 96 | 102 | +6 |
| **PER 召回（主集）** | 0.751 | **0.777** | +0.026 |
| **PER 召回（附集）** | 0.557 | **0.573** | +0.016 |
| MSRA test | 0.8310 | 0.8364 | +0.0054 |
| cluener | 0.9362 | 0.9303 | **−0.0059** |
| 名单留出 | 0.9395 | 0.9432 | +0.0037 |
| ONNX 体积 | 6.74 MiB | **7.49 MiB** | +0.75 MiB |

**它确实打在了靶子上**：PER「完全没认」从 154 降到 122，正是 §1.4 指认的那一桶。
代价是边界问题多了 6 个——总漏检从 302 降到 271，净赚 31。

**附集（19 字未登录）涨得比主集少得多**（+0.0028 vs +0.0141），人名召回只有 0.573。
这是本轮最该被记住的一个数：**感受野解决的是「上下文不足」，
而未登录字造成的是「字形信息本身缺失」，前者救不了后者。**
词表覆盖是另一条轴，与感受野正交——两者不能互相替代。

按长度分层的召回全线上升：2 字 0.7702→0.7957、3 字 0.7715→0.7997、
4 字 0.7027→0.7189、6 字 0.9138→0.9655。

**代价**：cluener 掉 0.0059。这是本项目里唯一一个「短文本」基准，
感受野变宽后长上下文的信息对短文本略微冗余。可接受，但要如实报。

**「先算感受野，再谈加宽」**——感受野不足是可以算出来的，
容量不足只能赌。+0.75 MiB 换 +0.0141，是本轮性价比最高的一步。

### 1.13 v8 是负结果：感受野 31 → 63 字，**定版 v7**

既然 RF 是算得出来的，那就把它加到底看看极限在哪。
v8 = `--dilations 1,2,4,8,16`（RF **63**），其余参数与 v7 逐字相同
（同种子 20261016、同数据、同 30 epoch）。参数量 2,160,158（v7 是 1,963,294）。

法律域确实又涨了，而且附集涨得比主集还多：

| 指标 | v4 | **v7（定版）** | v8 | v8 vs v7 |
|---|---|---|---|---|
| 法律主集 F1 | 0.8271 | 0.8412 | **0.8450** | +0.0038 |
| 法律附集 F1 | 0.6606 | 0.6634 | **0.6765** | +0.0131 |
| ONNX 体积 | 6.74 MiB | 7.49 MiB | 8.24 MiB | +0.75 MiB |
| MSRA test | 0.8310 | **0.8364** | 0.8338 | **−0.0026** |
| cluener | 0.9362 | **0.9303** | 0.9188 | **−0.0115** |
| 名单留出 | 0.9395 | **0.9432** | 0.9280 | **−0.0152** |

**三个外部/半外部语料集同向下跌，法律域上涨。** 这个方向组合本身就可疑：
主集与附集都出自 §2 那套合成模板，与训练数据同源；MSRA / cluener / 名单留出不是。

于是做了三件事，每件都推翻了一条「看起来显然」的解释。

**第一件：+0.0038 是不是噪声？** 主集 1352 个金标实体（实测），
二项近似标准误 `se ≈ √(F1(1−F1)/n) = 0.0099`（**算术，非实测**）。
差值 0.0038 只有 0.38 个 se —— **统计上不可区分**。
换算成实体数更直观：总漏检 271 → 259，净多认出 **12 个实体 / 1352 = 0.89%**。
为这点东西付出 0.75 MiB 和三个外部集的退化，不成立。

**第二件：三个外部集下跌，是不是过拟合？**
不是。**v8 的训练 loss 从第 0 个 epoch 就全程落后**：

| epoch | v7 loss | v8 loss | v7 名单 F1 | v8 名单 F1 |
|---|---|---|---|---|
| 0 | 31.9690 | **36.2942** | 0.0012 | 0.0000 |
| 2 | 3.4082 | **4.7023** | 0.8403 | 0.7365 |
| 5 | 1.4739 | **1.7561** | 0.8877 | 0.8849 |
| 14 | 0.5674 | **0.6649** | — | — |
| 24 | 0.3000 | **0.3546** | — | — |
| 29 | **0.2470** | 0.2846 | 0.9432 | 0.9280 |

训练 loss **更高**，就不是过拟合（过拟合是训练 loss 更低、验证更差），
而是 **`d=16` 那一层让优化变难了**——这是推断，不是实测：合理机制是感受野跨度
±16 字已达训练语料最长实体 35 字的一半，梯度路径又长了一层。

**这一条要单独记住，因为它决定修法方向相反：**
「验证集跌」既可能是过拟合（加正则 / 减层 / 加数据），
也可能是欠收敛（加 epoch / 调学习率）。**只看验证集会归因反。**
判据是训练 loss 的走向——**loss 更高就该先怀疑欠收敛**，加 epoch 才是修法。

⚠️ **未验证**：v8 加 epoch 能不能救回来，**没有跑过**（本轮只跑了 30 epoch）。
从曲线看 30 epoch 时差距已拉开且两条曲线都还在下降、没有收敛迹象，
但「加到 60 epoch 仍不行」这句话目前只是推断。要证伪它需要实跑
`--dilations 1,2,4,8,16 --epochs 60`，本轮没做。

**第三件：主集涨的那 0.0038 是什么？**
误差结构分解（同一探针、同一口径）暴露了一个 v7 没有的错误类型：

| 漏检归因 | v7 | v8 |
|---|---|---|
| 完全没认 | 135 | **120**（−15） |
| 同类型重叠（切边界） | 130 | **118**（−12） |
| **仅异类型重叠（认错类别）** | 6 | **21（+15，3.5 倍）** |

「认错类别」在 ORG 上从 4 涨到 **18**。v8 的召回是靠**更敢标**换来的
（误报 137 → 142，其中「孤立且全字登录」1 → 7），
代价是把一部分机构名判成了别的类别——**换的是精确率，不是能力**。

**定版 v7。** 三条理由各自独立成立：主集提升落在 1 se 内（算术）、
三个外部集同向退化（实测）、引入了一个此前不存在的错误类型（实测）。

**这一轮架构轴的结论**：RF 15 → 31 是有效区间，31 → 63 是负结果（实测）。
再往下（v9，RF 127）**推断**只会让优化更难，不值得跑——
理由是 RF 63 在 30 epoch 下已从第一步就落后，而 RF 127 的跨度更大。
**这是推断，没跑过 v9**；但它可算：第 5 层已经让收敛变慢，第 6 层只会叠。

### 1.14 一次红灯：测试的前提依赖了开发机状态，是我亲手弄红的

定版 v7 后做交付验收，把模型包装进 `~/.litemask/models/ner`（这正是 README 教用户做的事），
然后跑 `mvn test` → **931 个容器里红了 1 个**：

```
NerWiringTest.registryDisabledWithGuidance:189
  前提：本机 /Users/zhanghongqian/.litemask/models/ner 不该存在模型包，
  否则这条用例测不到「未启用」 ==> expected: <false> but was: <true>
```

**这次红灯原因是正确的**：不是编译失败、不是抛异常、不是超时，
是前提断言失败，且失败信息直接把被污染的路径打出来了。
用例自己的注释早就写明了它为什么存在——

> 不写这条的话，某天有人在 `~/.litemask/models/ner` 放了包，
> 这条用例会变成「突然红了」——而红的原因与被测代码无关。

**它宁可红，也不静默跳过。** 这条测试没做错，做错的是使用它的环境。

但它同时暴露了一个真实缺陷：**按 README 装好模型的用户，`mvn test` 会永久变红**。
交付后律所同事拉源码跑测试就会撞上，而红的原因与他们无关——
这是把「开发机当时装没装过东西」当成了测试前提。

**修法是让测试自证隔离，而不是删断言**：

```xml
<systemPropertyVariables>
  <user.home>${project.build.directory}/test-home</user.home>
</systemPropertyVariables>
```

⚠️ **不能用 `env -i HOME=<空目录>`** —— 已实测无效：
macOS/Unix 的 JVM 取 `user.home` 走 **passwd** 而不是 `HOME` 环境变量，
改 HOME 根本不改变 `System.getProperty("user.home")`。
只有直接设系统属性才真的隔离得开。

**双向验证（只做正向等于没验证）**：

| 场景 | 期望 | 实测 |
|---|---|---|
| 真实 `~/.litemask/models/ner` **有**模型 | 测试不该红 | **931 全绿，BUILD SUCCESS** |
| 测试期 `target/test-home/**.litemask**/models/ner` 有模型 | 断言必须红 | **红了 1 个**，红因正确 |

第二条的失败信息里打印的是
`.../desens-desktop/target/test-home/.litemask/models/ner` —— 路径本身就证明了隔离生效。

**这一条差点被我漏掉**：第一次做反向验证时，我把模型放在
`target/test-home/models/ner`（**少了一层 `.litemask`**），结果测试**全绿**。
如果就此收工，就会留下一个「看起来隔离了、实际断言已经永远为真」的改动——
正是「守卫必须验证它会抛」这条存在的理由。
「断言不响」和「断言生效」在正常路径上表现一模一样，只在故意破坏时才区分得开。

### 1.15 同一轮里发现的第二个「从不报警」的东西：体积闸门

跑 `tools/measure-size.sh` 时它报：

```
L0 jlink 运行时  .../target/runtime   MISSING
X 有必需组件缺失（jlink 运行时或 fat jar），这次量出来的合计不成立
```

而打包脚本 `tools/package-macos.sh` 产出的明明是 **`target/runtime-image`**。
**这个闸门从写下来那天起就没量到过任何东西**——它每次都失败，
失败得足够显眼，所以一直没人当成 bug 去查。但它同时意味着：
M3-4 引入它是为了「盯住唯一会悄悄涨的东西」，实际上**从来没盯住过**。

修了两处，外加一个更隐蔽的：

1. **路径默认值与产出脚本漂移**（`target/runtime` vs `target/runtime-image`）。
   改成与 `package-macos.sh` 同名，并在缺失时明确告诉人用 `RUNTIME=<dir>` 覆盖。
2. **L2 默认去 `target/models/ner`** —— 那不是任何真实产物的位置。
   改成按序回退到「app 内的 models/ner」与「用户实际投放的 `~/.litemask/models/ner`」。
   **量一个开发目录而不量用户目录，报出来的余量是虚的。**
3. **预算行把字节数打印成了 MiB**：`预算 90 MB（94371840.00 MiB）`——
   `90 × 1048576` 的字节被当成了 MiB，**预算看起来被放大了一百万倍**，
   而这一行恰恰是唯一声明预算口径的地方。

修完实测（L0 49.17 + L1 16.97 + L2 7.51 = **73.65 MiB，余量 16.35 MiB**；
此后 v9 与原生库剪除又把合计降到 **75.38 MiB / 余量 14.62 MiB**，见 §1.16 与 §1.17），
并做了三向验证：

| 场景 | 期望 | 实测 |
|---|---|---|
| `BUDGET_MB=10`（实际 73.65） | 必须判红 | `rc=1`，「X 超出预算：73.65 MiB > 10 MB」 |
| `RUNTIME=/tmp/不存在` | 必须判红并提示 | `rc=1`，打印 MISSING + 覆盖方式 |
| 正常 | 判绿 | `rc=0` |

**教训与 §1.14 同源**：那个测试是「前提依赖环境」，
这个闸门是「默认路径依赖了一个不存在的世界」——
共同点是**它们都只在坏的那一侧有输出，正常那一侧看起来一切正常**。
所以两者都必须做反向验证：**只看它正常时说什么，不看它在坏掉时是否真的会叫。**

### 1.17 第四次：同一天里我自己写的剪除逻辑，第一次跑就静默失效

给 `package-macos.sh` 加「剔掉 win-x64 原生库」（省 4.26 MiB）之后跑打包：

```
== 1/8 打 fat jar ==
    desens-core.jar = 17791696 B = 16.97 MiB      ← 一个字节都没变
...
PASS 打包并验证通过                                 ← 照样报 PASS
```

手工执行同样两行却是好的（省 4,467,594 B）。差别在**上下文**：

```bash
set -uo pipefail                      # 脚本开头有 pipefail
if unzip -l "$JAR" | grep -q 'xxx/';  # 手工跑时没有 pipefail
```

`grep -q` 命中即退出 → `unzip` 写到一半收到 SIGPIPE，退出码 **141**；
`pipefail` 让整个管道返回**最后一个非零**命令的退出码 → `if` 条件为假 →
**剪除一步都没执行**。

这条特别值得记，因为它同时踩了三个已经写进本项目的东西：

1. **「条件判断」本身成了最不可靠的一环**——正确做法是**无条件执行、再用体积是否真的变小来判断**。
   现在改成了这个形状：退出码不再是证据，**体积才是**。
2. **绿灯会掩盖新代码没跑过**。整场打包 PASS，包括 4/8、7/8 三项实跑验证，
   没有任何一项能发现「第 1 步少做了一件事」——
   因为它们验的是**产物能不能用**，不是**产物是不是按预期做出来的**。
3. **我这次没做反向验证**。刚写完就跑了正向，看到 PASS 就收工；
   而真正暴露问题的是「手工执行」这个偶然动作。
   **新写的剪枝/裁剪逻辑，第一次跑就必须先问「我怎么知道它执行了」。**

> 与前三次并排看，四次里**有三次是我自己的「新逻辑」**（测试隔离、闸门路径、原生库剪除），
> 三次都曾静默失效。**新写的检查性代码，默认假设它没跑，直到有证据。**

### 1.11 「换更强底座」要花多少体积（先算，再谈选型）

这一节把选项②「换更强的中文 NER 底座」变成**可判断的**问题。

**已实测的锚点**：

* v4 的 `ner.onnx` = 7,067,296 B = **6.74 MiB**（真实字节）
* v9 的 `ner.onnx` = 14,140,874 B = **13.49 MiB**（真实字节，现行交付）
* 核心包当前 **75.60 MiB**，预算 90 MiB，**余量 14.40 MiB**（2026-10-22 实测）

**下面三条是算术，不是实测**（参数→字节的换算，标注清楚以免被当成结论）：

| 候选 | 参数量 | fp32 | 对 14.59 MiB 余量 |
|---|---|---|---|
| 中文 BERT-base（词级，21128 词表，d=768，12 层） | ≈101M | **386 MiB**（int8 仍 96 MiB） | ✗ **超 22 倍，路是死的** |
| char 级 Transformer（沿用本项目 4588 字表，d=256，4 层） | ≈4.32M | 16.5 MiB（int8 4.1 MiB） | ✗ 已超（余量 14.59） |
| 只加宽本模型（embed 256→512） | ≈4.71M | 18.0 MiB | ✗ 超 3.4 MiB（但 §1.16 的 384 已是实测正结果，512 待测） |
| **v7：只加一层 dilation=8** | 1,963,294（**实测**） | 7.49 MiB（**实测**） | ✓ **只多 0.75 MiB** |

**结论很硬**：所谓「换 BERT 底座」在本项目的体积约束下**根本不是选项**——
即便 int8 量化也要 96 MiB，是余量的 5.6 倍。要用就只能蒸馏，那又回到
「精度损失不可预测」的老问题上，而不可预测的精度在验收线上等于没有验收线。

**真正走得通的是「沿用 4588 字表、把容量花在感受野和宽度上」**，理由是
本任务的词表本来就极小（4588 字 vs BERT 的 21128 词），
字级模型在这里的性价比远高于词级 Transformer。

v7 正是这条路上最便宜的一步：**感受野 15 → 31 字，参数量只多 196,864
（= 256² × 3，算术），体积只多 0.75 MiB。**
参数量由**两条独立路径交叉核对**：训练脚本自检打印 1,766,430 → 1,963,294，
而 ONNX 实际字节（6,707,296 → 7,855,050）扣掉约 2 KB 结构开销后 ÷4 得
1,766,324 → 1,963,262，两条在 ±100 内吻合。
（早先这里写的 1,963,038 是错的，差 256 = 恰好一层卷积核的数量——
只有一个来源时没人发现。**参数量这种数必须交叉核对**，因为它同时决定体积和推理开销。）

加感受野而不是加宽，是因为**感受野不足是可以算出来的
（1 + 2 × Σdilation = 15 字），而容量不足只能赌**。

**未测的下一块是宽度**：`--embed-dim` 从第一天就存在（默认 256），
v4/v7/v8 全部沿用默认值，一次没动过。按本节公式估算 384 宽约
+1.57M 参数 / +6.0 MiB（**算术，非实测**），512 宽约 +3.5M / +13.4 MiB——
**余量已从 10.36 涨到 14.62 MiB**（剔掉 win-x64 原生库省下的，见 §1.17；
2026-10-19 重测为 14.59 MiB），
所以 384/512 的算术都在预算内；但 **384 已经实测为正结果**（§1.16），512 仍未跑过。

### 1.18 端到端的形态必须由脚本决定；它顺手挖出一个真的原值泄漏

#### 1.18.1 病根：e2e 量的是开发机，不是被测代码

上一轮记下了「`pom.xml` 的 user.home 隔离只覆盖 surefire，e2e 还没改」。
本轮它变成了**实际故障**：按 README 把 v9 装进 `~/.litemask/models/ner` 之后，
5 个 e2e 里 4 个变红（ooxml / untrusted / pdf / serve）；把模型移走又全绿。

**两次都不是「端到端通过」**，只是「端到端测了当时那台机器的碰巧状态」。
和 surefire 那次是同一个病：闸门量的是环境，不是被测代码。

修法是新建 `tools/e2e-common.sh`，5 个 e2e 共用：

- **形态由脚本决定**，不再由开发机决定。默认 = 无模型形态，
  这正是 `pkg` 的交付形态（方案 B，pkg 里不含模型包）；
  `LITEMASK_E2E_NER=<目录>` 才切到带模型。
- 无模型时把 `user.home` 指到一个**空的临时目录**，并且
  **`unset LITEMASK_NER_MODEL`**——它的优先级高于 home，shell 里残留一个隔离就失效。
- **形态自证**：产品每次启动都会打印 `registry.describe()`，
  e2e 直接拿**产品自己的输出**来确认形态，不符就立刻退出。
  「设了变量」和「变量真的被读到了」是两件事，只有后者的输出能作证。

#### 1.18.2 自证必须先证明它会抛

一个只会报 PASS 的自证等于没有自证，所以双向验证过：

- **挡住已安装的模型**：把 v9 放回 `~/.litemask/models/ner`（`ner.onnx` 确实在位），
  跑默认形态 → 产品打印的查找路径是隔离目录、形态 `未启用`、全绿。
  **证据是产品打印的那行路径**，不是我「相信变量设对了」。
- **守卫会抛**：手工跑带模型的产品，它打印的是 `已启用`、输出里含
  `识别：未启用` 的次数 = 0 → 形态不符时 `e2e_form_check` 必然红并退出。

#### 1.18.3 抓出来的真缺陷：重叠消解把「不占令牌」当成了「不用脱」

跑带模型形态时，txt 路径出现：

```
身份证 <身份证1>, <人名1>gsan@corp.example.com
```

模型把**拼音邮箱的头 4 个字**认成人名。NER 的 `sortOrder` 900 高于邮箱规则的 120，
于是邮箱那条在重叠消解里**落败**——而旧实现是把落败命中**整条丢弃**：

```java
if (overlapsAny(accepted, candidate.start(), candidate.end())) {
    continue;          // ← 落败命中的非重叠部分从此没人管
}
```

邮箱整段 [0,20) 被丢，只有被盖住的前 4 个字换成令牌，
尾巴 `gsan@corp.example.com` **原样躺在交付物里**。

**关键在两者互不包含**（NER [0,4) ⊂ 邮箱 [0,20) 但更短），所以存在残余。
旧实现处理得了「NER ⊃ 规则」的那种包含关系（`重叠时AI胜出` 那条一直绿），
因为那时规则整段落在 NER 里面、残余为空——**这条路径从来没被测到过**。

更值得记的是它的隐蔽性：**往返照样无损**。映射只记了令牌对应的原值，
裸露的尾巴压根没进映射，所以还原之后看不出问题，
只有直接看脱敏件才发现邮箱还在。而且它**只在带模型形态出现**，
无模型形态下压根没有 NER 实体来触发它。

修法：落败命中只丢重叠段，独有部分作为残余放回队尾继续参与消解
（FIFO，排序键固定，同一组输入仍得到同一组输出）。
落败的含义是「不单独占一个令牌」，**不是「不用脱」**。

修复前后（实测，真实 jar）：

```
前：身份证 <身份证1>, <人名1>gsan@corp.example.com
后：身份证 <身份证1>, <人名1><邮箱1>          往返逐字一致
```

**验证**：红灯先写（`Failures: 1, Errors: 0`，失败原因逐字复现了上面的真实输出，
说明夹具有效而不是人造边界）；`mvn test` **932 全绿**（931 + 新增 1）；
新增对照实验**破坏⑶**把它改回旧行为 → **两个测试同时变红**
（`EngineEntitySourceTest` 新增那条 + `ExclusionTest` 的前置条件断言），
基线复核 GREEN。

**顺带修了一处测试自身的问题**：`ExclusionTest.排除输家时赢家也要让开` 的
「前置条件」原本断言正常态是 `证件 <丁1>231002 结束`——
**把身份证后 6 位的裸露写成了一个应当成立的前提**。
前提站在错的起点上，后面的断言就都站在流沙上。已改成两段都脱敏。

#### 1.18.4 校验器也有两处站不住：一处是夹具语义错，一处是加强

- **夹具语义错**：PDF 样本的「未命中的末行」原本写的是
  `此致 北京市朝阳区人民法院`，校验器要求它原样保留。
  但**法院名本来就是机构名**，装了模型之后它被识别成 `<机构名2>` 是**正确行为**，
  修法一度指向引擎或模型——两边都是对的，是夹具选错了东西：
  要验「不该脱的不被脱」，必须拿一个**确实不该被脱**的东西去验。已改成 `此致 敬礼`。
- **令牌序号解耦**：原来逐个断言 `<ID_1>` / `<PHONE_1>` / `<MAIL_1>` / `<CARD_1>`。
  NER 会插入自己的实体，同类别的第几次出现会整体后移，带模型形态下
  根本不存在 `<MAIL_1>`。改成断言「存在形如 `<MAIL_N>` 的令牌」——
  **这不是放宽**：规则若漏脱了邮箱（压根没写令牌），两条一样红。
- **加强**：「还原后无残留令牌」原来只检查那四个写死的序号，
  **NER 自己发出去的 `<机构名1>` 残留它根本抓不到**。
  改成扫 `<[A-Za-z_]+_\d+>` 全形态——这是本轮唯一一处把校验变严的地方。

#### 1.18.5 这一轮里我自己制造并修掉的三个回归（都写下来，因为都会复发）

1. **shell 函数后台启动，`$!` 不是目标进程的 PID。**
   把隔离包进 `prod()` 函数后，`prod ... &` 拿到的是**子 shell** 的 PID。
   实测探针：`$!=94874`（子 shell）/ 真正进程 `94876`，`kill $!` 打不到。
   后果是 e2e-serve 的「停止后工作目录整棵删除」红——服务收不到 SIGTERM。
   修法：改用**外部命令数组** `PROD_CMD=(env "JAVA_TOOL_OPTIONS=..." "$RUN_JAVA")`，
   前台用 `prod` 包一层，**后台必须展开数组**。
   更糟的是它有**自我强化效应**：第一次漏杀的 java 一直占着端口 18931，
   后面每一次跑 e2e-serve 都因为端口被占而拿不到令牌——一个 bug 污染了之后所有运行。
2. **`edit` 的 old_string 带尾换行而 new_string 不带，会把两行粘成一行。**
   `BUSY_PID=$!` 和下一行 `sleep 3` 粘成了 `BUSY_PID=$!sleep 3`，
   报错是 `3: command not found` 与 `BUSY_PID: unbound variable`——
   **报错完全指不到真正的病灶**。「edit 返回成功」不等于「改对了」。
3. **Java 实参急切求值。** 校验器里写成
   `require(!m.find(), "...", m.group() + after)`，
   结果 `find()` 返回 false（正是「一个残留都没有」这种最该绿的情况）时
   `group()` 照样被执行，抛 `IllegalStateException: No match found`，
   **端到端在通过的那条路上崩了**。匹配结果必须先存下来再拼进失败信息。

#### 1.18.7 校验器把「内容对不对」和「坐标还对不对」判成了一件事

`E2ePdfSample` 原来一律用 `extractText(setSortByPosition=true)` 做**所有**断言，
于是「版式没对齐」被报成「缺少令牌」——**而文件里的令牌其实逐个完整**。
更糟的是往返校验也用同一个模式：原件与还原件**错得一模一样**就判相等，
坐标问题被两边共同掩盖，「往返无损」这个结论便不再说明任何事。
这是「两个观察者错法一致时会一起错」的一个实例。

改法（**加，不是换**）：`extractText` 拆成两种模式，
内容断言与往返断言走默认（按内容流顺序），**另立一条「版式保真」断言**
走按坐标抽取。修好坐标之前那条保持 fail——换成默认抽取就等于把缺陷藏起来。

带模型形态下修完的结果：**36 项通过，唯一失败是那条版式保真**，
且失败信息明写「不是泄漏也不是内容缺失」。

#### 1.18.8 夹具也是要实测挑的，不是看着像就拿来用

「未命中的末行」这个夹具连换两次才换对：
第一次 `此致 北京市朝阳区人民法院` —— 法院名本来就是机构名，模型判它**没错**；
第二次 `此致 敬礼` —— **实测 v9 把「敬礼」认成人名**（`<人名1>`）。
最终用 `以上情况属实 特此说明`，候选实测结果：

```
✗ 此致 敬礼 -> 此致 <人名1>          ✓ 特此通知 请予审批
✓ 以上情况属实 特此说明              ✓ 据此 申请执行
```

**要验「不该脱的不被脱」，就必须先证明它确实不会被脱**——
拿一段「模型可能也会认」的文本当夹具，红了分不清是引擎错了还是夹具选错了。

#### 1.18.9 顺带查出的两个真实问题

**（1）`e2e-serve` 的排除项取错了目标。** 注释写「排除第一个**手机号**」，
代码取的却是 `hits[0]`（第一个**命中**）。无模型时 `hits[0]` 恰好就是 phone，
所以一直绿；带模型时 `hits[0]` 变成 `ner_person`，排除项就选错了，
测的其实是另一件事。已改成按 `ruleKey` 精确取（顺带不再依赖 JSON 是单行紧凑格式）。
**判据与它声称的不一致，本身就是一条测试缺陷。**

**（2）v9 在短文本上的误伤，比文档里原先记的要严重得多（实测）。**
拿 e2e-serve 那 3 行探针跑带模型形态，命中清单实际是：

```
'人'→人名   '张三'→人名   '电话'→人名   '1'→人名
'380013'→手机号   '8000'→人名   '13900139000'→机构名   '乙方'→机构名
```

`13800138000` 被切成 `1` + `380013` + `8000` **三条命中**，
`13900139000` **整串**被判成机构名、手机号规则那条完全落败。

- **没有泄漏**（三段全脱敏、往返逐字一致），但**界面呈现是错的**。
- 与「主集 F1 0.8479」不矛盾：那是**长法律文书里的召回**，这是**短文本里的误伤**。
- 已在 `docs/精度验收标准.md` 的「不适用」里补了一条：
  **短文本、标识符密集的混合内容**（名单页、联系页、表格行）应关掉 NER 只用规则。



**交付物层面也验过（不是只验源码）**：用重打后的
`target/app-image/LightMeter.app`（app 内 CLI + app 内 v9 模型）跑同一条泄漏用例：

```
身份证 <身份证1>, <人名1><邮箱1>       无裸露尾巴 ✓  完整邮箱已消失 ✓  往返逐字一致 ✓
```

重打包与体积：`package-macos.sh` **8 步全通**，fat jar 13,324,709 B（剔 win-x64 省 4.26 MiB），
`LightMeter.app` 79,182,098 B = **75.51 MiB**，核心 `.pkg` 45,357,096 B = **43.26 MiB**；
`measure-size.sh` → **75.38 MiB / 余量 14.62 MiB，rc=0**
（2026-10-19 重测为 **75.41 MiB / 余量 14.59 MiB**，见「交付件现状」；M2-c 补块之后复测为 **75.42 MiB / 余量 14.58 MiB**；
2026-10-20「上传先落盘」块之后复测为 **75.48 MiB / 余量 14.52 MiB**）。

- **PDF 带模型的「交错」——已修（§1.19）。**
  这条记录经历过两次更正，过程本身留着，因为两次都错在同一个地方：
  **把观察者的输出当成了被观察对象**。

  | 版本 | 说法 | 错在哪 |
  |---|---|---|
  | 最初 | 「产物里有交错残片」 | 拿 `extractText` 的结果当文件内容 |
  | 第一次更正 | 「内容完整无泄漏，交错只是抽取顺序」 | **对，但轻描淡写了** |
  | 第二次更正（§1.19.2） | 「那一行在页面上完全不可读」 | 把渲染图看过了 |

  第一次更正的三个观察者结论本身是对的：原始内容流字节里
  `<ID_1>` `<NER_PERSON_1>` `<NER_ORGANIZATION_1>` `<NER_PERSON_2>` `<MAIL_1>` 逐个完整，
  `extractText` 默认排序基本正常，只有 `setSortByPosition(true)` 交错，
  机制是**令牌墨迹比槽位宽 → 落到重叠 x 区间**。
  错的是**结论的力度**：「版式精度问题」听起来像抽取顺序的小毛病，
  而渲成 PNG 一看，那一行是四个令牌叠成一坨、完全不可读——可用性事故。
  真实宽度差：`<NER_PERSON_1>` 110 pt 顶替 15 pt（7.3×）。

  **修法与证据见 §1.19。** 这里保留这段，是因为它印证了一条本项目的通用教训：
  **「没泄漏」不等于「没坏」**，而用抽取结果推断版面问题尤其危险——
  抽取器的排序策略是一层你看不见的假设，不看渲染就永远不会知道它。
- **重叠时标识符被切成多段——已定论，见 §1.19.8。** 实测映射：
  `{"<人名1>":"邮箱", "<人名3>":"a.b", "<邮箱1>":"@x.", "<人名4>":"cn"}`
  ——一个 `a.b@x.cn` 被拆成三段，**完整原值不在映射里**，
  ooxml 与 untrusted 那两条红就是这个（「映射里找不到原值」）。
  往返逐字一致、无泄漏，所以**不是安全缺陷**，但界面上一个地址会显示成多条命中。
  这是「重叠时拆成多段（保守不泄漏）」与「合并成一段（界面对齐）」
  之间的取舍，本轮选了前者。**没定论，留作下一轮的取舍题。**
- 顺带记录一条**模型质量**事实（实测，非缺陷）：v9 在
  `邮箱 zhang@example.com 备用 a.b@x.cn` 这种**短文本**上把「邮箱」这个词本身
  认成了人名。上下文太少时误伤明显——这与 `docs/精度验收标准.md`
  里「人工复核」那条约束同源，不是意外。
- **`package-macos.sh` 第 7 步的验收只验「令牌存在」**：它确认
  `<身份证1>` 与 `<人名1>` 都在，也就是「确实脱了」，但**不验「没有碎片残留」**——
  与本轮修掉的 PDF 校验器那个毛病同型。所以上面那个交错缺陷它必然抓不到。
  真正抓到它的是 e2e 的带模型形态。**下一轮该把第 7 步也加上
  「产物里不得出现原值的连续片段」这一条。**

### 1.19 一个 163 行从未被执行过的类 + 一个被当成「精度问题」的版面缺陷

上一轮把 PDF 那个交错现象定性成「版式精度问题，产物内容完整无泄漏」，留着没修。
本轮先去看那张渲染图，结果和定性不符，所以重开。

#### 1.19.1 `TextAdvanceSimulator` 是死代码：164 行，零个调用点

它写得很完整——独立按 PDF 32000-1 9.4.4 重写了宽度公式、注释里专门写了
「不复用 `ShowTextOp`，否则写错了会一起错」。但：

```
$ grep -rn "simulate\|ShowStop\|displacement" src/test tools
（0 命中）
```

**它从未被执行过一次**。`ContentInterpreter` 的注释说「版面由 `TextAdvanceSimulator`
单独校验」，可没有任何地方调用它。于是一句「版面由 X 校验」实际是一句空话，
而它就摆在最容易被当成「已验证」的位置。

这正是本项目反复遇到的那一类：**绿灯旁边放着一个从不亮的东西**。

修法不是「把它用起来」，是**把它接到会真正报警的地方**：回写完每个内容流之后，
用同一条位移定义把改写前后的内容流各走一遍，比对每段末尾位移，不一致就写进 `warnings`。
接完之后，容差是**量出来的**，不是拍的：把容差临时设成 0，跑真实夹具，得到

```
第 4 段末尾位移差 0.000030518 pt（原 307.656005859 → 新 307.655975342）
```

3.05e-5 pt，正好是 307.656 处的 float32 单个 ULP（≈3.66e-5）。
于是容差取 **0.01 pt**：比噪声大 330 倍，比任何真实漏补（一个字符就是数个 pt）小两个数量级。
先量再定，这是本轮唯一一处「数值靠实测而不是靠直觉」的决定。

#### 1.19.2 渲染真图推翻了上一轮的定性

上一轮写进文档的结论是「版式精度问题，非脱敏失败」。这句话**只对了一半**，
漏掉了更严重的一半。把 `卷宗.redacted.pdf` 用 `qlmanage` 渲成 PNG 之后：

| | 第 3 行渲染结果 |
|---|---|
| 原件 | `身份证 11010519491231002X 邮箱 zhang@example.com` |
| 修前 | `<NER_PERSON_1><NER_ORGANIZATION_1><NER_PERSON_2><MAIL_1>` **四个令牌叠成一坨，完全不可读** |
| 修后 | `<PER_1><ORG_1> <PER_2> <MAIL_1>` 四个令牌各自可读 |

「精度问题」的说法让人以为只是「按坐标抽取时顺序有点乱」。
实际上**页面上那一行已经不能看了**——这是可用性事故，不是精度事故。

量出来的原因（告警里本来就写着，当时没当回事）：

| 令牌 | 实际宽 | 顶替的原文宽 | 倍数 |
|---|---|---|---|
| `<NER_PERSON_1>` | 110 pt | 15 pt | 7.3× |
| `<NER_ORGANIZATION_1>` | 151 pt | 24 pt | 6.3× |
| `<MAIL_1>` | 55 pt | 26 pt | 2.1× |

**注意这三行的文本本身没问题**——四个令牌都在、内容完整、往返一致。
坏的只有**墨迹宽度**。

#### 1.19.3 两处修法，都是早就该有的

**其一：`PdfTokens.SHORT_PREFIX` 漏了 NER。** 那张表的注释白纸黑字写着
「令牌画在 PDF 上，宽度是真金白银的版面成本」，理由举的正是 `<IP_ADDRESS_1>`
比 `192.168.1.100` 还宽。可它收了 17 条规则，唯独漏了
`ner_person` / `ner_organization` ——而这两个恰好是**最长的两个前缀**
（回退大写是 14 与 19 字符），顶替的又常常只有两三个汉字。补上 `PER` / `ORG`（各 6 字符）。

**其二：令牌按槽宽横向压缩。** `Tz` 只压横向不压字号，压到 45% 仍是正常字高的窄体字，
肉眼可读；再窄就成糊条。压到底还塞不下时**选择溢出并点名告警**——
溢出会被指名道姓地报出来，糊条则连「这里脱了什么」都读不出来，而令牌可读性是用户核对结果的依据。

#### 1.19.4 压缩顺带挖出两个**本来就存在**的潜缺陷

代码里原本有一段注释：「曾经试过压缩，代价是还原彻底对不齐：压扁写在 `Tz` 上，
而还原时无从知道原文的 `Tz` 该是多少。」这个理由**已经不成立了**——
`emitToken` 在令牌 TJ 之后必定写回 `<原 Tz> Tz` 与 `/原字体 原字号 Tf`，
还原时扫回来即可。于是按这个思路真去压缩，立刻踩到两个一直没被发现的问题：

1. **还原只写回 `Tf`，没写回 `Tz`。** 令牌画在 Tz=45%，原文该在 Tz=100%，
   还原时不切 Tz，原文就被按 45% 画回去，字挤成一小条，后面整段被甩出去，
   抽取出来是 `Tel 13800138000 done`——**凭空多出一个空格**。
   这个洞在令牌从不压缩时是**隐形**的（Tz 恒为 100），所以躲过了所有测试。
2. **继承来的 TJ 调整数被搬到另一种水平缩放下执行。** TJ 数字的含义是
   `n/1000 × 字号 × 水平缩放`。脱敏时那个数是在 Tz=45% 下写的，
   还原时同一行跑在 Tz=100% 下，不换算就多走一倍位移。
   实测偏差 **5.898941 pt**（`done` 的横坐标 144.835968 → 138.937027），
   由 `splitAcrossShowOpsRoundTrip` 这条**早就存在**的用例当场抓住。

两个都不是新压缩引入的，是**一直被补偿正确这个事实掩盖着**。
新写法只是把旧的遮羞布掀开了。

#### 1.19.5 判据：能算出来的先算，别看图

「令牌有没有压到后面的字」不需要人眼看。本轮定的判据是
**同一行的字形横坐标沿流顺序单调不减**——压上去就会出现坐标倒退。
宽度取 **PDFBox 自己算的 `getWidthDirAdj()`**，不按字体度量表估：
估出来的值和真值差零点几个点，而「有没有压上去」恰恰是这个量级的判定，
拿不准的尺子量出来的结论不能用。

（第一版这里踩了坑：拿「数字约 0.56em、大写约 0.67em」估字宽，
结果把 `A:` 的冒号判成被压，立刻红灯。红灯原因是对的——尺子不准，不是产品错。）

#### 1.19.7 顺带修掉的第三个弱验收

`package-macos.sh` 第 7 步原来只验 `<身份证1>` 与 `<人名1>` 存在——就是 §1.18.9
点名的那条「只验该有的在、不验不该有的不在」。现已加成五道：
原文零残留（含姓名）、**令牌化后不得出现连续 6 位以上裸数字**（碎片查不出来是因为
每个碎片都不等于原文）、映射三个原值齐全、**往返逐字一致**。

最后一条是刚补的，理由是打包产物用的是 jlink 精简运行时 + 另写的启动器，
与开发时跑的不是同一个二进制，只验「能脱敏」不验「能还原」是不够的。

**这一条上线后连踩三次才通**，而三次红灯全都指向错误的方向：

| 错在哪 | 红灯说什么 | 实际 |
|---|---|---|
| `<手机1>` | 「规则链路在打包产物里没接上」 | 前缀其实叫 `<手机号>`，我是**猜**的 |
| `t2.restored.txt` | 「还原失败或往返不一致」 | 还原早成功了，是我拼错文件名 |
| `${OUT%.*}` | 同上 | `OUT` 是绝对路径，去扩展名把目录也留下了 |

第三次尤其阴险：`$WS/<一整条绝对路径>` 这种双份路径，只看「不存在」根本想不出问题。
所以失败分支现在会把**期望路径与是否存在一起打出来**——前两次如果有这一行，
一眼就能看出问题在「期望值」而不在「产物」。

判据归纳成一句：**判据里凡是拼出来的字符串（路径、令牌名、正则），都必须来自一次实测**，
不能来自对命名规则的推理。这与 §1.19.3 里「夹具必须实测挑选」是同一条，
本轮在自己身上又犯了一次。

#### 1.19.8 定论：重叠时标识符被切多段，**维持拆分，不合并**

上一轮把它挂成「待决」，理由是「拆成多段安全但界面错」与「合并界面对齐但可能错分」
两难。本轮有了新证据，可以定了——**因为合并会造出一个源文件里根本不存在的原值**。

实测那条映射：

```json
{"<人名1>":"邮箱", "<人名3>":"a.b", "<邮箱1>":"@x.", "<人名4>":"cn"}
```

一个 `a.b@x.cn` 被切成四段。合并意味着要往映射里写 `a.b@x.cn` 这一个完整原值——
可它**从未作为整体出现在任何一份输入文件里**，它是把不同规则各自认领的片段拼出来的。
用户拿这份映射去核对源文件时，会找不到这个字符串；真拿去当审计证据，更是拿一条
「工具自己编出来的原值」去证明「源文件里有这个值」。

对比之下，拆分的三条代价都是**看得见**的：界面上一条地址显示成四条命中、
映射里没有完整原值、往返虽然逐字一致但用户会困惑。
**代价可见，编造不可见。** 后者更危险。

本轮新加的证据把取舍的权重又压了一分：拆分会**放大**版面代价。
一个标识符切成 N 段就是 N 个令牌，而窄槽位里每多一个令牌就多一份压字的机会
（§1.19.3）。所以「合并」对版面的好处是真的，对映射的可信度的代价也是真的。

**结论：维持拆分。** 后续要改的是**呈现**（界面上把同一原文相邻的命中归成一组展示），
不是**映射内容**。这一条已写进 `docs/精度验收标准.md` 的「不适用」。

| `mvn test` 总数 | 932 | 942（看着像 +10） | **943** |

**没有任何一层报警**：编译通过、单测全绿、对照实验那一轮也还在跑。
唯一响的是**对照实验**——`破坏㉓：不遍历表单 XObject` 从 RED 变成 GREEN，
而它上一轮明明是 PASS（RED）。也就是说：

> **对照实验不只是「撤掉实现测试会不会红」的检查，
> 它同时是「有没有哪条测试已经不执行了」的报警器。**
> 一个被摘掉注解的用例会**永久放弃它咬过的每一个变异**，而全量单测对此完全无感。

所以两条纪律，都是这轮的实际代价换来的：

1. **往测试文件里插用例时，替换块必须以「下一条用例的注解开头」收尾**，
   或者干脆把插入点放在方法**之间**而不是注解中间。
2. **只用 `edit` 局部替换时，收尾要显式数一遍**：
   `grep -c "@Test" 文件` 与 `grep -cE "^    void " 文件` 必须相等，
   再与 surefire 报的每类用例数对一次（本次 21/21/21 一致）。

顺带一条同源的教训：**中途 `task_stop` 掉对照实验会留下脏源码**。
本次中断后 `RedactionEngine.java` 停在变异体上、`.bak` 里才是基线。
判别方法很简单——`.bak` 是**变异前**的副本，所以**当前文件与 `.bak` 不同才是危险信号**。
下次中断后先 `diff 源码 源码.bak`，确认一致再删 `.bak`，反过来做就等于把变异体留下当基线。

### 1.20 一条「到 Windows 必红」的测试，和它顺带挖出的两个静默缺陷

#### 1.20.1 起点：一个「本机没字体就跳过」的判断

中文 PDF 的两条单测（往返保真、解码不空转）原来这样取字体：

```java
private static Path cjkFont() {
    for (String candidate : List.of(
            "/System/Library/Fonts/Supplemental/Arial Unicode.ttf",
            "/System/Library/Fonts/STHeiti Light.ttc",
            "/System/Library/Fonts/Supplemental/Songti.ttc",
            "C:/Windows/Fonts/msyh.ttc")) {
        Path p = Path.of(candidate);
        if (Files.isReadable(p)) {
            return p;
        }
    }
    Assumptions.assumeTrue(false, "本机找不到可用的中文字体，中文 PDF 路径未覆盖……");
}
```

看起来很克制——找不到就跳过、并明说「这是验证缺口」。但它有三个问题，
而这三个问题**都是实测出来的，不是推理出来的**：

1. **Windows 上唯一的中文字体候选是 `msyh.ttc`，那是字体集（TrueType Collection）。**
   PDFBox 的 `PDType0Font.load` 读不了它。而且 `cjkFont()` 找到文件就返回，
   **不会**走到 `Assumptions` 那一行——所以 Windows 上不是「跳过」，是**抛异常红**。
2. **「本机没字体就跳过」是个长期的静默覆盖洞。** 中文 PDF 这条路径在很多机器上
   根本没被执行过，而全量单测对此完全无感（跳过的用例照样计入「Tests run」）。
3. **不同机器的字体度量不同**，版面断言的数值随机器变，测试不可复现。

#### 1.20.2 实测一：`.ttc` 确实读不了，而且 PDFBox 自己也会栽在同一个坑上

fontbox 3.0.3 / PDFBox 3.0.3 实测：

| 加载方式 | `Arial Unicode.ttf` | `STHeiti Light.ttc` | `Songti.ttc` |
|---|---|---|---|
| `PDType0Font.load(doc, InputStream, true)` | OK | **`IOException: 'head' table is mandatory`** | 同左 |
| `PDType0Font.load(doc, File)` | OK | 同上 | 同上 |
| `TrueTypeCollection.getFontByName(...)` 取单个字体 | `Missing TTC header`（本来就不是集合） | **OK** | OK（但取到的首个字体 `fsType` 禁止嵌入） |

`'head' table is mandatory` 是 fontbox 在抱怨「你给了我一个集合而不是一个字体」，
但它一个字都没提该怎么改。要读 `.ttc` 必须走 `TrueTypeCollection`。

**独立佐证**：跑 e2e 时 PDFBox 自己在扫系统字体，也报了同一句——

```
WARNING: Could not load font file '/System/Library/Fonts/Supplemental/NISC18030.ttf': 'head' table is mandatory
```

那个文件其实是字体集，只是扩展名是 `.ttf`。所以这不是「用法姿势不对」，
是 fontbox 的一个真实边界。

#### 1.20.3 实测二：「这个字形在不在」不能问 `hasGlyph`

要把「打包字体覆盖了测试用到的每个字」变成断言，先得找到一个可靠的判据。
实测 PDFBox 3.0.3 对 CJK 字符的行为：

| 探针 | `hasGlyph` | `codeToGID` | `getPath` | `encode` |
|---|---|---|---|---|
| U+6C11 民（**在**字体里） | **false** | **0** | 非空 | `0816` ✅ |
| U+4E00 一（**在**字体里） | **false** | **0** | 非空 | `0130` ✅ |
| U+9F00（**不在**字体里） | false | 0 | 非空 | **抛 `IllegalArgumentException`** ✅ |
| U+20000（扩展 B，超出 BMP） | false | 0 | 非空 | 抛 `IllegalArgumentException` ✅ |

**`hasGlyph` 和 `codeToGID` 对 CJK 一律给「没有」**——连字体里明明有的「民」「一」也是。
用它们判存在性，等于永远判「不存在」。

能用的是 `encode`：**缺字时抛 `IllegalArgumentException`，两种 `embedSubset` 模式下都抛**
（这一点单独测过，因为下面 §1.20.4 会换模式）。

#### 1.20.4 实测三：三种写法只有一种能产出「真能用」的中文 PDF

改用仓库自带的字体子集后，第一版夹具写出的 PDF 是**坏的**。三种写法并排实测：

| 写法 | 产物大小 | `FontFile2` | 文本能原样抽回 |
|---|---|---|---|
| A `embedSubset=true`，不 `subset()` | 1,504 B | **缺失** | 否（抽出来是 `₉ƭ \| ̡͵ ᴫű`） |
| B `embedSubset=true`，编码后 `subset()` | 2,044 B | 有 | **否**（`ࠖůඕങड़`） |
| C **`embedSubset=false`** | 793,869 B | 有 | **是** ✅ |

A 和 B 的坏处是同一种：文件里**没有嵌入字体**（A 连 FontFile2 都没有），
换台机器打开就是乱码或替代字体。这类路径的产物在**这台**机器上看着正常，
因为 PDFBox 从系统里找到了替代字体。

代价是 C 会把完整字体塞进 PDF（几百 KB）。测试文件写在临时目录里，这个代价可以接受；
换来的是「夹具产出的 PDF 真的自带字体」，而不是靠阅读器去猜。

#### 1.20.5 实测四：`getFont()` 取回来的不是同一个字体——这是 e2e 一直有的暗伤

`PDResources.add(font)` 之后 `getFont(name)` 返回的是**从 COS 字典反序列化出来的副本**。
它看不到还没写进描述符的嵌入字体，于是 PDFBox 会找一个替代字体顶上：

```
WARNING: Using fallback font LiberationSans for CID-keyed TrueType font NotoSansSC-Thin
```

**老代码写的就是 `getFont(name)`。** 为什么一直没暴露？因为当时的字体是
Arial Unicode，PDFBox 的 FontMappers 恰好有它的系统映射，于是能编出正确的 CID，
文本抽出来还是对的——**但文件里依然没有嵌入字体**。
也就是说：**端到端样本 PDF 从来就没带着自己的字体**，
换台机器打开就是坏的，而端到端照样可能「跑通」。

修法两条一起上：用 `embedSubset=false`（§1.20.4 的 C），并且**用字体本体对象编码**，
不用 `getFont()` 取回的副本。

#### 1.20.6 实测五：生成脚本会被自己的测试污染

`tools/make_test_font.py` 的字符集是「从源码里出现过的字」扫出来的——
这样将来加了新测试、新文案，字体自动跟上。听起来很省事。

直到它把**测试文件里的探测字**也扫了进去：

```java
// 鿕 U+9FD5 不在子集里          ← 这一行里的「鿕」被扫进字符集
IllegalArgumentException boom = assertThrows(...);
```

于是重新生成后 U+9FD5 **在**字体里了，「缺字必须报错」那条用例变成**永远为真**。
（这个症状和 §1.19.9 里「`@Test` 注解被吞掉」是同一类：
测试自己把自己咬的东西放跑了，而全量单测完全无感。）

修法：**探测字必须动态挑**，不许写死码位——扫一段区间找第一个真缺的字。
字体里有什么就跳到下一个，测试永远在找一个真缺的字。字体子集变了也不用改测试。

#### 1.20.7 改了什么

| 项 | 改前 | 改后 |
|---|---|---|
| 字体来源 | 本机系统字体列表（macOS 3 个 + Windows 1 个） | **仓库自带子集**（Noto Sans SC 裁剪版，SIL OFL 1.1 可再分发） |
| 字体文件 | 无 | `src/test/resources/fonts/litemask-cjk-test.ttf` 1,214,072 B |
| 「本机没字体」 | `Assumptions` 跳过（静默覆盖洞） | **没有这条路了**——缺资源就是红 |
| 「跳过」计数 | 可能 >0 | **0**（实测 `Tests run: 949, …, Skipped: 0`） |
| 夹具嵌入方式 | `embedSubset=true` + `getFont()`（产出坏 PDF） | `embedSubset=false` + 字体本体（产出可用的 PDF） |
| e2e 样本字体 | 系统字体（Windows 上是 `.ttc`，必挂） | 仓库自带子集 |
| 授权 | 系统字体（不涉及分发） | OFL 1.1，附 `OFL.txt` 原文 |

**产物不进生产 jar**：`src/test/resources` 不进 shaded jar，90 MiB 预算不受影响
（§1.15 实测复核）。

新增守卫 `src/test/java/com/litemask/pdf/TestFontResourceTest`（6 条）：

1. 打包字体存在、可加载、且真的含中文字形（编得出「民」）；
2. 打包字体覆盖单测用到的每一个字；
3. 覆盖检查会把缺字**一次列全**（不是只报第一个）；
4. 字体集（`.ttc`）被**明确拒绝**，并给出正确做法（`TrueTypeCollection`）；
5. 夹具遇到缺字立刻失败，并给出「重新生成子集」的操作提示；
6. **夹具产出的 PDF 真的自带字体，且中文能原样抽回**（这条能抓住 §1.20.5 的替代字体退化）。

第 5 条为什么要额外断言「我们的提示词」：PDFBox 自己对缺字也抛
`IllegalArgumentException`（`No glyph for U+xxxx in font ...`），
只断言「抛了 IllegalArgumentException」分不出是**谁**在报错。

对照实验新增 4 条（ⓕⓖⓗⓘ），**变异目标是测试夹具而不是产品代码**——
这一组测的是「测试资源与夹具行为」，没有产品代码参与，唯一的证伪办法就是拆夹具。
这一点在脚本里写清楚了，免得读日志的人以为改了产品。

端到端也加了一步：拿打包的 `.ttc` 喂给样本生成器，**必须**被明确拒绝且给出提示，
否则端到端失败。这一步把「守卫自己有效」也纳入了端到端。

#### 1.20.8 这一轮的取舍与遗留

- **打包字体 1.16 MiB**，在仓库里、在测试资源里。选 GB2312 一级字库（3755 字）而不是
  「源码里用到的字」，是为了让将来的测试不必每次加中文都要重新生成字体；
  代价是产物大了 3 倍多。改法是 `python3 tools/make_test_font.py --charset sources`。
- **源字体没有随仓库**，脚本需要 `--source` 指向一份
  `NotoSansSC[wght].ttf`（Google Fonts 的 `ofl/notosanssc`）。这是有意的：
  17.7 MB 的可变字体进仓库不合适。**没有它就无法重新生成子集**——
  这是个真实的可复现性缺口，已写进本节。
- **Windows 侧仍未经真机验证**：本轮只证明了「测试不再依赖系统字体」，
  也就是「Windows 上不会因为字体而红」。`mvn test` 在 Windows 上到底能不能过，
  仍然要等 Windows 环境（§四 的未验证项）。

### 1.21 呈现层归组：把「一个地址被拆成三条命中」合成一条

#### 1.21.1 起点：§1.19.8 定论留下的那半件事

§1.19.8 定了：重叠时标识符被切多段，**维持拆分，不合并映射**——
合并会往映射里写一个「从未作为整体出现在源文件里」的原值。
那一节的结尾留了半件事：

> 后续要改的是**呈现**（界面上把同一原文相邻的命中归成一组展示），不是**映射内容**。

本节做的是那半件事。**映射一个字没动**，动的只有「界面上怎么显示」。

#### 1.21.2 先实测：切成多段真的会发生，而且三段是**严格相邻**的

写实现之前先量。用一个假的人名来源（把 `a.b`、`cn` 认成人名，优先级 900，
压过邮箱规则的 120），邮箱规则整段匹配 `a.b@x.cn` 后被切开：

```
原文: [备用 a.b@x.cn 联系人]  长度=15
脱敏后: [备用 <人名1><邮箱1><人名2> 联系人]
映射: {<人名1>=a.b, <邮箱1>=@x., <人名2>=cn}
命中段数: 3
  [0] rule=person   原值=a.b      区间=[3,6)  与上一段的间隔=-  令牌=<人名1>
  [1] rule=email    原值=@x.      区间=[6,9)  与上一段的间隔=0  令牌=<邮箱1>
  [2] rule=person   原值=cn       区间=[9,11) 与上一段的间隔=0  令牌=<人名2>
```

**间隔 = 0** 是这一节能成立的全部前提：三段在原文里是**连续的一段**，
所以拼出来的 `a.b@x.cn` 就是一个真实存在的子串，**不是编出来的**。
间隔只要大于 0，拼出来的东西在原文里就不连续——那就不是「显示得更友好」，
而是「报了一个源文件里没有的字符串」。

#### 1.21.3 三条硬条件

| 条件 | 不满足会怎样 |
|---|---|
| **严格相邻（gap=0）且同一文本单元** | 跨段拼出来的「标识符」在原文里根本不连续；跨内容流更是两段不相干的东西 |
| **每个成员的值在整篇文档里只出现一次** | 排除语义是「按值整体保留」：勾一个值＝这个值所有出现处都别脱。若某成员在别处还出现过，归组行只显示其中一处，勾它却会连带留下别处——**勾选粒度骗人**，比不归组更糟 |
| **拼出来的串不撞上文档里任何已有的命中原值** | 界面上会出现两行一模一样的值（一个是归组行、一个是完整命中），用户无从分辨 |

外加一条**整段判定**：一段连续相邻的命中，要么整段归组，要么一段都不归。
不去试它的子段——「为什么这两段归了、那两段没归」这种解释不了的界面更糟。
**宁可少归，不可错归**：少归只是行数多一点，错归是让用户在一个其实不相干的地方做决定。

实现落在 `core/HitGrouping`（新增，纯函数、不可变、线程安全）。

#### 1.21.4 改了哪些地方

| 层 | 改了什么 |
|---|---|
| `core/HitGrouping` | **新增**。归组算法：找「连续相邻的一段」→ 三条硬条件 → 通过则合成一条 |
| `docx/xlsx/pptx/ofd` 的 `Hit` | 各加三个字段：`start` / `end`（单元内偏移）与 `unit`（文本单元 id）。偏移取自引擎的 `Change`，本来就是单元内坐标 |
| `server/DocumentService` | `Raw` 带位置；`aggregate` 先归组再按 `(规则键, 原值)` 聚合；`HitItem` 加 `members` 与 `valueCount()` |
| `server/JobStore` | 排除项按**成员**逐个对账；清单 JSON 回传 `members`；**归组行必须整行排除**（见 §1.21.7） |
| `web/app.js` | 归组行加「原文里紧挨着的 N 处命中」标注与底色；勾选时**按成员展开成 N 条排除项** |

`unit` 的构造用**长度前缀**（`HitGrouping.unitId`）：部件名（zip 条目名）里可以出现任意字符，
直接拿分隔符拼会撞车——部件 `a@b` 配局部名 `c` 与部件 `a` 配局部名 `b@c` 拼出同一个串，
于是两个不相干的单元被当成同一个，归组就会把两段不相干的内容拼成一个「标识符」。

#### 1.21.5 计数语义：一律按「值」，不按「行」

归组后一行可能代表 N 个值。于是：

| 字段 | 含义 | 归组后的取值 |
|---|---|---|
| `summary.distinctHits` | 值的个数 | 3（不是 1） |
| `summary.rows` | 清单里的行数 | 1 |
| `summary.occurrences` | 命中总处数 | 3（不受归组影响） |
| `summary.excluded` / `redacted` | 被保留 / 被脱敏的**值**数 | 按值算 |

理由：用户勾的是**值**，脱敏的也是**值**，报告里写「保留 3 个值」才与实际相符。
写「保留 1 行」会让用户以为只留了一处。界面上的摘要因此多了一句「（清单里归成了 1 行）」，
行数与值数都对得上。

#### 1.21.6 映射一个字没动（实测）

`a.b@x.cn` 归成一行之后：

- 映射仍是 **3 条**（`<人名1>=a.b`、`<邮箱1>=@x.`、`<人名2>=cn`）；
- 文档里仍是 **3 个令牌**（`<人名1><邮箱1><人名2>`，紧挨着）；
- 还原逐字一致。

**合并会写出一个源文件里从未整体出现过的原值**，用户拿映射去核对源文件时找不到这个字符串；
真当审计证据用，更是拿一条「工具自己编出来的原值」去证明「源文件里有这个值」。
代价可见，编造不可见——后者更危险。

#### 1.21.7 fail-closed：归组行只排除一部分 → 请求当场失败

界面上归成一行的是若干处命中，勾这一行发回来的是 N 个 `(规则键, 原值)` 对。
如果只发回来 N−1 个（浏览器脚本写错、或者有人手工构造请求），
文档里会留下**保留了一半的标识符**——用户要的要么是「这个地址别动」，
要么是「这个地址脱掉」，没有第三种。

所以服务端**让请求失败**（400），并说清怎么做：

> 有一行命中只排除了 1 / 3 处：这一行是原文里紧挨着的若干处命中拼成的，要保留请整行勾选（否则会留下保留了一半的标识符）。

这与 §1.19 里 `verifyExclusionsMatch` 是同一条纪律，只是触发条件不同
（那边是「排除项对不上」，这边是「只排除了半行」）。**宁可让请求当场失败，
也不要一份「看起来成功、实则没按要求处理」的结果。**

#### 1.21.8 PDF 侧不归组——并且**显式声明**

`Change` 在 PDF 里被摊平成一串，**丢了内容流单元 id**：
各段命中的偏移是各自内容流块内的坐标，跨块比较毫无意义。
此时宁可不归组，也不能拿「偏移看起来连着」当「原文里紧挨着」。

但**不能静默跳过**。凡是有命中的 PDF，notes 里都会有一句：

> PDF 按内容流处理，界面无法判断两处命中在原文里是否紧挨着，因此被不同规则切开的标识符仍会显示成多行（docx/xlsx/pptx/ofd/txt 会归成一行）。

这句话是**关于工具能力的话**，不是对这份文档的断言——所以无论这份 PDF 里
有没有真的被切开的标识符，它都成立，不会出现「说了假话」的情况。

#### 1.21.9 顺带修掉的一个假话

原来的位置截断提示是这么算的：

```java
if (h.locators().size() < h.occurrences()) { truncated++; hidden += ...; }
```

PDF 的 `locators` 恒为空（它没有位置信息），而 `occurrences` 是 1 ——
于是**每一份 PDF** 都会被算成「有 N 个值出现次数超过 20 次、另有 N 处未展开」，
而那些值其实只出现了一次。**那句话对 PDF 是假的。**
现在先看 `hasLocators()`，PDF 不再报位置被截断。

#### 1.21.10 这一轮的取舍与遗留

- **相邻的两个不同人名也会被归成一行**（比如「张三李四」被模型认成两个「人名」）。
  归组条件只有「严格相邻」，工具分不出「这两个人」与「一个人的两段」。
  界面上的标注写明是「原文里紧挨着的 2 处命中」，映射也仍是两条——
  信息没丢，只是显示上合成了一行。**这是本轮接受的代价**，不是漏洞。
- **浏览器那半边没有自动化测试**（本项目一直没有，明确的验证缺口）。
  「勾选按成员展开成 N 条排除项」这件事只有静态断言守着
  （`WebUiTest` 断言脚本里存在 `members.forEach` 与逐个 `excluded.push`），
  **没有真人验收**。真正的安全网在服务端：半行排除会被 §1.21.7 挡住。
  > **更新（2026-10-19）**：浏览器那半边**已经有自动化测试了**——
  > `tools/e2e-browser.sh`（自建 CDP 驱动、真 Chrome、42 条断言 + 2 条负控制），
  > 见 `docs/M2-c-阶段状态.md` §5.8。
  > 上面这段是**本块交付当时**的状态，保留以示当时的口径；

- **PDF 不归组**（§1.21.8）。
- **归组只认「单元内偏移」**：docx 是段落、xlsx 是单元格、pptx 是形状、
  ofd 是 TextObject、txt 是整篇。跨单元一律不归。

### 1.22 对照实验工具自己的三个缺陷：都是「报了一个假的结论」

§1.21 那轮跑完 118 条全量对照实验，收尾报的是：

```
=== control experiment end: pass=116 fail=2 invalid=2 / 脚本共 118 条 ===
X 判过的 120 条 ≠ 脚本里声明的 118 条；有实验没被执行，pass 是个残缺的分子
```

**这三行里没有一行是准确的**：

| 它说 | 实情 |
|---|---|
| `fail=2` | 真实失败 **0** 条。那 2 条是 **INVALID**（锚点没命中），`fail` 把 invalid 又数了一遍 |
| `invalid=2` | 是的，2 条作废——但**原因不是变异体编译失败**，是锚点漂移 |
| 「有实验没被执行」 | 118 条**全部执行了**。120 是重复计数算出来的 |

更要紧的是：**收尾那一行把读的人导向完全错误的方向**。
「有实验没被执行」会让人去查 `ONLY` 过滤、查函数名拼写——
而真正的问题在别处（源码改了，锚点没跟着改）。

下面几条是本轮实际修掉的。

#### 1.22.1 改一个方法签名，就把它对应的对照实验弄瞎了

**现象**：改完代码跑全量，两条实验判 INVALID：

```
X 破坏㉜：不处理 TextCode 的关键字属性（正文脱了但检索仍搜得到原文） 变异点未命中，实验无效
X 破坏⒚：聚合键不用分隔符（两类命中串成一坨） 变异点未命中，实验无效
```

**原因**——两条都是本轮我改过签名的地方：

| 实验 | 锚点原来指向 | 我改了什么 | 现在指向 |
|---|---|---|---|
| ㉜ | `redactTextAttribute(code, "Text", session, name, hits)` | 给它加了 `unitLocal` 参数（`"TC" + i`） | 签名多了一个参数，字面量不再匹配 |
| ⒚ | `String key = raw.ruleKey + "\u0000" + raw.original;` | 聚合键抽成了 `值键()` 辅助方法 | 那行字面量已经不在了 |

**为什么这件事值得单列一节**：§1.20 已经记过一次同样的坑
（「抽公共类」这种重构必然动锚点，重构完就该重跑这几条）。
本轮再次踩中，说明**「记得重跑」靠不住**——靠的是记性，而记性不是工程手段。

而且这次的失效方式是**静默的**：脚本判 INVALID、整场失败、退出码非 0，
看起来很安全。但 **INVALID 的含义是「这一项没提供任何信息」**——
它咬不咬得住是**未知**的。脚本没有放它过关，可它也不是「测试有问题」。

**修法**：把锚点改成当前源码里真实存在的字面量，并重跑这两条。
改完两条都 PASS（㉜ 让 `OfdRedactorTest` 失败 1 条、⒚ 让 `AggregateKeyTest` 失败 2 条），
基线复核 GREEN。

**顺带修的第三处**：`破坏⒈`（六层 XXE 防护一起拆）里的一组锚点
`factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);`
在源码里**出现 2 次**——一次在 `parse()`（XXE 防护，本次要拆的那处），
一次在 `serialize()`（`TransformerFactory`，与 XXE 无关）。
`mutate` 只替换第一处，所以**当时行为是对的**；
但一旦有人调整了代码顺序，变异就可能落到序列化侧，那条实验就白做了。
锚点加了上下文（连着下一行 `ACCESS_EXTERNAL_DTD`）变成唯一。

#### 1.22.2 给脚本加了 `AUDIT=1`：静态体检锚点，秒出

**问题**：发现锚点漂移的唯一时机是「整场跑完看收尾」——那要几十分钟。
而此时「这条实验原本守的是什么」已经没人记得了。

**做法**：`AUDIT=1 ./tools/control-experiment.sh` **只读源码、数锚点命中次数**，
不跑测试、不改任何文件，秒出结果：

```
=== 锚点体检：131 个锚点，0 处有问题 ===
全部命中且唯一。
```

**关键实现选择：复用 bash 自己的参数解析，不另写解析器。**

第一版我另写了个 Python 解析器，结果**漏判了 41 条**（多行锚点被切开，
`shlex` 直接报 "No closing quotation"），报出来的「问题」全是假的——
比如把 `破坏⒈` 的六组三元素拆成了十二组。

判据：**工具的解析语义必须与被测对象的语义一致，否则它报的问题就是噪声。**
锚点里有嵌套引号、多行文本、空串，bash 的引号规则很具体，
另写一个解析器必然有偏差。**让 bash 把参数原样递进来**，语义与真正执行时完全一致。

体检还报「命中 N 次（不唯一）」——这一项是体检比真跑多出来的东西：
真跑时 `mutate` 用 `replace(..., 1)` 只替换第一处，
所以「不唯一」在真跑时**不会立刻出事**，但它是颗定时炸弹。

#### 1.22.3 `run_case_multi` 每跑一条就漏一个临时目录

**现象**：一轮跑完，TMPDIR 下积了 **11 个**临时目录，
每个里面躺着源码的完整副本（`*.orig`）。日志里 `rmdir` 报错 5 次。

**原因**：`rmdir` **只能删空目录**，而备份文件还在里面。代码是：

```bash
for f in ${unique//|/ }; do cp "$tmpdir/$(basename "$f").orig" "$f"; done
rmdir "$tmpdir"          # ← 目录不空，失败
```

**修法一（不够）**：先 `rm -f` 掉每个 `.orig` 再 `rmdir`。实测**仍然失败**——
因为目录里还有 **`.DS_Store`**：macOS 的 Finder 会自动往任何被它看过的目录里塞这个文件，
它与本项目毫无关系，却足以让 `rmdir` 永远失败。

**修法二（采用）**：整目录 `rm -rf`。这里用 `rm -rf` 而不是回收站：
这个目录是**脚本自己刚 `mktemp` 出来的**，路径不含任何用户输入，
而且它必须在同一轮实验里立刻消失——留着它等于留着源码副本。

> 顺带记一笔同类的事：`${unique//|/ }` 是**不带引号**的展开，靠 IFS 分词。
> 本项目的路径里有中文但**没有空格**，所以现在是安全的。
> 哪天路径里出现空格，这行会静默地拆错、还原不完整。
> 现在没改，是因为它没有真实发生过——但记在这里。

#### 1.22.4 汇总行把「作废」算成了「失败」，还报了一个假的「有条实验没被执行」

**两处计数错误**：

1. `judged = pass + fail + invalid`，而每处 invalid 都会**同时** `invalid++` 和 `fail++`
   （invalid 是 fail 的子集，两者都要让整场失败）。于是 invalid 被算了两次：
   实测 116 过 + 2 作废 = 118 条，`judged` 却算出 120。
2. 收尾打 `fail=2 invalid=2`，读起来像「2 条没咬住 + 2 条作废」（4 条出问题），
   实情是只有 2 条有问题、且都是作废。

**为什么这比数字错更严重**：那一行报的是
**「有实验没被执行，pass 是个残缺的分子」**——
这个结论与实情（118 条全部执行了）**相反**。
读的人会去查 `ONLY` 过滤、查函数名拼写，而真正的问题在源码里。

**修法**：

- `judged = pass + fail`（invalid 已含在 fail 里，不能再加一次）；
- 汇总行报 `fail=<真失败数>`（= `fail - invalid`），invalid 另列。
  **「真失败」才是「测试没咬住」**——那才是需要改测试的信号；
  作废是「这条实验没提供任何信息」，修法完全不同（改锚点，不是改测试）。

#### 1.22.5 这一轮的取舍

- 体检只说「锚点会命中」，**不说「变异有效」**。
  修完锚点必须**真跑那几条**（本轮三条都真跑了，都 PASS，基线 GREEN）。
  「体检全绿」不能替代「跑一遍全绿」。
- 体检报「命中 N 次」是它比真跑多出来的一项，不一致的地方要靠人判断
  （本轮⒈ 的第二处在 `serialize()`，与 XXE 无关，所以是加上下文而不是删实验）。
- 临时目录的泄漏**不体现在任何测试或计数里**——它是「只有人去看才会发现」的一类。
  这一条是本轮手工翻 TMPDIR 才发现的。

## 二、评测集是怎么建的，以及它**不能**证明什么

`tools/gen_legal_eval.py` 生成，`tools/LegalEvalProbe.java` 评测。

### 2.1 三条硬约束（都是代码断言，不是注释里的声明）

1. **实体表面串与 MSRA train 零重叠**——脚本把生成结果与 train 里出现过的
   17826 个 PER/ORG 求交集，非空即退出。留出集里只要有一个名字两边都有，
   F1 就分不清哪一分是泛化、哪一分是记忆。
2. **不参与训练**——生成物写到独立目录，训练脚本的数据路径不包含它。
3. **句式来自法律文书**，与三个训练来源（人民日报新闻 / 微博短文本 / 名单式合成）都不同。

### 2.2 它**不能**证明什么（这一段不能省）

- 它是**模板合成**的，不是真实法律文书。真实文书的句式多样性远高于这里的 9 个模板，
  所以这个 F1 是**上界估计**，不是现场错误率。
- 它只覆盖 PER / ORG 两类，不覆盖本项目其他实体类型。
- 它量的是**模型识别质量**，不包含冲突消解、排除项、还原这些下游环节。
- 要回答「本工具在真实卷宗上的错误率是多少」，需要真实脱敏样本，
  而那属于用户侧的数据，本项目拿不到。

结论：它能回答「模型能不能在法律文书这种句式上认出人名机构名」，
**不能**回答「本工具在现场准不准」。

## 三、为什么分成主集与附集：一个 33% 的坑

第一版只生成了一个集，F1 是 **0.3867**。拆开看才发现问题出在评测集自己身上：

**19 个生僻字（乜仉儋埇扈昝歙澹瑄盱眙睢秭訾郗郜郫阚隰）不在模型的 4586 字词表里。**
845 个实体中有 276 个（33%）至少含一个字走 UNK embedding。

那个 F1 量到的**不是泛化能力，是词表覆盖**。两件事必须分开：

| 评测集 | 未登录字 | 完全由已登录字组成的实体 | F1 |
|---|---|---|---|
| 主集 | **0** | 755/755 (100%) | **0.5376** |
| 附集 | 19 | 568/864 (65.7%) | **0.3816** |

主集测「组合与句式的泛化」，对应 0.9 验收线；
附集测「模型没学过那些字时会发生什么」，那是**真实的业务限制**，要报告而不是藏起来。

> 附集那 19 个字是真实存在的姓氏（眭、仉、訾、郗、阚…），
> 真实法律文书里会遇到。这不是评测集的缺陷，是模型的已知短板，
> 报出来比藏起来有用。

## 四、评测器为什么在 Java 侧、标尺为什么独立

`tools/LegalEvalProbe.java` 走**只读产物**的路径：磁盘模型包 → 七道闸 → ONNX →
`SequenceDecoder` → `NerEntitySource`。不用训练脚本里那个 torch 模型。

理由是本项目已经吃过这个亏的实体版：训练日志打印 F1 0.8397，
拿导出的 `.onnx` + `vocab.txt` 重新打分只有 0.1209——
**两个文件各自都合法，合起来才不合法**。训练侧的数字不能代表产物。

标尺（BIO→span、预测归一化、P/R/F1）**全部独立实现**，一行都没有复用
`SlidingWindowNer` / `SequenceDecoder` / `NerRecognizer`。被测的是「模型准不准」，
标尺若与被测共用实现，测出来的就是「实现自洽」。

### 4.1 一个真实的标尺事故

交叉验证时，`read_msra` 报 3777 个实体、生成器报 1259，差三倍。
查下来是**我的一次性验证脚本写错了**：`for _, t in sents` 解出来的是**文本**不是标签，
而 `spans_from_tags` 传字符串会走 `KeyError`。

正确的三个口径（生成器自报 / `read_msra` + `spans_from_tags(tags)` / 直接数 `B-` 行）
**都是 1259**。教训：两个数字对不上时，先怀疑自己的验证代码，
再怀疑数据——尤其当其中一个数字「看起来更详细」的时候。

## 五、下一步该修哪一类，以及为什么先不修评测集

三类错误对应三种完全不同的修法：

| 现象 | 数量 | 根因假设 | 修法 |
|---|---|---|---|
| ORG 误报 227 个 | 大头 | 训练集里 ORG 形态单一（多为「地名 + 公司/大学」），法律文书里「地名 + 字号 + 行业后缀」的三段式没见过 | **补训练覆盖** |
| 漏检「完全没认出」454 个 | 大头 | 同上：法律文书的角色词上下文（`法定代表人：`、`鉴定机构为`、`审判长`）训练里没出现过 | **补训练覆盖** |
| 边界重叠但切错 273 个 | 次要 | CRF 转移与滑窗边缘规则在长上下文下的表现 | 调解码，不是调训练 |

**为什么不改评测集让它变好看**：机构名写成「桦甸泰合建筑工程设计研究院」

## 六、已知限制 / 未验证

### 本轮新增

- **v8 未验证能否用更长训练补回来**：只跑了 30 epoch，判定为负结果是基于
  「训练 loss 从 epoch 0 就更高」+ 三个外部集同向退化。要证伪需实跑
  `--dilations 1,2,4,8,16 --epochs 60`，**本轮没做**（见 §1.13）。
- **v9 未跑多种子**：定版依据是附集 +0.0785（6 个 se）与 cluener +0.0471，
  幅度远超噪声，但**单次训练仍没有方差估计**。要给出方差需多个种子各跑一遍。
- **宽度 512 未测**：按算术需 +13.4 MiB，余量 14.59 MiB **装得下但只剩约 1.2 MiB 缓冲**。
  本轮没有跑——缓冲太薄，且 384 已经拿到 6 se 的收益，边际收益需要实测确认而非算术。

  没测长文档、没测批量、没测内存峰值。**在一个真实 200 页卷宗上的表现未实测。**
- ~~**`pom.xml` 的 user.home 隔离只作用于 surefire**~~ —— **已于 2026-10-19 修复**，
