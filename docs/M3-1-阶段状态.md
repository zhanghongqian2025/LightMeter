## 1. 解码层：为什么它比想象中重要

NER 的最终输出 = 模型分数 → 解码 → 实体区间。这条链上，
**模型的分数是可以换模型、可以重训的，唯独解码层的错误不会被任何后续环节发现**：

| 错误 | 现场 |
|---|---|
| 解出没有开头的实体 | 正文里凭空多出一个单字实体 |
| 丢掉被截断的实体 | 某个机构名整个消失，且报告数字正常 |
| 采信切边的半截 | 多脱一段不存在的名字 |
| 同一实体报两次 | 界面上两行、两个令牌、映射表一个原值对两个令牌 |

**共同点：全部静默。** 报告里的命中数、令牌编号、脱敏后的文档看起来都正常。

## 2. 三个设计决定

### 2.1 Viterbi + BIO 结构约束，两层都不可省

- 只有转移分数：解码器可能选出一条结构非法的路径（`I-机构名` 前面既不是 `B-` 也不是 `I-`）。
- 只有结构约束：整段文本上的置信度比较被丢掉。

`TagScheme` 把结构规则显式化并在**构造期**严格校验——
残缺的标签方案来自离线导入的模型包，「尽量兼容地放行」会让通道号被解释成不相干的实体类型，
于是公司名被人名规则吃掉，而报告一切正常。

另外补了一条**开头约束**：`I-` 不能出现在序列开头。放任它的话，
模型在窗口首字给高分的 `I-`（多半因为实体从窗口外延续进来）会被当成实体，
**文档第一行被凭空脱掉一个字**，且没有任何提示。

### 2.2 滑窗用「边缘不可信」，不用「归属区投票」

第一版是**归属区**：每块两端各让出一个 overlap 作为归属区，只有完全落在归属区的观测算票。
测试立刻打脸——**跨窗口的实体两边都拿不到票，整个消失**。

根因：归属区必须在两端各让出一个重叠宽度，而块只推进 `maxChars - overlap`，
于是**相邻块的归属区之间必然留一段空洞**。现场是「大部分实体都对，只有跨块那几个没了」，极难归因。

改成单规则：

> 采信条件 = 实体完全落在某块内 **且不触碰该块被切开的那条边**；
> 文本真正的首尾**不算**被切开。

跨边界实体总有一个窗口能完整看见且不贴切边 → 自动采信；
每块贴切边的那几个字由相邻块负责；被截断的半截实体因为贴切边而自动被挡掉，不需要额外规则。

**必须同时测正反两面**：贴切边的观测要丢、**贴文本首尾的不能丢**。
只测会丢的那一面，会把「文档第一行和最后一行被漏掉」放过——
而那恰恰是最该脱的两处。

### 2.3 标签方案不写死在代码里

通道数由模型包提供。写死 5 个标签的话，换模型包就得改代码，
而那正是最容易「改了代码、忘了改界面标签」的地方。
`EntityType` 仍然是枚举——模型可以只带它支持的子集，但代码这边必须有一份已知清单，
否则来路不明的标签会直接变成一条脱敏规则。

## 3. 测试标尺：穷举，不是再写一遍 DP

解码器是 Viterbi，但测试的 oracle 是**暴力枚举所有合法标签路径**（T≤5，最多 3125 条），
160 组随机对账全部一致。

两者唯一的共同点是**那个数学定义**（最大化所有合法路径的总分），
实现方式毫无关系：一个是穷举，一个是动态规划。这才是独立标尺——
「再写一遍 Viterbi 看看一不一样」只能证明两份代码抄得像。

> **这条也踩了一次坑**：给解码器加「开头不能是 `I-`」之后，
> 穷举器还按旧规格判合法，DP 解出 `[1,2]`、穷举解出别的路径，
> 红灯**看着像解码器有 bug**，其实是对账的**规格**不同步。
> 独立标尺要独立**算法**，但**规格必须对齐**。

### 3.1 「变异后仍全绿」四种成因

这轮把四种全撞了。它们都显示成同一个 GREEN，修法完全相反：

| 成因 | 本轮实例 | 修法 |
|---|---|---|
| **锚点漂移** | ⒚：M2-c1 改了 `RedactionEngine.redact` 签名，脚本锚点还是旧行 | 改锚点 |
| **空操作变异** | ⒟ 第一版：`putIfAbsent` → `put`，值相同、Map 里还是一条 | **改变异**（去重键多带窗口号） |
| **测试不敏感** | ⒞ 第一版：xlsx 表名排在单元格之后，改变不了序号归属 | 改测试 |
| **前提被架空** | ⒚ 新测试：被排除的命中不进 `changes`，合并后剩的那条键恰好与正确实现一致 | 加前提断言 |

## 4. 模型自包含校验

这是 §3.1 那个「残留未知」的处理办法：**不等厂商发版，从设计上让外部数据无从发生**。

### 4.1 为什么不靠字节搜索

ONNX 的「外部数据」把权重存在 `.onnx` 之外的 `.data` 文件里，加载时按路径打开它们——
这一族正是路径穿越 / 符号链接遍历漏洞的入口。

而**权重就是几千字节的裸数据，里面出现形似字段号的字节几乎是必然的**
（`0x6A` = `13<<3|2`，正是 `external_data` 的标签）。
用「扫字节找关键字」去判，必然误报，**误报的代价是所有合法模型都加载不了**——
那道闸门会退化成「一律拒绝」，等于没有。

所以这里按 protobuf 线格式**按路径**走：

```
ModelProto.graph(7) → GraphProto.initializer(5) / sparse_initializer(15) → TensorProto
                                                                              ├ external_data(13) 出现即拒
                                                                              └ data_location(14) != 0 即拒
权重 raw_data(9) 当成字节整段跳过
```

刻意不解析未知的嵌套结构——那需要完整 schema，而这里只需要顶层字段号与线类型就能正确跳过。

### 4.2 解析不了就拒绝

连 `graph` 都找不到、varint 截断、长度前缀越界、出现已废弃的 group 编码——**一律拒绝**。

「没扫到外部数据」和「文件是干净的」是两件事。解析失败时返回「通过」，
就是把**「没检查」说成「没问题」**，正是本项目质量红线第 6 条要区分的那两种状态。

### 4.3 两种失败要能被上层区别对待

| 异常 | 含义 | 上层该怎么说 |
|---|---|---|
| `ExternalDataRejected` | 模型是我们**不接受**的那一类 | 「这个模型包不适用，请换一个自包含模型包」 |
| `IllegalArgumentException` | **文件本身损坏** | 「模型文件已损坏」 |

前者可以引导用户换包，后者是数据问题——混成一句话会让用户去反复重下同一个坏包。

### 4.4 判错一次的代价不对称

| 漏判（该拒没拒） | 误判（不该拒拒了） |
|---|---|
| 加载时去读本机任意文件 | 所有模型都用不了 |
| **安全问题** | **功能不可用** |

两者都不该发生，但**这道闸门的主要防线是「设计上不产生外部数据」**（模型包只允许清单里的文件），
扫描是第二道。第一道失效时第二道兜住，第二道失效时第一道还在。

## 4.5 推理链路的测试夹具：手写的玩具 ONNX 模型

M3-1c 要接上 ORT。**测试不能拿真实训练模型当输入**：权重一改测试就红，
而红的原因不是代码缺陷；期望值也只能靠「再跑一遍 PyTorch」得到——
和 Java 共用同一份权重，一致时看不出问题，不一致时说不清谁对。

所以用 `tools/make_ner_fixture.py` 生成一个**只有一层 Gather 的玩具模型**：

```
out[0, t, :] = table[ids[0, t], :]
```

字符 → id 的映射和每一行的 7 维 logits **全部写死在脚本里**，
期望实体（`张三丰` / `北京大学` / `上海`）可以在 Java 测试里直接手写出来，
**标尺完全独立于被测实现，也不依赖任何机器学习框架**。

用**标准库手写 protobuf**（不依赖 `onnx` 包），满足「脚本在别的机器上可复现」。

产物 `src/test/resources/ner-fixture.onnx`，1,969 字节，
SHA-256 `e00031d469708b610b7348d04d35f58027243d1b0c8dc3aaeee835a563b080a7`。

### 交叉验证（本轮实跑）

手写 protobuf 必须被**两个独立实现**验证过才算数：

| 步骤 | 结果 |
|---|---|
| `onnx.checker.check_model(full_check=True)` | 通过 |
| `onnxruntime.InferenceSession` 真实加载 | 通过，`[1,N] int64 → [1,N,7] float32` |
| 输出与独立重建的期望表逐元素比对 | `np.array_equal → True` |

比对时验证脚本**刻意不引用生成器的任何函数**，
而是从第一性原理重建期望表（先铺 `[-5]*7`、再把 `O` 抬到 `+5`、再改实体行）——
否则就退化成「用被测代码验被测代码」。

### 这个夹具抓到的三个真 bug

1. **`Gather` 参数顺序写反。** ONNX 规定 `Gather(data, indices)`，
   我写成了 `Gather(indices, data)`。**`onnx.checker` 的普通模式查不出来**（它默认不做算子类型推导），
   只有 ORT 加载时才报 `Type 'tensor(float)' of input parameter (table) ... is invalid`。
   读起来像「权重类型不对」，实际含义是「这个参数被当成 indices 了，而 indices 必须是整型」。
   **教训：静态校验必须用 `full_check=True`，并且要真的加载一次。**
2. **构造期望表时验证脚本自己写错了底**（用全 0 而非 `[-5]*7`），
   一度把差异指向模型。判别方法是先看差异矩阵的形状：一行 `[-10,0,0,…]`
   说明两边都命中了同一个 id，是基准表的初始化不对，不是模型算错。
3. **`tag=None` 走了实体分支。** 字典里用 `None` 表示「这个字符不构成实体」，
   但代码仍对它调用 `entity_row(None)`——`None` 不等于任何标签，
   于是**七个标签全部落到 `-5.0`**，普通字符变成了「没有 O 倾向」。
   表现是 argmax 仍挑到通道 0，但分数是 `-5`，数值完全对不上。
   **只有真正做一次数值比对才会暴露它**；靠看 argmax 的标签名会以为是对的。

## 6. 已知限制与缺口

1. **这一层没有任何真实模型喂进去过。** 目前的证据是「给定标签分数，
   解码与合并是对的」。**模型本身的准确率完全未测**，那是 M3-3 的事。
2. **模型包的整体校验还没做**：清单、签名、版本、解压加固（路径穿越 / 条目数 / 炸弹预算）
   都还没写。当前只有「模型文件自包含」这一道。
3. **字符级分词没做**。中文没有空格，字符级最稳且与模型无关，
   但未登录生僻字只能退化成 UNK——而机构名里恰恰爱出现生僻字。
4. **窗口大小与重叠宽度是构造参数，没有依据**。目前是调用方给什么就用什么，
   没有「实体最长多少字」这个来自模型的口径。
5. **同一段文字被两个窗口给出不同类型判断时两条都保留**，这是刻意的
   （不悄悄二选一），但**差异目前没有任何机制去暴露**——那是 M3-3 一致性检查的事。
6. **Windows x64 的 ORT native 体积仍未知**（本机测不了），M4 打包前必须在 Windows 侧实测。
