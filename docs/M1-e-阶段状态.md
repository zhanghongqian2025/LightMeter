## 覆盖范围：OFD 的坑全在正文之外

OFD 与 OOXML 同构（zip + XML，文本藏在少数几种节点里），所以实现是**对包内每一个 XML 部件
做一次深度优先遍历**，靠元素名识别载体，而不是按目录约定去找那几个文件。

| 位置 | 样例文件里的实际内容 | 漏了会怎样 |
|---|---|---|
| `Pages/Page_N/Content.xml` | 正文 TextCode | 正常场景 |
| `Tpls/Tpl_N/Content.xml` | **模板页，屏幕上看不见** | 文件里留着身份证，正文清清爽爽 |
| `Annots/.../Annotation.xml` | 批注/水印里的 TextCode | 批注区的邮箱 |
| `TextCode/@Text` | 关键字属性 | 正文脱了，但**全文检索仍搜得到原文** |
| `OFD.xml` 的 `DocInfo/CustomData` | **发票号码、两个纳税人识别号** | 打开属性面板就能看到 |
| `OFD.xml` 的 `DocInfo/Author` | 人名 | 正则永远命中不了，只能清空 |
| 无 `TextObject` 祖先的孤儿 `TextCode` | 规范不该允许，但存在 | 静默漏脱，且不报错 |
| `Attachments.xml` + **zip 条目名** | `Attachs/13800138000_申请书.pdf` | XML 引用改了、文件名留着，一样泄露 |
| `Doc_0/Signs/**` + `<ofd:Signatures>` | 签章部件与引用 | 留下一个必然验不过的死签名 |

其中最值得记的是 `CustomData`：那张真实发票的
`DocInfo/CustomDatas/CustomData` 里直接写着发票号码 `24112000000048542163` 和两个
纳税人识别号 `91110108690017781B` / `91460300MAA92DJN95`。**只看正文的实现会理直气壮地
报告「已脱敏」，而这三个值原封不动躺在文件里。** 这就是「静默漏脱」的典型形态——
文件正常生成、工具正常报告成功、内容还在。

## 三条刻意的取舍

### 1. 不跨 `TextObject` 合并文本

组内拼接只做在**同一个 `TextObject` 的多个 `TextCode`** 之间（`TextCode@X` 是对象内横向偏移，
一个号码被拆成「1390013」+「9000」是真实存在的，逐槽跑正则必然漏）。
但**不跨对象**。

理由不是保守，是版式：OFD 是绝对定位版式，跨对象合并只能靠几何启发式，而**发票这类多栏文件里
左右两栏的 y 完全相同**——一合并就把两栏拼成一条原文不存在的字符串，轻则假脱敏，重则把版面改坏。
宁可少认，也不在版式文件上赌。独立读取器也证实了这一点：ofdrw 自己抽出来就是两行，不会帮你拼。

### 2. 不改 `DeltaX`

`DeltaX` 是逐字字距表，数量必须与字符数一致。改了就丢了：按新长度裁剪之后，
还原时只剩前 N 个值，**再也回不到原值**。留着它的代价是脱敏后数量可能多于字符数
（阅读器按字符数取用，多出来的忽略），换来的是还原后与原文件一致。

对照实验 ㉟ 专门盯住这条，防止将来有人「顺手优化」把它裁掉。

### 3. 路径字符串一律不走引擎

附件条目名和指向它的 `FileLoc` 必须拿到**同一个**令牌，否则引用会指向不存在的条目。
如果两边各自跑一次引擎，分配器按先到先给的规则会发出两个不同编号，
结果就是「文件名改了、引用还指着旧名」。所以只认一张改名表，XML 里的路径字符串也只由它改。

改名表还分「全条目名」和「裸文件名」两张：裸文件名在包里可能重名
（`Res/a.pdf` 与 `Tpls/a.pdf`），按裸名替换会把另一处引用一起改坏。全路径永远安全，
裸名只在全局唯一时才允许替换。`ZipXmlPackage.writeZip` 会检查重名并直接报错——
两个附件都被脱敏成同一个令牌名时，zip 里出现重名条目，阅读器只会看到其中一个。

## 还原的两条不对称

还原做的是**把令牌替换铺满全部叶子文本与全部属性值**，而不是照着脱敏时的载体清单再走一遍。
脱敏必须逐类枚举载体（多改一处就是误伤），还原却可以只认一个不变量：**令牌只会出现在
我们写进去的地方**。照单枚举反而会漏——附件改名后同步替换进去的路径字符串不属于任何一类载体，
漏掉它的后果是「文件改回来了、引用还指着新名字」。

换不回来的三样，写进了类注释和用户文档：

1. `Author` / `Creator`：直接清空，原值从未保存（不保存正是「不留原文」的意义）。
2. 签章：脱敏改动了页面内容，原签名必然验不过，删掉并明确告知比留一个死签名诚实。
3. **跨 TextCode 的段结构**：令牌整个写进第一个槽，后面的槽被清空。还原后文字与原文完全一致，
   但原来分散在三个 TextCode 里的那串数字会连成一个。docx 里这看不出来（文字自动回流），
   OFD 里位置会有肉眼可见的偏移。要真正复原得额外记录「原文按什么切分写进每个槽」，那是 M2 的数据结构。

## 附带的一次重构

`OoxmlSupport` 改名 `ZipXmlPackage`（`com.litemask.ooxml` → `com.litemask.zipxml`）。
它对 OOXML 没有任何特殊逻辑，OFD 接进来之后那个名字就开始骗人了。

走**命令行 + 打包后的 jar**，校验器是 `tools/verify_ofd.py`——用 Python 按规范重写了一遍

改名 1 个附件条目且内容保留；移除 4 个签章条目；**全包字节扫描 8 个原文值 0 残留**
（含 zip 条目名）；往返 144 字符去空白后逐字相同；fat jar 5.94MB。

脚本里有两个细节值得留着：

- **样本自检（`require`）**：脱敏前先断言那些值确实在文件里，否则后面的「0 残留」是空转。
- **拆开的那串手机号不能用它自己校验**：它被切进两个 `TextCode`，从来就不是一段连续字节。
  能证明的是它那两半——脱敏前在、脱敏后不在。

## 如实呈现的局限

- **不跨 `TextObject` 合并**：两个相邻 `TextObject` 拼出来的号码识别不到（见上文理由）。
- **不做版面补偿**：令牌比原值短会留一段空白，但不会重叠、不会错位。真正补版面要字体度量。
- **段结构还原不回来**：文字一致，切分方式不一致。
- **`DocID` 不脱敏**：它是文档标识符（哈希），一串 18 位十六进制完全可能碰巧通过身份证校验位，
  脱敏会造成莫名其妙的误脱还会改掉文档标识。这条有测试专门钉住（它是决定，不是遗漏）。
- **加密 OFD 不支持**：内容 XML 被加密时解析失败，按 fail-closed 报错。
- **OFD-A 档案模块（GB/T 42133）未处理**。
- **印章图片里的文字是位图**，本工具不做 OCR。
