# M3-1d 阶段状态：砍掉 java.desktop

## 一、结论

`ServeCommand` 原来用 `java.awt.Desktop` 开浏览器，只为这一件事拖进了整个 `java.desktop` 模块。
换成 `ProcessBuilder` 调系统命令后，**jlink 定制运行时实测省 14.51 MiB**。

| 项 | 命令 | 结果 |
|---|---|---|
| 单测 | `mvn -o test -Dtest=BrowserLauncherTest` | **14 用例全绿** |
| 新增变异（子集） | `ONLY='破坏Ⓐ\|Ⓑ\|Ⓒ\|Ⓓ' ./tools/control-experiment.sh` | **4/4 PASS**，invalid=0，基线复核 GREEN |
| 残留备份 | `find src -name '*.bak' \| wc -l` | **0** |
| 对照实验总数 | `grep -c '^run_case' tools/control-experiment.sh` | **93 条**（89 → 93） |
| 体积实测 | `bash work/probe_jlink_size.sh` | 见下表 |

### jlink 体积实测（macOS arm64 / JDK 21.0.12.1）

模块集合由 `jdeps --print-module-deps` 从 fat jar 实算，不是手列的：

| 运行时 | 大小 |
|---|---|
| 含 `java.desktop` | 51,639,978 B = **49.25 MiB** |
| 去掉 `java.desktop` | 36,427,898 B = **34.74 MiB** |
| **差额** | **15,212,080 B = 14.51 MiB（-29.5%）** |

> 用 `find -exec stat -f%z` 累加真实文件大小，不用 `du -sk`——后者受块大小影响，
> 对成千个小文件会虚高好几 MB。

**精简运行时真的能干活**（不是「建出来就完事」）：用 `jlink-probe/without/bin/java`
实跑了 txt 脱敏（3 处命中正确）、`rules` 规则查询、`serve` 起 HTTP 服务，全部正常。

## 二、实测记录（写代码前先跑的探针）

不凭印象写。`work/ProbeBrowse.java` / `work/ProbeBrowseStdin.java` 的结论：

| 探针发现 | 影响 |
|---|---|
| macOS `open <url>` → exit 0 | 可行 |
| 命令不存在时 `ProcessBuilder.start()` 抛 **`IOException`**，不是「返回 false」 | 判据必须是 catch 异常，只判断命令存在的实现会把异常抛给调用方 |
| 子进程输出走管道时，写满 65520 字节缓冲后**子进程阻塞在 write，父进程 `waitFor` 等它退出 → 死等** | 必须 `Redirect.DISCARD`（连管道都不建） |
| `open` 把以 `-` 开头的参数**当成自己的选项**（实测 `open -weird-flag` 报 `invalid option -- w`） | URL 必须先校验，不能直接丢进去 |
| `open -u` 强制按 URL 处理 | 少了 `-u`，`open` 会按「文件」规则找默认程序 |

## 三、三条设计决定

### 3.1 纯逻辑与启动分离

`commandFor(osName, url)` 与 `isLaunchable(url)` 都是纯函数，逐平台可断言；
真正启动那一步在 `open(url)`。

`java -version` 能跑**不算证据**——所以另有一次真实脱敏的验证（见上）。

### 3.2 命令可注入，为了让失败路径在任何平台可测

`open(String url, List<String> cmd)` 这个重载不是多余的。
第一版 `open` 内部自己读 `System.getProperty("os.name")`，
于是「命令不存在」这条分支**只在当前系统恰好缺那个命令时**才被走到——
在 macOS 上跑测试时 `rundll32` 根本不会被执行，
「去掉 catch IOException」这个变异会得到 GREEN，而它本该是红的。

注入命令之后，这条路径在哪个平台都能被咬住。

### 3.3 `InterruptedException` 必须恢复中断标志

「失败一律吞掉」针对的是**浏览器打不开**，不是**线程被打断**。
打断通常意味着整个进程正在被关停；把中断标志清掉等于告诉上层「没被打断」，
关停逻辑会继续跑，进程可能半死不活地留着。

## 四、四条变异

| 编号 | 变异 | 撤掉后的症状 | 判据 |
|---|---|---|---|
| Ⓐ | 命令不存在时抛异常而不是返回 false | Windows 上 `rundll32` 缺失 → 服务起不来 | `missingCommandIsSwallowed` 断言失败 1 条 |
| Ⓑ | 放行非 http/https 协议 | `file:///etc/passwd` 被交给系统打开 | 失败 4 条 |
| Ⓒ | 撤掉 `isLaunchable` 守卫 | `file://` 也会被真的启动 | 失败 1 条 |
| Ⓓ | Windows 用 `open` | Windows 上没有这个命令，浏览器永远打不开 | 失败 1 条 |

> Ⓒ 的判据必须配一个**真能跑起来的命令**（`/bin/sh -c exit 0`）。
> 用「不存在的命令」去测的话，守卫撤掉后 `open()` 照样返回 false（启动失败），
> 测试仍然全绿——那是空操作变异，会给出一个假的 GREEN。

另有 `BrowserLauncherTest.noJavaAwtDependency`：扫 **class 常量池**（不是源文件）
确认 `BrowserLauncher.class` / `ServeCommand.class` 里没有 `java/awt` / `Desktop` / `GraphicsEnvironment`。

> 第一版这条扫的是**源文件**，结果 `src/main/java` 不在测试 classpath 上，
> 测试直接报「读不到源码」——于是这条守卫**从未真正生效**。
> 扫 class 既精确（注释里当然可以写「为什么不用 Desktop」），
> 又不依赖「源码在不在 classpath 上」这个前提。

### 4.1 Ⓐ 第一次跑出来是 INVALID，成因不在实现、在测试

变异把 `IOException` 抛出去而不是吞掉，测试确实红了，但 surefire 记的是
`BrowserLauncherTest … 错误1 失败0`——**Error 而非 Failure**，断言失败 0 条。
按规矩这判 INVALID 作废：抛异常红不等于测试咬住了实现。

查下来问题在测试这边。原用例是裸调：

```java
assertFalse(BrowserLauncher.open(URL, List.of("litemask-no-such-command")));
```

`open` 的契约「失败一律吞掉」只写在 javadoc 里。实现违约时，
异常直接甩到测试方法上，JUnit 记 Error。**契约写了但没被断言，等于没测。**

改成 `assertDoesNotThrow(() -> …)` 包一层之后，红灯原因变成
`失败1 错误0` ——断言失败，实验有效。这条对任何「不许抛」的契约都适用。

### 4.2 顺带修掉的：源码里落了两个 U+FFFD

`BrowserLauncherTest` 第 53 行 `@DisplayName("不认识这个系统返回空命令，不瞎猜")`
里有两个**真实的 U+FFFD 替换字符**（不是终端显示问题，文件本身是合法 UTF-8，
但那两个码位就是写进去的）。已修为「不认识这个系统返回空命令」。

> ⚠️ 本节里这两个 U+FFFD 是**故意保留的**：它引用的是修复**之前**的样子，
> 删掉它们这段就看不出当时坏成什么样了。源码 `BrowserLauncherTest` 现在是干净的。

出现的位置是中文注释/文案，说明**批量写文件时某一轮的字符被截断替换了**。
它不会让任何测试变红，只会让一条用例的名字显示成乱码——这类东西最容易被
当成「终端字体问题」放过去。

## 五、已知限制 / 未验证

- **只实测了 macOS**。Windows 的 `rundll32 url.dll,FileProtocolHandler` 与 Linux 的
  `xdg-open` 只有纯函数断言覆盖，**没有真机验证过能打开浏览器**。
- **Windows 侧体积未测**：jlink 产物是 macOS arm64 的，win-x64 的体积要等 M4。
- **90MB 硬指标**：核心包 = fat jar 17.76 MB + jlink 运行时 34.74 MiB ≈ **52.5 MB**（未含模型包）。
  这个数还没把 M3-2 的模型包算进来，属于 M3-4 的账。
- **NER 仍然默认关闭**：实测里 `张三` / `北京星辰贸易有限公司` 没有被脱——
  模型包加载器属于 M3-2，不是本阶段范围。
