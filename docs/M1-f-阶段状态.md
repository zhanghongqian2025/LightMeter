## 二、VIN 校验位：为什么不能做门禁

### 依据

取自 `en.wikipedia.org/wiki/Vehicle_identification_number`（ISO 3779 条目原文）：

1. 校验位 *"compulsory for vehicles in North America and China, **but not so in Europe**"*
2. 欧洲厂商 *"started to encode ... the control digit during 2009–2015 for selected models"*，且 *"not in all brand-models"*
3. **同一条目收录的两个真实欧洲 VIN 明确标注过不了校验位**：
   - `WP0ZZZ99ZTS392124`（保时捷 911 照片里的车）
   - `KLATF08Y1VB363636`（GM-T 车身照片里的车）
4. 第 10 位年份码 *"Outside of North America the 10th digit is usually 0"* —— 所以把年份码当门禁同样会误拒欧洲车

### 为什么方向不能反

脱敏工具的两类错误代价完全不对称：

- 误拒一个真 VIN → **它没被脱敏，原文留在交付的文档里**。这是隐私泄漏，而且是静默的。
- 误纳一个假 VIN → 原文位置多一个令牌。而那个串本来就不是真的 VIN，**没有任何信息因此丢失**。

所以门禁方向选错，直接换来数据泄漏。

### 实现

- `Validator.vinCheckDigit(String)`：ISO 3779 模 11 换算，余 10 记 `X`。
  **返回 `0` 表示"算不了"（长度不对 / 含 I、O、Q），不是"结果是 0"** —— 调用方必须能区分这两件事。
- `Validator.vinCheckDigitOk(String)`：诊断信号，**不参与命中判定**。
- `Validator.VIN` 门禁逻辑**一字未改**（长度 17 + 字符集排除 I/O/Q + 至少一个字母），只在 javadoc 里把"计划补校验位"改成了上述实测结论。

### 留下的防线

`VinCheckDigitTest.真实欧洲车架号仍然通过门禁被识别` 断言那两个反例 VIN **仍然被脱敏规则命中**。
将来谁"顺手"把校验位加进 `VIN.isValid`，这条立刻红；对应的对照实验 ㊿ 就是把这件事真的做一遍。

## 三、发票号码：为什么 20 位无条件、8 位要引导词

### 先看真实样本

从 ofdrw 仓库的 `发票示例.ofd` 里，同一个号码 `24112000000048542163` 出现在**两处，上下文完全不同**：

```
OFD.xml        <ofd:CustomData Name="发票号码">24112000000048542163</ofd:CustomData>
Content.xml    <ofd:TextCode X="0" Y="3.6414" DeltaX="g 19 1.5875">24112000000048542163</ofd:TextCode>
```

把 `Content.xml` 那一页所有 `TextCode` 的文字按顺序打出来是：

```
24112000000048542163 / 2024年05月28日 / 海南麒麟云服科技有限公司 / 91460300MAA92DJN95 / ...
```

**页面正文里没有任何标签文字**，标签在模板页（`Tpls/`）里，是一个独立的文本对象。
OFD 的"标签"和"值"在文本层面根本不相邻。

→ **纯上下文锚定会漏掉正文这一处。** 这是先解剖样本、而不是照着直觉写正则的直接回报。

### 规则

```
(?<!\d)\d{20}(?!\d) | (?<=发票(?:号码|号)[：:\s]{0,5})\d{8}(?!\d)
```

- **20 位无条件识别**：足够独特（与银行卡 16–19 位、身份证/信用代码 18 位都不重叠），漏掉的代价是隐私泄漏。
- **8 位必须带引导词**：裸 8 位数字会与日期、金额、数量混淆。

### 为什么没有校验码

- 票面「校验码」是**密码区**，不可推导；
- 20 位号码的官方生成规则**没找到可查证的公开资料**；
- 我试过的猜测权重（对前 10 位算得 5，与实际末位 0 不符）已判定不可用，**没有采用**。

规则 description 里如实写明了这一点，不含糊过去。

## 四、不信任文档：实测到什么，就补什么

### 实测（M1-f 探针，不是推理）

| 探针 | 结果 |
|---|---|
| zip 炸弹 | 597KB 的包 → **600MB**，中央目录 `getSize()` 报 629145600，实际真能读出 629145600。原来的 `readEntry` 用 `readAllBytes()` **整个进堆** |
| 超深 XML 解析 | Xerces 解析 **20 万层不抛异常也不爆栈**（-Xmx512m）——我原本以为会 StackOverflow，**错了** |
| StAX 流式数深度 | **50 万层不爆栈**，且能在第 513 层提前放弃——深度预扫描方案可行 |

于是防护重点**压倒性地放在"流式计数 + 硬上限"**，深度限制退居其次（仍是廉价纵深防御）。

### 防护清单与默认限额

| 项 | 上限 | 判定时机 | 为什么是这个数 |
|---|---|---|---|
| zip 条目数 | 20000 | 打开时 | 真实办公文档几十~几千条 |
| 单条目解压量 | 256MB | 流式读/写，每 64KB 判一次 | 真实 part 在几百 KB 量级 |
| 整份文档解压总量 | 2GB | 同上，跨条目累计 | 没被改过的 part 走流式拷贝、不进堆，但**照样扣预算** |
| XML 嵌套深度 | 512 | **建 DOM 之前**，StAX 流式数 | 真实 OOXML 在 20~40 层，留了一个数量级余量 |
| 条目名 | 拒绝绝对路径与 `..` 穿越 | 打开时 | 真实 docx/xlsx/pptx/ofd 不会出现 |

**限额按实际读到的字节判定，不看 `ZipEntry.getSize()`** —— 那个值来自中央目录，是文件作者自己填的。

### 一个容易被漏掉的洞

没被改动过的 part 在写回时走**流式拷贝**，不进堆。如果只对"读过的"扣预算，把炸弹塞进 `word/media/` 就能绕过总量上限把磁盘写满。
所以 `write()` 对拷贝路径同样扣预算。对照实验 ⒁ 专门钉这一条。
（第一次写这条实验时它没能咬住——因为只压到了单条目上限，单条目那道还在挡。补了"三条各 60 字节、上限 128"的总量场景才真正咬到被撤的那一层。）

## 六、本轮修掉的真实缺陷

| # | 缺陷 | 怎么发现的 |
|---|---|---|
| 1 | `Validator.vinCheckDigit` 用 `VIN_TRANSLITERATION.indexOf(字母)` 查换值表，而那张表存的全是数字 → **恒为 -1，所有合法 VIN 都返回 0** | 新测试 `维基算例算出X` 直接红 |
| 2 | `VinCheckDigitTest.probeWith()` 拼出 16 位而不是 17 位 | 同上，红灯消息"expected X but was \<空\>" |
| 3 | 我自己写的 `invoice_no` 负样本 `"...20 位 32"` —— 20 位后面跟空格，按设计**就该命中**，是我把样本写错了 | RuleSampleTest 报"本不该命中却误报" |

| 5 | **对照实验脚本复合变异会静默污染工作区**：同一文件连续变异时，每轮都 `cp` 一次备份，后一次 cp 拿到的是**已变异的状态** → 最后只回滚了后面几步，源码留在变异态而 `.bak` 已消失 | 脚本的基线复核报了"实验污染了工作区"（**这条防线起作用了**） |

第 5 条值得单独说：**它不会让任何一条测试变红**，只会在收尾时留下一份行为不同的源码。如果基线复核没做断言，这个 bug 会安静地活到下一次开发，被误判成"我改坏了"。

## 八、关于 XXE 防护的诚实结论

XXE 防护实际是**六层**叠加：StAX 的 `SUPPORT_DTD` / `IS_SUPPORTING_EXTERNAL_ENTITIES`，DOM 的
`disallow-doctype-decl` / `FEATURE_SECURE_PROCESSING` / `ACCESS_EXTERNAL_DTD`，加兜底 `EntityResolver`。

我写了探针逐层拆开实测（探针真的把本机文件内容读进了 DOM 才作数）：

| 拆掉的层 | 观察到的结果 |
|---|---|
| StAX `SUPPORT_DTD=false` | StAX 报 `entity "xxe" was referenced, but not declared` |
| StAX `IS_SUPPORTING_EXTERNAL_ENTITIES=false` | 解析成功，**内容为空** |
| DOM `disallow-doctype-decl` | 报 `DOCTYPE is disallowed` |
| DOM 全拆（对照） | **真的泄漏，读出了 `TOP-SECRET-CONTENT-DO-NOT-LEAK`** |

**结论：单独撤掉任何一层，对面那层都还在拦。** 所以任何单点变异都抓不住 —— 这不是探针失效，是纵深防御在挡。
对照实验 ⒈ 因此把六层一起拆，副作用是**六层全部写进了脚本**，将来有人删掉其中任何一层都看得见。

## 九、如实呈现的局限与缺口

1. **发票号码没有校验码**。没有公开可查证的算法，不自编。误报风险：任意裸 20 位数字串都会被脱敏（代价是一个多余令牌），漏报风险：0。
2. **VIN 校验位只做诊断，没有接进用户可见的报告**。`Validator.vinCheckDigitOk` 目前只被测试调用，CLI 不会提示"这处车架号校验位不符"。接进报告是有价值的下一步（M2 做界面时一起）。
3. **限额是常量，不可配置**。256MB 单条目 / 2GB 总量对单机场景够用，但用户遇到超大扫描件 PDF（不进这条路径）或超大 xlsx 时无法调整。
4. **防护只覆盖四种 zip 文档**。PDF 走 PDFBox，其解析器自身的资源上限不在本轮范围内。
5. **端到端里的正常文档样本是我手搓的最小 docx**（真实 OOXML 命名空间 + 单一 `<w:p>`）。它证明链路通，不证明对 Word 生成的各种变体都健壮；真实样本的覆盖要等 M2 之后接入更多真实卷宗。
6. **深度上限 512 是拍的**，依据是"真实 OOXML 在 20~40 层"这个经验值，没有大规模真实语料的分布统计。
7. **窗口文件符 `\r\n` 未做特殊处理**——已有行为，非本轮引入。
